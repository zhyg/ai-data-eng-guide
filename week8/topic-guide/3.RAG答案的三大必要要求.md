# 导学 03：AI 答完了，凭什么让人信？

## 一句话理解

生产级 RAG 的答案必须满足三个硬性要求：结构化输出（机器可解析）、引用来源（可追溯）、置信度（知道自己不确定时别硬答）。

## 用生活打比方

继续我们的急诊室。医生看完检查结果，给病人开药。如果医生只是口头说"吃点消炎药"，没有处方单、没写依据、没标注过敏风险，这张"处方"在药房拿不了药，出了问题也查不到是谁开的、根据什么开的。

生产级 RAG 的答案也一样。Demo 阶段返回一段文字看着没问题，但上线后客户会问：这个答案从哪来的？能看原文吗？你有多大把握？如果回答不了这些问题，答案就不可信。

所以 AI 的输出必须像正规处方单一样：格式固定（前端能解析）、标注依据（能跳转到原文）、标注把握程度（把握不大就转人工）。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **结构化输出（Structured Outputs）** | 让 AI 的回答严格按照预定义的 JSON 格式输出，每个字段都有明确定义。比如答案、引用、置信度各有对应字段，前端直接解析，不用再猜格式 |
| **引用（Citations）** | 答案里每条结论都标注"这个信息来自哪个文档的哪个位置"，精确到字符级别。用户点击就能跳转到原文，不是 AI 自己编的来源 |
| **置信度（Confidence）** | 每条证据带一个分数，表示 AI 对这条证据的把握程度。分数低于设定的阈值时，系统不硬答，而是提示"建议咨询人工" |
| **JSON 契约（Schema）** | 对 AI 输出格式的强制约定。用 JSON Schema 定义好每个字段的名字、类型、是否必填，AI 输出时严格按格式来，不会出现字段缺失或格式错误 |
| **上下文工程（Context Engineering）** | 控制喂给 AI 的信息：放什么、放多少、按什么顺序放。不是塞越多越好，超过一定量 AI 会"中间失忆"，最相关的证据要放在最显眼的位置 |
| **Prompt 缓存（Prompt Caching）** | 把不变的系统指令缓存起来，每次请求只传变化的部分（用户问题和检索结果）。读缓存的成本远低于正常调用 |

## 避坑提醒

- **以为在 Prompt 里写"请按 JSON 格式输出"就行**：靠 Prompt 要求 AI 输出 JSON，总有一定概率格式出错（多个逗号、漏字段等）。用 Structured Outputs API 才能保证格式合规。
- **以为引用可以让 AI 自己生成**：AI 自己编引用经常张冠李戴，看着有出处但实际对不上原文。必须用原生的 Citations API，由模型从给定的文档中定位引用，而不是让它自由发挥。
- **以为所有问题 AI 都应该给出答案**：当置信度低于阈值时，硬答的结果大概率是错的。正确的做法是设置兜底策略，让系统回复"无法确认，建议咨询人工"。
- **以为上下文塞得越多 AI 答得越好**：上下文超过一定长度后，AI 对中间位置的信息回忆能力明显下降。控制在少量高质量证据，比大量堆砌效果好得多。

## 一句话总结

> **结构化输出、原生引用、置信度兜底，三者是生产级 RAG 答案的合规基线，少一个客户验收都过不了。**
