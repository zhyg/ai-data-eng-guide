# 导学 01：为什么 Demo 好用的检索一上线就不灵了？

## 一句话理解

纯向量检索只擅长"意思相近"的匹配，遇到订单号、错误码、专有名词这类必须字面精确命中的场景就会失效，生产环境必须同时跑向量和关键词两路检索。

## 用生活打比方

这一周我们用"急诊室看病"来串起所有概念。

你去急诊室，护士需要快速判断你的情况。如果护士只会一种检查方法，比如只会量体温，那发烧的病人能识别出来，但骨折的、过敏的就全漏了。反过来，如果只会看外伤，内科问题又全漏了。

检索也是同一个道理。向量检索像"看症状描述"，能识别"我头疼""我脑壳痛"是一回事（语义相近）。但如果病人报的是一个具体的病历编号，靠症状描述根本匹配不上，必须用另一种方法去精确查编号。

所以急诊室需要多种检查手段配合，检索也需要向量 + 关键词两路同时跑，再把结果合并排序。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **向量检索（Dense Retrieval）** | 把文字转成一串数字（向量），用数字之间的距离衡量"意思像不像"。比如"退货"和"退款"距离很近，能匹配上 |
| **BM25 检索（Sparse Retrieval）** | 按关键词出现的频率打分，专有名词、编号、错误码这类精确字符串是它的强项 |
| **混合检索（Hybrid Search）** | 同时跑向量和 BM25 两路检索，再把两边的结果合并成一份排名。两者互补，生产环境的默认配置 |
| **RRF 融合算法（Reciprocal Rank Fusion）** | 合并两路排名的方法：只看每条结果在各路中的排名位置，不看分数本身。好处是不用操心两边分数尺度不同的问题 |
| **查询改写（Query Rewrite）** | 用 AI 把用户口语化的提问改成更精确的检索用语。比如把"那个产品多少钱"改写成带有明确产品名称和属性的查询，召回率会明显提升 |
| **自适应 RAG（Adaptive RAG）** | 先判断用户问题的类型（简单事实、多步推理、数值计算等），再分流到不同的检索路径。简单问题走便宜快速的通道，复杂问题才走高成本通道 |

## 避坑提醒

- **以为 Demo 效果好就能直接上线**：Demo 测试的问题往往是语义类的（"怎么退款""售后流程"），一上线遇到编号、错误码、专有名词，纯向量检索的召回率会大幅下降。
- **以为 BM25 过时了可以不用**：BM25 在精确匹配场景依然是最强的。向量和 BM25 不是替代关系，是互补关系，生产环境两个都要跑。
- **以为检索效果差就该换更好的向量模型**：很多时候问题出在用户的提问本身太模糊。加一层查询改写，不换任何检索组件，召回率就能大幅提升。
- **以为所有问题都该走最强的检索链路**：大部分用户问题是简单事实查询，走最基础的混合检索就够了。全部走复杂链路只会浪费钱和时间，用自适应路由按类型分流才合理。

## 一句话总结

> **混合检索是生产 RAG 的默认配置，在此基础上加查询改写和自适应路由，比单纯升级向量模型更有效。**
