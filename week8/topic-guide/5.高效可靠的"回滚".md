# 导学 05：出了事故，怎么 30 秒恢复到上一个好的状态？

## 一句话理解

把索引、Prompt、模型、评测报告四样东西用一个版本号绑在一起，回滚时只需要切换这个版本号的指向，不需要重新部署。

## 用生活打比方

继续我们的急诊室。假设急诊科主任最近批准了三项更新：换了一批新药、修订了用药指南、升级了检验设备。周末突然有医生反馈治疗效果变差了。排查时发现，问题可能出在新药，也可能是新指南，也可能是新设备，但三项是分别批准的，组合太多，排查了很久才定位。

如果科主任每次更新都打包成一个"标准操作版本号"（第 15 版 = 某批次药品 + 某版指南 + 某代设备 + 上一轮质检报告），出问题时直接切回"第 14 版"，所有环节一起回退，不用逐个排查。

RAG 服务的回滚也是这个逻辑。索引、Prompt、模型、评测报告四样东西各自独立变化，任何一个变了答案就可能变。把它们用一个 release_id 绑在一起，回滚就是把指针从新版切回旧版。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **release_id（版本标识）** | 一个唯一编号，把索引版本、Prompt 版本、模型版本、评测报告打包绑定。所有 AI 的回答都带着这个编号，出了问题能精确追溯到是哪个版本 |
| **Release Manifest** | 一份 YAML 配置文件，记录了某次发布的全部信息：用了哪个索引、哪版 Prompt、哪个模型、评测跑分多少。相当于这次上线的"出厂合格证" |
| **原子绑定** | 索引、Prompt、模型、评测报告四样东西必须一起上线、一起回滚、一起审计，不能各自独立部署。否则出问题时不知道是哪个组合导致的 |
| **指针切换回滚** | 系统维护一个"当前激活版本"的指针，回滚时只改这个指针的指向，不需要改代码、不需要重新构建镜像、不需要重跑 CI |
| **灰度发布（Canary）** | 新版本先只让一小部分用户使用，观察指标稳定后逐步扩大范围。出问题时只影响小部分用户 |
| **成本工程（Cost Engineering）** | 通过 Prompt 缓存、路由到便宜模型、精排替代全量喂 AI 等手段降低月账单。几种手段组合使用能大幅降低成本 |

## 避坑提醒

- **以为重启服务就算回滚**：重启服务需要 git revert、重新构建、重新部署，最快也要半小时。用 release_id 切指针，30 秒就能恢复，完全不碰代码和部署流程。
- **以为索引、Prompt、模型可以各自独立上线**：三样东西分别部署，出了问题需要排查所有组合才能定位原因。原子绑定后，回滚一个 release_id 就把三样都恢复了。
- **以为答案不需要带版本信息**：如果 AI 的每条答案不带 release_id，客户问"上周的答案为什么不一样"，你根本查不到当时用的是哪个版本的索引和 Prompt。
- **以为新版本效果好就可以直接全量上线**：测试环境和生产环境总有差异，直接全量切换一旦出问题就是所有用户受影响。从小比例灰度逐步扩大到全量的分阶段发布是基本纪律。

## 一句话总结

> **release_id 把索引、Prompt、模型、评测原子绑定，回滚只需切指针，事故响应从几小时缩短到 30 秒。**
