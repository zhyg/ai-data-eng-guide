# 导学 06：怎么把前面学的东西组装成一条能上线的链路？

## 一句话理解

本节是工程实践课，把前五节的混合检索、精排、受约束生成、Prompt 管理和版本治理，组装成一条从查询到回答的完整 RAG 服务链路。

## 用生活打比方

继续我们的急诊室。前五节课分别讲了分诊怎么做、专家会诊怎么筛、处方单格式要求、诊疗指南管理、出了事怎么快速恢复。这节课要做的是：把这些环节串成一条完整的急诊流程，从病人进门到出院，每一步都有标准操作、有质量检查、有记录可查。

流程是这样的：病人进门 → 护士分诊（查询理解）→ 多种检查同时做（混合检索）→ 专家筛选关键结果（精排）→ 医生看最相关的结果开处方（受约束生成）→ 处方单入系统存档（RAG API 输出）。横贯全流程的是：整个急诊科按同一版标准操作规程（release_id）运行，每一步都有记录，每条记录都能追溯到当时用的哪版规程，出了问题能完整回溯。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **六阶段链路** | RAG 服务从左到右分六步：资产增强 → 索引构建 → 查询理解 → 混合检索 + 精排 → 受约束生成 → API 服务。每步独立，串起来就是完整的生产链路 |
| **资产增强** | 在上一周产生的文档切片基础上，补充评测字段、观测性字段、引用字段等，让切片具备被检索、被追踪、被评测的能力 |
| **索引构建** | 对切片做向量化（Embedding），生成索引清单（Index Manifest），记录这次构建用了什么模型、多少条数据、构建时间。支持试运行模式，不写入真实数据也能验证流程 |
| **RAG API 契约** | 服务的输入和输出都有严格定义。输出必须包含答案、引用、证据 ID、置信度、版本号、追踪 ID，缺一个都算不合规 |
| **审计日志（rag_audit_log）** | 记录每次 AI 回答的完整上下文：用了哪些过滤条件、命中了哪些证据、各项分数多少、对应哪个版本。Bad Case 通过追踪 ID 就能还原问题全貌 |
| **契约测试** | 上线前必须通过的 6 项检查，包括输入格式校验、正常/异常输出格式校验、引用完整性校验、RRF 算法正确性校验等 |

## 避坑提醒

- **以为把各模块代码拼在一起就是"一体化"**：一体化的关键不在代码怎么组织，而在数据怎么流转和追溯。每个环节的输出必须带版本信息和追踪 ID，能串成一条完整的审计链。
- **以为检索不到内容时让 AI 自由发挥就行**：检索不到证据时，应该返回空答案并说明原因，而不是让 AI 猜测。AI 猜出来的答案没有依据，风险很高。
- **以为上线前跑通一个测试用例就够了**：契约测试覆盖正常路径和异常路径，包括"有答案""无答案""缺引用""拒绝回答"等多种场景，所有检查项全部通过才能上线。
- **以为索引构建不需要记录**：每次索引构建的模型版本、数据量、构建时间都要记录在 Index Manifest 里，和 release_id 关联。没有这个记录，索引版本就无法追溯和回滚。

## 一句话总结

> **生产级 RAG 是六个阶段串联加全链路追溯，能跑通不算完成，能审计、能回滚、能通过契约测试才算上线就绪。**
