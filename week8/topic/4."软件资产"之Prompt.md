# 4. "软件资产"之 Prompt

## 核心问题

Prompt 不是 .py 里的字符串，是「软件资产」。2023 年 prompt 硬编码在代码里没事，2025 年客户已经不允许。本节从「Prompt as Code」的 4 大支柱出发，讲解版本化、模板化、测试化、发布化，以及 Eval 金字塔、LLM-as-Judge、Bad Case 库和 Drift 漂移监测。

## 真实场景：Prompt 硬编码翻车

某项目 prompt 直接 hardcode 在 .py 里，PM 想改一个字段，工程师周五下班前改了 push 上线。周六客户反馈 RAG 答案突然变了，排查 4 小时，最后发现是改了 system prompt 里的一句语序。根因不是工程师粗心，是没把 Prompt 当代码管理——没版本、没 Review、没 Eval。

## Prompt as Code 的 4 大支柱

少一个都不算工程化：

| 支柱 | 具体做法 | 决定了什么 |
| :--- | :--- | :--- |
| **Versioned（版本化）** | Git 管理 prompts/*.j2，Semantic versioning (v1.2.0)，每个 prompt 有 PR + Review，prompt_id + version 入 evidence | 能不能回退/追责 |
| **Templated（模板化）** | Jinja2 / Handlebars 模板，业务变量从代码注入，不在 prompt 里写硬编码值 | 能不能维护 |
| **Tested（测试化）** | Golden set 50-200 真实样本，CI 跑 Ragas / DeepEval，回归测试阻断 PR | 能不能不翻车 |
| **Released（发布化）** | canary 灰度 5% → 100%，指标自动监控 + 回滚，prompt_version 进 release.yaml | 能不能 24x7 运维 |

## Golden Set 回归测试

Prompt 改一字段就跑全套，50-200 真实样本 + Ragas + DeepEval + GitHub Actions CI 阻断。

核心机制：
- 参数化测试新旧两版，一次跑两版直接看 diff
- Ragas 三件套（2025 事实标准）：faithfulness（忠实度）、answer_relevancy（相关性）、context_precision（上下文精度）
- 阈值阻断：faithfulness >= 0.85，context_precision >= 0.80，新版不能比旧版低 3%
- PR 触发自动跑，指标退化则阻断 merge

## A/B 测试 + Canary 灰度发布

不是「直接全切新版」，而是三阶递进：

```
Dev（本地测试, pytest + golden set）→ Stage/Canary 5%（真实流量, 监控核心指标）→ A/B 25%（对比观察 p99/quality/cost）→ Rollout 100%（指标稳定后 full rollout）→ Watch（持续监控, 回滚预案）
```

关键指标监控（自动触发回滚）：
- Faithfulness 退化 > 3% → 立刻回滚
- P95 延迟上升 > 20% → 立刻回滚
- Cost 上升 > 30% → 告警

## Eval 三层金字塔

80% 团队上线后才补 Eval，Day 1 就该建。

| Eval 层 | 问什么 | 核心指标 | 工具 | 上线门槛 |
| :--- | :--- | :--- | :--- | :--- |
| **L1 检索质量** | Reranker 排没排对？ | Recall@K / MRR / NDCG / Hit Rate | Ragas context_precision | Recall@5 >= 80% |
| **L2 端到端** | Agent 答案对不对？ | Faithfulness / Answer Correctness / Citation Acc | Ragas + LLM-as-Judge | Faith >= 0.85 |
| **L3 业务效果** | 用户满意吗？ | CSAT / 转化率 / Deflection 率 | Product Analytics | CSAT >= 4.2/5 |

L1 跑全量/每次 PR，L2 跑全量/每天，L3 持续在线，三层缺一不可。

## LLM-as-Judge 自动评测

生产用 Sonnet，judge 用 Opus/GPT-5（比生产强 1 档）。核心流程：

1. 把答案拆成 N 条独立断言（atomic claim）
2. 对每条断言判断：supported / partial / unsupported / irrelevant
3. faithfulness_score = supported / total
4. 每条跑 3 次取均值，方差 < 0.05 才可信

评测 1000 条成本约 $30-100（Opus）。

## Bad Case 库：上线后最重要的资产

产品里加 thumbs down，下来的 case 每周专家 review 50-100 条，3 个月 bad case 库就值百万。

4 类 root_cause 标签：

| 类别 | 含义 | 修复方向 |
| :--- | :--- | :--- |
| **retrieval_miss** | 没召回到正确 chunk | 修 Hybrid / Query Rewrite |
| **rerank_wrong** | 召回对了但 rerank 排错 | 调 reranker / 加 LLM judge |
| **hallucination** | context 对了但答案乱编 | 加 Citations / 紧 Schema |
| **knowledge_gap** | 知识库根本没这个内容 | 补数据 / 标 fallback |

Bad Case 比 golden set 更有信号，是真实用户痛点的快照。每次 prompt / model 大改前全量跑回归测试，阻断 merge。

## Drift 漂移监测

上线 1 个月后效果一定会漂，早发现早修。3 个监控点：

| 监控点 | 统计方法 | 告警阈值 | 修复方式 |
| :--- | :--- | :--- | :--- |
| **Embedding 漂移** | KL divergence / MMD | > 0.15 → 告警 | re-embed 增量数据 |
| **Retrieval 漂移** | Recall@5 周环比 | 下降 > 3% → 告警 | 扩 golden set 重训 |
| **Answer 漂移** | Faithfulness / CSAT 周环比 | Faith < 0.85 → 告警 | 回滚 release_id |

没有 Drift Detection 的 RAG 上线等于闭着眼开车，3 月内必出大事故。

## 五个常见反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| Prompt hardcode | 直接 SYSTEM = "..." 在 .py | 无版本/无 Review | Git + Jinja2 模板 |
| 改一字段不测试 | PM 想改就上线 | 5% 请求质量下降 | Golden set + CI 阻断 |
| 没有版本号 | 一个 prompt 改 100 次 | 出问题不知道怎么回退 | semver + prompt_id |
| 不入 evidence_anchor | 答案不知道用的哪版 prompt | 审计断链 | prompt_version 必入 |
| 直接全切新版 | 不经 canary 上线 | 事故概率指数级上升 | 5% → 25% → 100% 三阶 |
