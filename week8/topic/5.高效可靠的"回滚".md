# 5. 高效可靠的"回滚"

## 核心问题

事故响应从「6 小时排查 + 重新部署」变成「30 秒切回上版」。本节讲解 release_id 原子绑定、Release Manifest YAML 设计、秒级回滚机制、Canary + Feature Flag，以及 Cost Engineering。

## 真实场景：找不到「上周的状态」

某团队周五上线 RAG 改动，周六客户反馈「同样问题答得跟上周完全不一样」。排查 6 小时才搞清楚——是改了 prompt 还是换了索引还是切了模型？日志混乱根本对不上时间。根因：没有 release_id 把「索引 + Prompt + 模型 + Eval」原子绑定，任何一个改动都可能引爆事故，又找不到怎么回去。

## 原子绑定 4 件套

RAG 服务有 4 个独立可变的部分，任何一个变了答案行为就会变。如果各自独立部署，排查事故只能「猜」。

release_id 把 4 件套原子打包，上线一起上、回滚一起回、审计一起查：

| 组成 | 内容 |
| :--- | :--- |
| **索引（Index）** | embedding 模型 / 切片版本 / vector db snapshot_id |
| **Prompt 模板** | prompt_id + version（L04 输出） |
| **模型版本** | 精确到 build（如 claude-sonnet-4-6） |
| **Eval 报告** | golden set 跑分快照（faithfulness / context_precision） |

## Release Manifest：RAG 服务的「DNA」

一份 YAML 决定这次上线的全部行为，是治理周的核心制品。

关键字段结构：

| 字段组 | 关键字段 | 说明 |
| :--- | :--- | :--- |
| **顶层** | release_id, created_at, created_by, status | status 流转：canary → active → archived，任何状态都可回退 |
| **index** | snapshot_id, embedding_model, embedding_dim, chunker_version, total_chunks | 锁定索引版本 |
| **prompt** | prompt_id, version, git_sha | 锁定 Prompt 版本 |
| **model** | primary, fallback, rerank, embedder | 锁定所有模型版本 |
| **eval** | golden_set, golden_size, faithfulness, context_precision, citation_accuracy, run_id | Eval 跑分快照 |
| **rollout** | canary_percent, rollback_to | 灰度比例和回滚目标 |

release_id 是「主键」——任何答案都能回查到这个 ID，客户问「上周怎样」直接切 release_id。rollback_to 是兜底——出问题秒切 pointer，不需要重新部署服务。

## 秒级回滚机制

不是「重启 docker」，而是「切指针」。

核心设计：服务中维护一个 ACTIVE_RELEASE 单一指针，所有请求基于该指针加载对应的 release manifest，从中获取锁定的索引版本、Prompt 版本和 LLM 模型。答案自带 release_id，全链路可追溯。

回滚操作 = 改 ACTIVE_RELEASE 这一个变量 → 重启或热更新即可。不需要改代码、不需要重新构建镜像、不需要重新跑 CI。事故响应从 6 小时变 30 秒。

## Canary + Feature Flag

让 RAG 上线像 deploy 代码。按 user_id / tenant_id 分流。

| 工具 | 类型 | 关键特性 | 适用 |
| :--- | :--- | :--- | :--- |
| LaunchDarkly | 商业 SaaS | 企业级 Feature Flag 标杆 / Targeting / Rollout | 生产 RAG 灰度 |
| Statsig | 商业 SaaS | Feature Flag + A/B + Eval 一体 / 免费 tier 慷慨 | 中小团队 |
| Unleash | 开源 | Feature Flag OSS / 自托管 | 自托管首选 |
| OpenFeature | 开源标准 | CNCF 项目 / 跨厂商 SDK | 避免锁定/抽象层 |
| 自研 release.yaml + 路由 | DIY | 简单实用 / 适合小团队 | 默认推荐 |

RAG 灰度策略 4 种维度：
- **按 tenant 分流**：5% 租户先用新版，出问题不影响所有客户
- **按 user 哈希**：20% 用户固定到新版，监控 cohort 指标
- **按 query 类型**：FAQ 类用 v2.0，订单类继续用 v1.5，风险隔离
- **按时段**：低峰期上新版，高峰期回稳定版

## Cost Engineering：让月账单不爆炸

按 10 万 query/月计算，无优化 $48K → 全套优化 $9K，降 81%。

| 优化手段 | 机制 | Cost 降幅 | 上线难度 |
| :--- | :--- | :--- | :--- |
| **Prompt Caching** | 缓存 system + skills | 60-75% | < 1 天 |
| **Router 便宜模型** | 简单 query 走 mini，复杂走 Sonnet | 40-60% | 2-3 天 |
| **Reranker 替代精排** | top-50 → reranker top-5 而非全塞 LLM | 降 75% | < 1 天 |
| **Embedding 自托管** | BGE-M3 / Jina v3 替代 OpenAI | embedding 1/5 | 1 周 |
| **Context Pruning** | Top-K + Token Budget + LongLLMLingua | 50-70% | 2-3 天 |
| **批量化推理** | 低延迟 query 批量化（Anthropic batch） | 50% | < 1 天 |
| **模型蒸馏** | 微调小模型替代大模型 | 80-90% | 1-2 月 |

组合拳：Prompt Cache + Router + Reranker，3 件套立刻能省 65-75%，是 ROI 最高的组合。

## 五个常见反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 重启 docker 算回滚 | 回滚 = git revert + 重启 | 事故响应 1 小时起 | release_id 切指针，30 秒 |
| 4 件套独立部署 | 索引/Prompt/模型各自上线 | 排查事故只能猜 | 原子打包 release.yaml |
| 没 release_id 入审计 | 答案不知道哪个版本 | 客户问追溯不到 | release_id 入 RAGAnswer |
| Prompt 改了不重测 | PM 上线就上，没跑 Eval | 指标退化才被发现 | CI 强制 Eval 阻断 |
| 不灰度直接全切 | canary_percent=100 上线 | 事故概率 5-10x | 5% → 25% → 100% 三阶 |
