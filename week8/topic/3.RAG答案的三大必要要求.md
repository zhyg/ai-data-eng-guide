# 3. RAG 答案的三大必要要求

## 核心问题

Demo 阶段关心「答得对不对」，生产阶段关心「凭什么这么答」。分水岭在于输出是字符串还是 JSON 契约。生产级 RAG 的输出必须可被前端解析、后端审计、客户追溯。本节讲解受约束生成的 4 种机制、Citations API、Structured Outputs，以及 Context Engineering 和 Prompt Caching。

## 从字符串到 JSON 契约

Demo 阶段的典型做法：拼个 prompt → LLM 写一段文字 → 前端 markdown 渲染。上业务验收时客户问「这答案从哪儿来的」——答不出来；「让我看下原文」——没法跳；「换个语言再问一遍为啥结果不同」——无法解释。

生产级 JSON 契约答案需要 4 大约束：

| 约束 | 作用 |
| :--- | :--- |
| **Schema（结构化）** | JSON Schema 强制输出格式，前端可解析，后端可校验 |
| **Citations（引用证据）** | 每条结论带 evidence_anchor，字符级/段落级精度 |
| **Confidence（置信度）** | 每条 evidence 带 score，阈值过滤 + 前端热力图 |
| **Audit（可审计）** | release_id + parsed_at + parser_version，全链路追溯 |

RAG 输出从字符串升级成 JSON 契约，是 To B 客户对 AI 系统的合规基线。

## Anthropic Citations API（2025.1 GA）

模型原生输出引用片段，不靠 prompt hack 让 LLM 说出来源，幻觉率降低 50%。

核心特性：
- 模型 native 输出，不靠 prompt hack
- 引用片段精确到字符级（char_location）
- cited_text 直接用，无需 chunk_id 反查
- 2025.5 更新：PDF 直传、字符级 char_location、跨多文档引用

Citations 配合 Hybrid + Rerank 是 RAG「黄金三件套」。

## OpenAI Structured Outputs（2024.8）

不再在 prompt 里求 LLM 输出 JSON，而是通过 schema 100% 合规。Pydantic BaseModel 直接传给 API，响应自动 parse 到 Pydantic 对象，0 JSON parse error，0 缺字段。

生产价值：
- 前端解析无 try/except
- 后端审计 schema 强保证
- Eval 测试可枚举字段
- DeepSeek / Gemini / Mistral 都已跟进，Structured Outputs 已成 LLM API 标配

## RAGAnswer 完整 JSON 契约

一个 schema 串起前端、审计、评测，是 L01-L05 工程化的「最终产物」：

| 字段组 | 关键字段 | 说明 |
| :--- | :--- | :--- |
| **答案** | answer, evidences, overall_confidence | evidences 是数组，复杂问题需要多源证据 |
| **证据锚点** | chunk_id, doc_id, doc_version, page_no, bbox, cited_text, confidence | 来自第七周的 evidence_anchor，带版本可回退 |
| **审计** | release_id, parsed_at, model_version, retrieval_stage, prompt_version | 任何答案能回退到具体的索引/模型/Prompt 版本 |
| **兜底** | fallback_action | confidence < 0.3 → "ask_human"，不让 LLM 硬编 |

## Context Engineering：喂什么、怎么喂

比模型选型更影响答案质量。Claude 4.8 / GPT-5 都支持 1M context，但实测超过 100k 后开始「Lost in the Middle」——同样 20 条 evidence 放最前/最后 vs 平均散布，答对率差 12-18%。

Context 的目标不是「塞越多越好」，而是「让最相关的 5-10 个 chunk 出现在最显眼位置 + 让结构最清晰」。

Context 的 4 块组成 + XML 标签结构：
1. **system**：角色定义和约束指令
2. **knowledge**：reranker top-k 证据，按分数从高到低排列
3. **history**：对话历史
4. **query**：用户问题放最末位

## Context Pruning：4 种剪枝策略

| 策略 | 机制 | Cost 降幅 | 延迟代价 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| Top-K 截断 | rerank 后只取 top-5 | 50-70% | 0（默认） | 默认首选 |
| Token Budget | 按分排序到 4000 token 上限 | 50-70% | 0 | chunk 长度差异大 |
| LLM Compression | mini LLM 针对 query 压缩 | 50-70% | +200-500ms | 高质量场景 |
| LongLLMLingua | 小模型快速删冗余 token | 40-60% | +50-100ms | 大批量低延迟 |
| Selective Citation | 只保留有 cite 标注 chunk | 30-50% | 0 | Citations API 配合 |
| Hierarchical Summary | 长文档先摘要再注入 | 60-80% | +1-2s（一次性） | doc 单条 >10k token |

先 Top-K，再 Token Budget，顶到极限上 LongLLMLingua。

## Prompt Caching：2026 必用

Anthropic 2024 推出、OpenAI 2025 跟进。将不变的 system prompt 和 Skills 标记为缓存，动态的检索结果不缓存。

- Cache write：1.25x 正常价
- Cache read：0.1x（便宜 10 倍）
- hit rate 80%+ 可达，token 成本降到 1/3 至 1/5

实测：10 万次/月，启用 cache 后 $48K → $14K，setup 不到 1 天，ROI 最高。

## 五个常见反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 只输出字符串 | answer = "...一段文字" | 前端/审计都做不了 | 强制 RAGAnswer schema |
| Prompt 里求 JSON | "请按 JSON 格式输出..." | 5-10% schema 错，上线翻车 | Structured Outputs API |
| Citations 靠 prompt 拼 | LLM 编引用/张冠李戴 | 幻觉引用，客户失信 | Citations API 原生 |
| 没有 confidence | 所有 evidence 一视同仁 | 低质量证据干扰 | score + 阈值过滤 |
| 没有 fallback | 低置信度也硬答 | 客户被错答案误导 | confidence < 0.3 → ask_human |
