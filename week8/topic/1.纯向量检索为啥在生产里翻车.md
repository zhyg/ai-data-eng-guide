# 1. 纯向量检索为啥在生产里翻车

## 核心问题

Demo 阶段纯向量检索看着够用，但生产环境中 30-50% 的查询涉及专有名词、编号、错误码等字面精确匹配场景，纯向量召回率立刻塌一半。本节从「为什么单一检索必坏」出发，讲解混合检索的原理、RRF 融合算法、Query 理解层以及向量库选型。

## 纯向量 vs 纯 BM25：为什么单一检索必坏

| 场景 | 纯向量(Dense) | 纯 BM25(Sparse) | Hybrid 必要性 |
| :--- | :--- | :--- | :--- |
| 专有名词/订单号/编号 | 召不回（语义近邻干扰） | 字面匹配精确 | 高 |
| 同义改写/概念相近 | 召得到 | 字面不匹配 | 高 |
| 代码/标识符/错误码 | 几乎完全失效 | 必杀 | 极高 |
| 长尾语义/推理问题 | 优势 | 关键词不全 | 中 |
| 短词 query（1-3 字） | 向量噪声大 | 频率倒数，中等 | 高 |
| 多语言/跨语种 | 跨语种能力强 | 死锁在原语言 | 高 |

真实案例：客服 RAG 上线后客户问「订单号 N-1234-AB 的退款流程」，向量检索召回的全是「退款/流程/客服」相关的语义近邻，正确订单完全没在 top-50 里。不是模型笨，是「字符精确匹配」场景纯向量天然干不过 BM25。

## 混合检索：2024 后 RAG 的默认配置

向量检索擅长「语义近邻」，BM25 擅长「字面精确」，两者天然互补而非替代。Hybrid Search 同时跑两路检索，用 RRF（Reciprocal Rank Fusion）把两个排序合并，输出统一的 top-k。

工业界验证数据（2024-2025）：

| 方案 | NDCG@10 相对提升 | 来源 |
| :--- | :--- | :--- |
| 纯向量（基线） | 基线 100 | Anthropic 2024 |
| 纯 BM25 | -5% 到 -15% | Anthropic / Pinecone |
| Hybrid（BM25 + Dense + RRF） | +15% 到 +35% | Anthropic 2024 / Pinecone Lab 2025 |
| + Reranker（Cohere 3.5） | +40% 到 +60% | Cohere 2024 / 实测 |

## 四种主流检索策略

1. **Dense（纯向量）**：embedding 模型相似度，语义召回强但专有名词失效，适用于对话和长尾问题
2. **Sparse（BM25/SPLADE）**：词频+倒文档频率，精确匹配快但同义词失效，适用于专有名词和代码
3. **Hybrid（Dense + BM25）**：两路并发 + RRF 融合，互补提升 15-35%，索引双份，适用于 90% 生产场景
4. **Hybrid + Rerank（二阶）**：Hybrid 召 50 条再由 Reranker 精排到 5 条，提升 40-60%，适用于高质量要求场景

## RRF 算法：混合检索的核心融合机制

RRF（Reciprocal Rank Fusion）不需要分数归一化，只看排名。核心公式：对每路检索结果，文档分数累加 `1 / (k + rank)`，k 默认 60。

**为什么不归一化分数？** 不同检索器分数尺度差异巨大（Cosine 0-1，BM25 可达 50+），排名是「天然归一化」。

**为什么不用加权求和？** 加权求和需要归一化算法且权重是超参数，每个数据集都得调，不可移植。RRF 只看排名，完全不依赖分数尺度，跨数据集稳定。k=60 是 Cormack 2009 原始论文实验值，Pinecone / Vespa 工业实测最稳，范围 30-100 影响不大。

## Query 理解层：检索前的 4 件套

用户 query 80% 是「烂的」，先做 query 改写比硬调向量库更有效。真实案例：电商客服 RAG 上线 3 周被骂，Hybrid + Cohere Rerank 全堆上 recall@5 仍然只有 62%，加一层 LLM-based Query Rewrite 后直接跳到 84%，没换任何检索组件。

| 方法 | 机制 | 示例 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **Query Rewrite** | 模糊转明确，LLM 改写口语化 query | "那个产品多少钱" → "Product X 2026 零售价" | 对话型 RAG 标配 |
| **Decomposition** | 复合转子问，LLM 拆解多事实 query | "A 创始人 + 在哪上学" → 两个子问题 | Agent 知识库 |
| **HyDE** | Query 转 Doc，让 LLM 假想答案再 embed | Recall +10-20% | 垂直专业领域 |
| **Query Router** | 判类型分流：事实/关系/计算 | 事实→向量，关系→图，数→SQL | Adaptive RAG 入口 |

## Adaptive RAG：2026 生产最佳实践

不是「全用 Agentic RAG」，而是「Query Classifier + Multi-Path 路由」。

| Query 类型 | 典型样例 | 路由到 | 延迟/成本 | 占比 |
| :--- | :--- | :--- | :--- | :--- |
| 简单事实 | "产品 X 价格" | Naive Hybrid RAG | P50 600ms / $0.002 | 60-80% |
| 多步推理 | "客户 X 去年订单 + 退货" | Agentic RAG (LangGraph) | 3-8s / $0.02 | 10-15% |
| 关系问题 | "A 公司高管之间关系" | Graph RAG (Neo4j) | 1-3s / $0.005 | 3-5% |
| 数值计算 | "上季度 GMV 同比" | SQL / Code Interpreter | 1-2s / $0.008 | 2-5% |
| 闲聊/OOD | "你是谁" | 直接 LLM（不检索） | P50 400ms / $0.001 | 5-10% |

Classifier 用 GPT-4o-mini 或 BGE-M3 微调，每 query 不到 $0.0001，ROI 极高。80% query 走 Naive 省钱省时，15% 走 Agentic 兜底质量，5% 走专用路径。

## 向量库选型：按规模分梯队

| 工具 | 规模 | Hybrid 原生 | 推荐场景 |
| :--- | :--- | :--- | :--- |
| pgvector | < 1M chunk | 需 BM25 自配(tsv) | 中小规模默认选择 |
| Qdrant | 1M-50M | 原生 + RRF | 中型项目/自托管 |
| Weaviate | 1M-100M | 原生 + alpha 融合 | 需要数据契约 |
| Milvus | 100M+ | 原生 + WAND | 超大规模/多模态 |
| Pinecone | serverless | Hybrid API | 不想运维/快速上 |
| Elasticsearch | 海量 | KNN + BM25 一体 | 已有 ES 集群/复用 |

90% 中小项目 pgvector 够用，别一上来就 Milvus，上 100M+ 再切大规模引擎。

## 行业信号

2024-2025 已收敛为「Hybrid + Rerank + 上下文增强」的默认组合：

- **Anthropic Contextual Retrieval**（2024.09）：Chunk 加 50-100 token 上下文前缀 + Hybrid + Reranker，检索失败率 5.7% → 1.9%（-67%）
- **Jina Late Chunking**（2024.09）：先全文 embedding 再切片，长文档跨段引用不丢
- **Pinecone Hybrid + Assistant**（2024-2025）：serverless hybrid 一行 API，Multi-tenant 友好
- **Vespa / ColBERT-late**（2024-2025）：Late interaction 范式，极大规模 + 复杂 ranking 的工业级方案
