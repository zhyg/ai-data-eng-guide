# 6. 检索 X 生成一体化实现

## 核心目标

本节是第八周的工程实践课，目标是把前五节讲解的混合检索、精排门禁、受约束生成、Prompt as Code 和版本治理，组装成一条完整的生产级 RAG 服务链路。整条链路承接第七周产生的非结构化资产（knowledge_doc、knowledge_section、evidence_anchor），在此基础上增强评测、观测性和 Citations 等能力，最终交付可上线、可回滚、可审计的 RAG API 服务。

## 整体架构

整个 RAG 服务链路从左到右分为六个阶段：

```
资产增强 → 索引构建 → Query 理解层 → 混合检索 + 精排 → 受约束生成 → RAG API 服务
```

横穿全链路的能力包括：证据链追溯、版本发布、质量检测和审计日志。

### 资产增强

在第七周产生的 chunk 基础上，补充以下字段：
- **分数范围、tier、status、quality**：用于检索时的过滤或权限控制，获取更精确的结果
- **评测字段**：支持 Eval 流程
- **观测性字段**：支持运行时监控
- **Citations 字段**：支持引用追溯

### 索引构建

索引构建阶段包括三个步骤：
1. **Embedding**：对 chunk 进行向量化，支持批量处理（batch size 可调，实践中使用 32）
2. **Index Manifest**：记录每次索引构建的发布信息，新增 index_manifest 表
3. **Build Log & Reporting**：记录构建过程，生成索引报告（包含 chunk 数量、构建时间等）

索引构建通过 Dagster 资产化管理，将索引清单和知识索引定义为资产，整条链路资产化。支持 dry-run 模式（不写入 embedding，只生成 index_build_report 和 index_manifest），方便验证流程。

真实索引构建需要大模型 API Key（如 text-embedding-3-small），会为每次构建分配 index_id 并关联 release_id，确保可追溯。

### Query 理解层

Query 理解层是 RAG 服务中非常关键的部分，在检索之前对用户查询进行预处理：

- **查询改写**：将口语化或模糊的表达标准化为精确的检索 query
- **查询路由**：通过分类逻辑将请求路由到不同代价的模型（简单事实走小模型，复杂推理走大模型）
- **HyDE 文档构建**：让 LLM 假想答案再做 embedding，提升垂直领域召回
- **多跳查询**：对需要多步推理的问题进行迭代检索

### 混合检索 + 精排

检索阶段采用混合检索模式，基于 pgvector（PostgreSQL）同时支持向量检索和全文检索（FTS）：

1. **向量检索**：将 Query 进行 embedding，与向量库中的数据匹配
2. **BM25 全文检索**：基于 PostgreSQL 的 tsvector 进行精确文本匹配
3. **RRF 融合**：两路并行执行后合并结果（类似 MapReduce），总体延迟取决于最长的并行任务
4. **Cross-Encoder Rerank**：对融合后的初排结果（top-50）进行精排，设置质量门禁
5. **元数据过滤**：在检索时根据权限或质量控制条件过滤结果

### 受约束生成

精排后的 top-k 证据进入生成阶段：

- **Context Pruning（剪枝）**：控制上下文数量，避免 token 预算超支
- **Citations 处理**：确保生成的答案带有引用来源
- **置信度判断**：对未知问题和知识库未覆盖问题进行识别，低置信度时触发 fallback
- **结构化输出**：答案包含 answer、citations、evidence_ids、confidence、release_id、data_release_id 等字段

### RAG API 服务

RAG API 的输入和输出构成完整的服务契约：

**输入**：product_line、actor_role 等字段

**输出契约**：
- answer：结构化答案
- citations：引用证据
- evidence_ids：证据标识
- confidence：置信度
- release_id：版本标识
- data_release_id：数据版本标识
- trace_id：追踪标识

当检索不到内容时，默认设为空值以避免大模型猜测，而非强行生成答案。

## 数据模型扩展

第八周在数据层新增了三张核心表：

| 表 | 用途 |
| :--- | :--- |
| **index_manifest** | 记录索引的发布信息，每次构建生成一条记录 |
| **index_build_log** | 记录索引构建过程的详细日志 |
| **rag_audit_log** | 记录 RAG 服务的审计信息，包括 trace_id、index_release_id、prompt_release_id 等 |

审计底座可以将遇到的 bad case 固化到存储中，通过 trace_id 还原问题细节，包括使用的 filter、命中的 evidence、分数以及对应的 release 信息。

## 健康检测

Health 检测用于确认 RAG API 服务是否正常运行，核心检查项：
- release_id 是否存在
- data_release_id 是否存在
- index_release_id 是否存在

这些字段的存在性贯穿了第八周的核心内容，缺少任何一个都说明服务状态异常。

## 契约测试

第八周共有 6 个契约测试，确保所有契约在实际运行前通过：

1. **请求 schema 合法性验证**：确保输入格式正确
2. **响应合法性检查（正常回答）**：验证正常情况下的输出格式
3. **响应合法性检查（无回答）**：验证无法回答时的输出格式
4. **缺少引用时回答失败**：确保没有引用时不会返回答案
5. **拒绝回答时必须提供原因且无证据支持**：确保 fallback 行为正确
6. **RRF 融合正确性**：验证 RRF 算法的计算结果，可手动对照公式验算

## RAG Answer 的两条路径

RAG 服务需要处理两条路径：

- **有答案路径**：检索到相关证据，生成结构化答案并附带 citations
- **无答案路径**：未检索到证据时，返回空答案并说明原因，不让大模型猜测

两条路径都需要满足输出契约的完整性要求。

## 评测与冒烟测试

上线前的评测覆盖多个维度：

- **查询改写测试**：验证原始查询的改写效果和路由功能
- **HyDE 文档构建测试**：观察假想答案的形态
- **RRF 融合测试**：验证两路检索结果的融合正确性
- **冒烟测试（Smoke Test）**：评估系统边界，生成评测报告记录各项指标
- **可解释性输出**：支持查看改写过程和路由决策的中间结果

## Dagster 资产管理

第八周的 RAG 资产通过 Dagster 进行管理，构建了多个资产包括索引清单和知识索引。通过 Dagster 将整条链路定义为资产图（Asset Graph），实现：

- 资产间依赖关系的可视化
- 增量构建和重建的自动化
- 构建状态的监控和告警

## 本周交付物总览

第八周的工程实践涵盖了从索引到服务的完整链路：

| 模块 | 交付内容 |
| :--- | :--- |
| **Query 理解** | Query Rewrite + HyDE、Adaptive RAG 路由（LangGraph） |
| **混合检索** | Dense + BM25 + RRF、Cohere + ColBERT + LLM Rerank、Multi-Hop 迭代检索 |
| **生成服务** | RAGAnswer JSON 契约、Context Pruning（Top-K + Token Budget）、Prompt Caching |
| **Prompt 管理** | Jinja2 模板 + Git 版本化、release_id 路由 |
| **评测** | LLM-as-Judge Faithfulness、Bad Case 库 + 4 类标签 |
| **监控与治理** | Drift 漂移监测（3 监控点告警）、Release Manifest（原子绑定 4 件套） |

整条链路的配置包括 pgvector、FTS、RRF 和结构化的 RAG API，为后续生产做好准备。RAG 可以作为一个独立课程深入学习，本周重点在于把关键知识点串联成完整的工程闭环。
