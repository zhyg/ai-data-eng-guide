# 3. 图增强检索

## 核心问题

Lesson 2 把图建好了，这一讲讲怎么用它做检索。图真正的价值是三种向量根本做不到的检索模式：子图扩展（Local）、社区检测（Global）、路径遍历（Multi-hop）。

真实场景：图建得挺漂亮，可检索代码还是「查相似 chunk」那一套，只不过多召回了几个图节点。这么用，图的钱全白花了。

关键判断：图检索的核心不是「查得更准」，是召回向量召不回的东西。

## 召回向量召不回的东西

两种检索目标根本不同：向量找「长得像答案」，图找「通过关系连到答案」。

| 维度 | 向量检索 | 图检索 |
| :--- | :--- | :--- |
| 依据 | 语义相似 | 结构关系 |
| 找什么 | 「长得像答案」的 chunk | 「通过关系链到答案」的实体 |
| 举例 | 「重置密码」→ 找操作步骤 | 「半年 P0 共性」→ 找一组关联实体 |
| 答案位置 | 单个 chunk 内 | 实体之间 |
| 定位 | 它的舒适区 | 向量的盲区 |

工程结论：两种并存，不是二选一。按题型路由到不同检索，继承 Week 8 的 intent routing。图 + 向量混合是标配，单一模式都不够用。

## 3 种核心检索模式

Local 聚焦、Global 归纳、Multi-hop 遍历，代价从低到高。

| 模式 | 做法 | 解决什么题 | 示例 | 查询代价 |
| :--- | :--- | :--- | :--- | :--- |
| LOCAL · 子图扩展 | 以一个实体为起点召回邻居 | 聚焦类问题 | 「客户 X 的所有工单和问题」 | 低，最常用 |
| GLOBAL · 社区归纳 | 社区检测 + Map-Reduce | 全局归纳类 | 「过去 6 个月主要故障类型」 | 高（需预计算），微软论文核心 |
| MULTI-HOP · 路径遍历 | 从一实体走 ≤ N 跳 | 关系遍历类 | 「A 公司的子公司的供应商」 | 中（限跳数），最容易爆炸 |

同一套图，三种问法要走三条完全不同的检索路。选错模式，图召回再全也答不对题。

## 模式选择标准：按题型路由，4 选 1

这个路由由「题型分类器」做，Week 8 学过的 intent routing 在这儿继续用。

| 题型 | 示例 | 检索模式 | 为什么 |
| :--- | :--- | :--- | :--- |
| 聚焦实体类 | 「客户 X 的所有工单」 | Local Search | 已知锚点 + 邻居扩展 |
| 全局归纳类 | 「P0 故障类型分布」 | Global Search | 需要全图聚合 |
| 关系遍历类 | 「A 公司收购了谁」 | Multi-Hop | 需要走结构关系 |
| 具体事实类 | 「重置密码步骤」 | 向量 RAG | 图用不上，别浪费 |
| 对比类 | 「V1 和 V2 的差别」 | Local + 向量混合 | 结构 + 内容都要 |

关键判断：注意最后两行——不是所有题都非得走图。好的 GraphRAG，一半功夫花在「什么时候别用图」上。

## Local Search：子图扩展

从锚点实体出发扩展 1-2 跳，限住 maxLevel 防图爆炸。实现要点：

1. **识别 query 里的锚点实体**：NER + Lesson 2 的实体对齐
2. **从锚点 BFS 扩展 max_hops 跳**：Neo4j 里用 `apoc.path.subgraphAll`，`maxLevel` 限死防图爆炸，别自己写遍历
3. **`relationshipFilter` 白名单**：只走业务相关关系，不让「任意边」污染子图
4. **通过 `source_chunk_id` 反查原文 chunks**：生成层既有结构又有证据
5. **「子图 + 原文」一起交给生成层**

降级设计：识别不出锚点（比如「如何重置密码」）就 `fallback="vector"`，降级走向量，用户无感。Local 对降级很友好，是最先该上线的模式。

## Global Search：社区检测 + Map-Reduce

微软论文的核心创新——把「看全图」拆成「看 N 个社区再合并」，复杂度 O(N²) 降到 O(N)：

Cluster 社区检测（Leiden）→ Summarize 社区摘要（LLM per cluster）→ Map 查询打到所有社区并行答 → Reduce 汇总社区答案（LLM 归纳）→ Output 全局归纳答案

关键判断：这一步的精髓是「预计算」。社区检测和摘要不是每次查询现算，是建完图批量算一次、入库存着。用户问全局类问题时，只做 Map（并行读各社区摘要）+ Reduce（LLM 汇总）。这就是 Global Search 建图贵但查询能扛的原因，重活提前干完了。2026 LazyGraphRAG 要优化的正是这块的成本。

### 社区检测的实现要点

- **igraph + Leiden**：工业界事实选择，比 NetworkX 的 Louvain 快 10 倍、更稳定，不会产生「断裂社区」
- **摘要是预计算产物**：建图后批量算并入库，不是每次查询现算。摘要结构统一为「topic + key facts + key entities」
- **保留 `source_chunks`**：Map 阶段可同时返回摘要和具体原文
- **社区检测要进 release manifest**：图变 → 社区可能变 → 摘要要重算，Week 14 治理的活
- **重跑时机**：建图后跑一次，每周或大批量入图时重跑
- **2026 提醒**：LazyGraphRAG 把「给每个社区都预生成摘要」这步的钱省了，延迟到查询时按需做

## DRIFT Search：2026 把 Local / Global 融合

DRIFT = Dynamic Reasoning and Inference with Flexible Traversal。

| 维度 | Local / Global 分开跑（2024） | DRIFT Search（2024 末起） |
| :--- | :--- | :--- |
| 起点 | Local 只从锚点，Global 只看社区 | Local 起点里就注入社区信息，起点更宽 |
| 覆盖 | 选错模式就漏答案 | 一次检索兼顾「聚焦细节 + 全局背景」 |
| 效果 | 两种各有盲区 | 召回的事实种类明显更多、答案更全 |

DRIFT 的思路：用户问一个聚焦问题时，光看锚点周围往往不够，它把「这个锚点属于哪个社区、社区的大背景是什么」一起带进检索起点，然后动态地在局部和全局之间来回走，相当于把 Local 的「细」和 Global 的「广」揉进了一次查询。

落地建议：新项目别再手写 Local / Global 两套路由再纠结怎么合并，直接用微软 GraphRAG 里的 DRIFT 模式起步，它已经把「该看局部还是全局」这个判断内化掉了。

## Multi-Hop 的 4 个坑

图最强的能力，也是最容易爆炸的能力。一道护栏都不能少。

| 坑 | 具体表现 | 后果 | 解法 |
| :--- | :--- | :--- | :--- |
| 无跳数限制 | 「找所有相关」无上限 | 召回 1000+ 节点 | max_hops ≤ 3，常用 2 |
| 关系不过滤 | 走所有边 | 噪声 + 语义偏离 | relationshipFilter 白名单 |
| 不打分 | BFS 平等对待 | 强弱关系混一起 | 按距离 + 边权重打分 |
| 不验证路径 | 「有路径就相关」 | 语义可能不连贯 | LLM 验证路径语义 |

反模式提醒：没限跳数的 multi-hop 查询在大图上跑，一口气能召回几千个节点，直接把 LLM 上下文撑爆、把这次请求的成本干到平时的几十倍。Multi-hop 是图最性感的能力，不上护栏就是个吞钱吞算力的黑洞。

### 受控 Multi-Hop 的四道护栏

1. **`max_hops > 3` 直接抛错**：4+ 跳几乎没法解释，先把图爆炸堵死
2. **关系类型白名单**：Cypher 里写成 `-[r:TYPE_A|TYPE_B*1..max_hops]->`，只走业务关系
3. **路径打分**：沿路径累乘每条边的 `confidence`，低于阈值的路径直接丢，强关系优先，把「图的稳定边」和「LLM 抽的边」区分开
4. **LLM 验证路径连贯性**：路径 score 高不代表逻辑通，让 LLM 看一眼「机械正确但语义无关」的路径

另外结果要 `ORDER BY score DESC, hops ASC` 并 `LIMIT` 截断，避免路径过多。

2026 备选：HippoRAG 2 用 personalized PageRank 一步做多跳，省掉迭代遍历，适合关系很密的图。

## Industry Signals（2026）

Local + Global + 向量混合是共识，2026 又多了 DRIFT 和单步多跳。

| 方案 | 能力 | 2026 建议 |
| :--- | :--- | :--- |
| Microsoft GraphRAG (DRIFT) | Local / Global / DRIFT 融合 | 新项目直接用 DRIFT 起步 |
| Neo4j + APOC | subgraphAll / Dijkstra / 社区检测 | 开箱即用，别手写图算法 |
| HippoRAG 2 | personalized PageRank 单步多跳 | 关系密、多跳深的图值得一试 |
| LangChain GraphCypherQAChain | 自然语言转 Cypher | 复杂关系探索，让 LLM 写查询 |
| LlamaIndex KG Retriever | 图 + 向量混合默认 | 上手成本低，快速验证 |

选型一句话：存储和图算法交给 Neo4j + APOC，检索范式跟微软 GraphRAG 的 DRIFT 走，真遇到深多跳、关系密的图再评估 HippoRAG 2。你要写的只有「题型分类器」和「prompt 模板」这两块业务胶水。

## Recap

- 图检索的工程价值是召回向量召不回的东西，生产里从来不是图取代向量，是两种并存按题型路由。
- Local 解聚焦题、Global 解归纳题、Multi-hop 解关系遍历题，代价从低到高。
- Global Search 的精髓是预计算：社区检测和摘要建完图批量算一次入库，查询时只做 Map-Reduce。
- 2026 用 DRIFT 把 Local / Global 融成一次检索，别再手写两套路由。
- Multi-hop 必须上四道护栏：限跳数、关系白名单、路径打分、LLM 验证连贯性。
