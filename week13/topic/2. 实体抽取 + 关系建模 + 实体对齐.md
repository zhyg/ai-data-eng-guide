# 2. 实体抽取 + 关系建模 + 实体对齐

## 核心问题

上一讲确认了「该上图」，这一讲讲怎么从 Week 7 的 chunks 抽出一张真能用的图。图建错，下游再好也救不回来。

真实场景：图省事，直接拿 LLM 跑了一遍所有 chunk，让它「自由抽实体和关系」。出来的结果是 8 种「产品」类型、12 种「组织」类型、同一家公司在图里有 5 个名字、关系动词五花八门。这种图的下游社区检测、路径遍历、子图扩展全被噪声击穿，基本等于废了。

关键判断：90% 的 GraphRAG 失败根本不在图算法，就死在构建这一步。

## Schema First, Extraction Second

图构建是工程问题，不是「让 LLM 抽一下」。没定 schema 就抽，LLM 自由发挥出来的图类型乱、动词乱、粒度乱，上面所有下游算法都会被噪声击穿。工程化的做法只有一条：先定 schema（哪些节点类型、哪些关系类型），再用「LLM + 规则」约束着抽。这是 GraphRAG 工程化的第一性原理。

| 先定什么 | 规模 | 具体内容 | 硬规则 | 工程价值 |
| :--- | :--- | :--- | :--- | :--- |
| Node Types | 5-20 种 | Person / Org / Product / Issue | 类型必须有明确定义，不许 LLM 自创类型 | 可治理 |
| Edge Types | 10-30 种 | works_at / produced_by / depends_on | 动词标准化，禁止 `related_to` 这种含糊 | 可推理 |
| Properties | 每类节点 / 边的属性 | name / aliases / domain / source | 一致命名规范，业务必含字段（如时间） | 可查询 |

## 图 schema 的关键字段

强类型 + 版本号 + 别名 + 血缘，每一个字段都是为了下游可治理。

- **`version` 字段**：schema 也有版本，Week 14 治理会锁它
- **`type` + `required`**：强 schema 约束，堵死 LLM 自由发挥
- **`aliases: list[string]`**：显式支持别名（Acme Inc / Acme Corp / Acme），是实体对齐的地基
- **枚举约束**：`tier: [free, paid, vip]`、`severity: [P0, P1, P2, P3]` 这类字段用 enum 焊死取值范围
- **边上的 `source_chunk_id`**：每条边都能反查「来自哪个 chunk」，Week 7 证据链贯穿到图
- **边上的 `confidence`**：关系置信度，后面路径打分要用
- **关系名一律大写动词**：`SUBMITTED_BY`、`RELATED_TO`，Neo4j / Cypher 的习惯，跨工具兼容

## 3 种实体抽取策略

抽取是最大成本来源，按精度 × 成本权衡。

| 策略 | 具体做法 | 精度 | 成本 /1k chunks | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| 纯规则 | NER 模型 + 正则 + 词典 | 中 70-80% | < $1 | 已知实体 / 简单场景 |
| 纯 LLM | 让 LLM 自由抽 | 高 85-92% | $50-200 | 复杂关系 / 灵活领域 |
| LLM + Schema 约束 | 强制按 schema 输出 | 高 88-94% | $30-100 | 生产推荐默认 |
| 混合（规则 + LLM 兜底） | 规则先扫，复杂 LLM 救 | 高 85-93% | $10-40 | 大规模 + 成本敏感 |

默认配方：LLM + Schema 约束做主链路，规则给高频实体（客户名、工单号）加速，后面再挂一道 LLM 校验。这套下来精度稳在 90% 上下，成本压在每千 chunk 几十美金。配 LazyGraphRAG 那套延迟抽取还能再降一档。

## 抽取实现要点

用类型系统焊死「不许自创」：

- **`Literal["Customer", "Ticket", "Product", "Issue"]`**：LLM 在解码层就只能输出 schema 内的类型，绝不可能自创
- **`response_format` 结构化输出**：配合 pydantic 模型，输出 100% 合 schema
- **关系上的 `evidence_text` 必填**：每条关系带原文片段，后期能人工 review + 错误溯源
- **Prompt 里硬写约束**：`Do NOT invent types` / `If ambiguous, skip`。宁可漏抽不要错抽，错抽进图会污染下游所有推理
- **换模型等价写法**：Anthropic 侧用 `client.messages.parse(...)` 或 `output_config={"format":{"type":"json_schema"}}`，课程主线用 claude-sonnet-4-6 更省

## 实体对齐：最被低估的难点

抽完你会发现，一个「Acme 公司」在文档里能有 5 种写法：「Acme Inc」/「Acme Corp」/「Acme」/「艾克美」/「ACM」。不对齐，同一个实体在图里就是 5 个节点，关系全被切碎，图基本废了。实体对齐（Entity Resolution）比抽取本身难 3 倍。

| 对齐问题 | 具体表现 | 难度 | 工程解法 |
| :--- | :--- | :--- | :--- |
| 命名变体 | 「Acme Inc」/「Acme Corp」/「Acme」 | 中 | 别名词典 + 字符相似度 |
| 缩写 / 翻译 | 「OpenAI」/「OAI」/「开放 AI」 | 高 | LLM 判断 + 别名集合 |
| 类型冲突 | 同名不同类（产品名 vs 公司名） | 高 | 上下文消歧 + 人工 review |
| 时间漂移 | 「Twitter」→「X」（品牌改名） | 极高 | 时序图：带时间的别名链 |

这几类没有银弹，必须组合「别名词典 + 字符相似 + Embedding + LLM + 人工」一起上。

## 实体对齐的 4 阶段分层

让 95% 免费完成，只有 5% 走 LLM。大规模图构建必须这么分层，不然对齐成本比抽取还爆。

| 阶段 | 手段 | 处理什么 | 成本 |
| :--- | :--- | :--- | :--- |
| 阶段 1 | 别名词典精确匹配 | 70% 高频实体 | 几乎零成本 |
| 阶段 2 | 字符相似度（rapidfuzz） | 拼写 / 大小写 / 标点差异 | 快到可忽略 |
| 阶段 3 | Embedding 相似度 | 同义词 / 翻译变体 | 中等成本 |
| 阶段 4 | LLM 兜底判断 | 上下文模糊的 | 贵但量小 |

要点：
- 候选集先按同类型过滤（`e.type == new.type`），跨类型不比
- 字符相似度设两道线：粗筛 > 85 进候选，最高分 > 92 才自动合并
- Embedding 余弦相似度 > 0.92 才合并
- 四阶段都不命中就新建节点，不强行合并

## 2026 新解法：用时序图根治实体漂移

「Twitter→X」这种品牌改名，本质是「事实有生命周期」，静态图存不下，时序图能。

| 能力 | 静态知识图（传统） | 时序知识图（Graphiti / Zep 2026） |
| :--- | :--- | :--- |
| 边的时间 | 无，只有「当前事实」 | 每条边带 valid_from / valid_to / invalid_at |
| 「改名前叫啥」 | 答不了，旧事实被覆盖 | 原生支持，事实有生命周期，历史可查 |
| 生产指标 | —— | 时序推理 +18.5%（LongMemEval）· P95 300ms |

Zep 那篇 Graphiti 论文把「双时序」做成了图的一等公民：一条边不光记「A 拥有 B」，还记「这个事实从什么时候到什么时候是真的」。于是「Twitter 2023 年改名 X」不再是让人头疼的对齐冲突，而是别名链上一个带时间戳的正常事件，甚至能回答「改名前它叫什么」。

落地判断：如果领域实体会随时间变（公司改名、并购、人员变动、合同版本），别再用静态图硬扛对齐，直接上 Graphiti 这类时序图，把「漂移」从 bug 变成 feature。

## Industry Signals（2026）

从 0 起步别自己造轮子，抽取 + 对齐 + 存储都有成熟栈。

| 工具 | 定位 | 2026 建议 |
| :--- | :--- | :--- |
| Microsoft GraphRAG / LazyGraphRAG | 端到端框架 | 从 0 起步 + 想省成本，首选 Lazy 版 |
| Neo4j neo4j-graphrag (GA) | 官方 Python 抽取 + 存储 | 生产级、可视化（自建集群约 $300+/月） |
| LangChain LLMGraphTransformer | 把「抽实体关系」做成组件 | 配 schema 约束，快速 PoC |
| Graphiti / Zep | 时序知识图 | 实体随时间漂移的领域必看 |
| Diffbot Knowledge Graph | 商业预构建图 | 金融等不想自建的团队 |

选型路径：PoC 用 Microsoft GraphRAG 快速验证 → 生产存储上 Neo4j（neo4j-graphrag 包已 GA，别自己写 Cypher 胶水）→ 实体会随时间变的领域，加 Graphiti 那套时序层。

## Recap

- schema-first 是图构建的第一性原理：先定节点类型、关系类型、属性，再约束着抽。
- 生产默认策略是 LLM + Schema 约束，用 Literal 类型在解码层焊死「不许自创」。
- 每条关系必带 evidence_text 和 source_chunk_id，宁可漏抽不要错抽。
- 实体对齐比抽取难 3 倍，用 4 阶段分层让 95% 免费完成。
- 实体会随时间漂移的领域，上时序图比静态图硬扛对齐更靠谱。
