# 4. 图增强生成

## 核心问题

Lesson 3 把图数据召回了，但 LLM 不会自然消费「节点 + 边」这种结构。这一讲讲清楚怎么把图翻译成 LLM 吃得香的文本。

真实场景：Global Search 召回质量明明很高，最终答案还是稀烂。问题出在最后一公里——工程师图省事，直接把召回的图 JSON（一堆 node、edge 的字典）原封不动塞进了 prompt。LLM 是在文本上训练的，喂它「A 收购了 B」这句话它秒懂，喂它 `{"src":"A","edge":"acquire","tgt":"B"}` 它就懵。

关键判断：图增强生成的核心工程问题不是图算法，是「图 → 文本」的翻译质量。

## LLM 不会读图：3 种序列化策略

| 策略 | 做法 | 配合哪种检索 | 优点 | 局限 |
| :--- | :--- | :--- | :--- | :--- |
| 路径 → 文本 | 多跳路径写成自然语言，「A 收购 B；B 拥有 X」 | Multi-Hop | LLM 友好 | 长路径冗长 |
| 子图 → 表格 | 子图变 markdown 表，行是节点 / 关系 / 邻居 | Local Search | 结构清晰 | 吃上下文 |
| 社区 → 摘要 | 预计算的社区摘要，「主题 + 关键事实 + 实体」 | Global Search | 信息密度高 | 丢局部细节 |

关键判断：能用文本就别用 JSON。LLM 在文本上训练，文本永远比结构化 JSON 好懂。实测里同一个子图，用 markdown 表喂比用 JSON 喂，答案准确率能差 30% 上下。

## 3 种序列化的实现要点

- **`serialize_path`**：把 `(src)-[rel]-(tgt)` 变成「X 动词 Y」的句子，关系名下划线转空格、转小写，多段用句号拼接，出来就是「Acme acquired Beta. Beta produces X.」这样 LLM 立刻能懂的文本
- **`serialize_subgraph`**：输出 markdown 表格，表头固定为 Entity / Type / Relation / Connected To，前面加一行 `# Subgraph on: {anchor}` 说明锚点。GPT / Claude 对 table 解读非常稳
- **`serialize_community`**：预计算摘要模板化，输出社区 ID、实体数、Topic、Key Facts、来源文档数，token 效率最高
- **三种都保留 chunk_id / source**：Week 7 证据链贯穿到图增强生成

## 3 套 prompt 模板，不能一套通用

Local 要「基于具体实体说」，Global 要「跨社区归纳」，写混了召回再好也白搭。模板用 Jinja2 管理，配合 Week 8 的 Prompt as Code，改模板就能改图增强行为，还能版本化、回滚。

| 模板 | 上下文内容 | 核心 Rules |
| :--- | :--- | :--- |
| graph_local | 以锚点为中心的序列化子图 + 证据 chunks | 只用子图内实体 + 证据 chunk；不要发明未展示的关系；用 [chunk_id] 引用 |
| graph_global | N 个相关社区的摘要 | 跨社区综合出全局规律；识别共性 / 异常；引用社区（「Community 3 显示...」） |
| graph_multihop | 按相关性排序的关系路径 | 清晰追踪关系链「A → B → C」；每步必须有路径支撑；无路径就直说答不了 |

要点：
- `graph_local` 强调「只用子图 + 不要发明关系」，防 LLM 在熟悉领域里编造
- `graph_global` 强调「跨社区综合规律」，这正是 Global 的目标
- `graph_multihop` 要求把路径用 → 链表示，让答案可被审计
- 3 个模板都强制 citation，Week 7-8 证据链在图层延续

## 图增强的 evidence：做成「双链」

图增强后必须保留 Week 8 的 evidence 契约，但要从「只有 chunk」扩展到「chunk + 图」。

| 契约对象 | 关键字段 | 作用 |
| :--- | :--- | :--- |
| `ChunkEvidence` | chunk_id / doc_id / page_no / text | Week 8 原样保留，客户端代码零改动 |
| `GraphEvidence` | type（subgraph / path / community）、anchor_entity、path_text、community_summary、source_chunks | 图增强新增，前端能可视化图证据：渲染子图、显示路径、展示社区 |
| `RAGResponse` | answer、chunk_evidences、graph_evidences、retrieval_mode、confidence、trace_id、release_id | 统一响应，`retrieval_mode` 取值 vector / local_graph / global_graph / multi_hop / hybrid |

要点：
- `GraphEvidence` 里也保留 `source_chunks`，图证据能反查原文，形成双层证据链
- `retrieval_mode` 显式暴露，审计和评测才知道这次用图还是向量，Week 11 能分模式统计
- 这个字段是下一节 A/B 的地基，没有它永远算不清「图到底在哪类题上赢了」

## 完整流水线：5 步走完，90% 代码复用

Route 题型分类（选检索模式）→ Retrieve 图检索（Lesson 3）→ Serialize 图 → 文本（Path / Table / Summary）→ Generate 受约束生成（Week 8 模板）→ Cite 混合 evidence（chunk + graph 双链）

关键判断：这五步里只有 Serialize 和 Cite 里的 GraphEvidence 是图增强真正新增的。Route 是 Week 8 的 intent routing，Retrieve 是 Lesson 3，Generate 是 Week 8 的受约束生成模板。图增强不是另起炉灶，是在已有的 RAG 流水线上插两块，90% 的代码原样复用。

## Anti-Patterns：图增强生成的 5 个反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 直接 JSON 喂 | 图节点 dict 丢 prompt | LLM 解读差 | 序列化成 path / table / summary |
| 一套模板通用 | Local / Global 同一 prompt | 归纳变枚举、聚焦变发散 | 3 套模板 |
| 丢 chunk 证据 | 只给图不给原文 | 客户问「凭证」答不上 | source_chunks 必带 |
| mode 不暴露 | 图和向量结果混着 | 评测无法分模式 | retrieval_mode 必填 |
| 路径太长 | multi-hop 序列化 7+ 跳 | LLM 失焦 | max_hops ≤ 3 |

第三条「丢 chunk 证据」要特别点一下：图增强很容易让人只顾着炫图关系，把原文引用丢了。图给的是「结构 / 线索」，原文给的是「证据」，在合规和信任上证据永远比线索重要，双链一个都不能少。

## Industry Signals（2026）

这一层是纯工程活，各家最佳实践高度一致。

| 来源 | 做法 | 启示 |
| :--- | :--- | :--- |
| Microsoft GraphRAG | Local prompt + Global Map-Reduce | 两套模板是官方范式，直接抄 |
| Anthropic Cookbook | 「path → 自然语言」最佳实践 | 关系写成句子，LLM 才真懂 |
| LangChain GraphRetriever | 检索 → 序列化 → 生成链式 API | 开发者只关心模板 |
| LlamaIndex KGRetriever | 默认 chunk + graph 混合 evidence | 前端同时渲染原文和图，信任高 |

这一节没什么高深算法，全是手艺——图怎么翻译成文本、模板怎么写、证据怎么带。但这些手艺决定了前面辛辛苦苦建的图、调的检索最后能不能变成一个好答案，是最不该省功夫的地方。

## Recap

- LLM 不会读图，必须先把图翻译成文本；能用文本就别用 JSON。
- 3 种序列化对应 3 种检索模式：路径写成句子、子图变 markdown 表、社区用预计算摘要。
- Local / Global / Multi-hop 各写一份 prompt 模板，3 个模板都强制 citation。
- evidence 从「只有 chunk」扩展成「chunk + graph」双链，`retrieval_mode` 必填，这是 A/B 的地基。
- 完整流水线里只有 Serialize 和 GraphEvidence 是新增的，其余 90% 复用 Week 7-8。
