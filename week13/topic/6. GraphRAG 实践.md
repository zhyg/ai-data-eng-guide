# 6. GraphRAG 实践

## 核心目标

把前 5 节落地成可运行的代码：基于 Week 7 的知识块生成有版本、有证据的关系图，接入 Week 8 的 RAG 服务，最后用 Week 11 的评测思路决定哪些题型适合 GraphRAG。

核心思想：GraphRAG 并不是万能的。重置密码、查制度、查字段这类简单问题仍然走向量 + 全文检索，关系题、跨文档归纳题和多跳题才是图的主场。

## 整体架构

最上游的数据已经处理成标准化的证据资产，Week 13 在这些资产上做派生，继承数据的版本、权限范围和引用能力：

Week 7 证据 chunks → 定 schema → 抽取 → 实体对齐 → 社区聚合 → 以 graph_release 为单位写入 PostgreSQL → 查询时分类路由（简单题走 hybrid search，关系题进 graph 检索）→ 序列化成文本 → RAG 生成带引用的答案 → 按题型分层 A/B

生成受系统元数据控制，确保模型不会随意生成内容。最终按事实性、局部、全局、多跳四类分别做 A/B，而不是只看一个总体平均分。

## 数据层

`data/` 目录放 Week 7 证据资产的可复现实验切片。每行数据携带 chunk 的身份信息：`chunk_id`、`event_id`、`data_release_id`、`product_name`、`visibility_scope` 等字段，把上游证据块与已审核的模型结合起来。

## 图构建流水线

代码集中在 `pipelines/graph/` 下。

### schema.yaml / schema.py

`schema.yaml` 规定图的边界和结构形状，是图的「业务宪法」：允许的实体类型白名单、边类型及其端点连接方式、质量阈值。这是 schema-first 实体抽取的先验规则，所有内容都要严格定义，避免大模型随意创造实体类型和关系动词。

`schema.py` 引用 `schema.yaml` 的数据结构，执行加载和完整性校验，尽早发现配置错误，防止系统启动时因不存在的实体类型或端点而失败，也阻止脏数据进入存储。

生产系统需要多层防线保障数据质量：先校验 schema 本身，再校验抽取结果，最后是持久化约束。

### models.py

定义图流水线的中间语言，描述对象生命周期：

| 对象 | 含义 |
| :--- | :--- |
| `source_chunk` | 上游事实，输入对象 |
| `entity_mention` / `relation_mention` | 抽取出的候选集 |
| `alignment_decision` | 记录合并或隔离的原因 |
| `graph_entity` / `graph_relation` | 图中的节点和边，构成可查询、可审查、可审计的发布候选 |
| `GraphBuildResult` | 整个构建过程的报告 |

### extract.py

用协议隔离抽取引擎：`Extractor` 是可替换的协议，默认实现也在其中。无论用大模型、规则引擎还是第三方 GraphRAG 框架，都实现同一个接口层。这样更换抽取器不会影响整个检索流程。抽取本身受 schema 约束，并带置信度防御。

### alignment.py

解决同一个实体多种写法的问题，做规范化并生成稳定 ID：

1. NFKC 归一化
2. casefold + 标点清理
3. 按 schema aliases 精确匹配自动合并
4. 高分 fuzzy 匹配自动合并

阈值设计：相似度高于 0.96 才自动合并；唯一候选落在 0.88 附近时判定为歧义，选择隔离处理，避免把两个不同的客户或产品错误合并。这就是课程里讲的同名不同义、同义不同名的实体对齐问题。

### community.py

通过节点和边生成可供 Global Search 使用的社区。课程实现采用 BFS 确定性连通分量方法，按成员排序生成稳定摘要。好处是没有外部依赖、结果可重复验证。

生产升级时可以替换为 LLM 摘要并做版本化社区，但输入仍需治理后的实体和边，输出要保留 `community_id`、`member_ids`、`event_ids` 及 `graph_release_id`，确保证据和版本不丢失。

### build.py

图构建的总编排入口 `build_graph`，先做输入身份校验，再依次串起抽取、实体对齐、社区摘要，最后交给 store 落库。

### store.py（构建侧）

负责事务性写入，所有步骤在一个事务中完成。任何一步失败，整个 release 都不会变成 active。

幂等设计：同一个 `release_id` + `index_release_id` 可以安全重跑；内容或上游 `index_release_id` 改变时，旧的 `graph_release_id` 无法复用。

## 数据模型扩展

`infra/` 下的 SQL 脚本定义 Week 13 新增的表结构。

| 表 / 概念 | 作用 |
| :--- | :--- |
| `graph_release` | 所有图资产的父身份，冻结引用的文本和定位信息，节点 / 边 / 社区都以外键挂在它下面 |
| 实体节点表 | 图的主实体 |
| 实体别名表 | 支撑实体对齐 |
| 关系边表 | 图的边 |
| 社区表 + 社区成员表 | Global Search 的预计算产物 |
| 隔离记录表 | 记录对齐时判定歧义、拒绝合并的实体 |

## Dagster 编排

图资产编排进 Dagster，与前几周流程一脉相承。Dagster 负责编排并观察构图报告，`graph_release` 也发布到这里。

流程：先确定 `release_id`、`graph_release_id` 和 `source_path`，再执行 build。元数据记录 chunk / entity 数量、社区数和稳定状态，方便在 Dagster UI 中查看运行结果。本周物化两个资产：`graph_release` 和 `graph_build`。

## 服务层

代码集中在 `services/graph/` 下。

### classifier.py

所有查询的第一道处理逻辑，是 graph route 的准入阀门，决定问题该走哪条链路。查询模式包括 `global`、`multi-hop`、`local`、`hybrid`。

分类器通过确定性规则保证可解释性：全局词命中走 global，多跳关系词命中走多跳，局部关系走 local。例如「全局共性」类问题进 graph global，「关系链 / 传播影响路径」类问题按具体情况路由。

### models.py

构建时和运行时分别描述怎么造图、图怎么用。三个主要结构：路由对象、`graph_path_record`、最终结果。构建侧和运行侧的对象可能不同，这是概念性的区分。

### store.py（运行时）

构建侧的 store 负责写入，运行时的 store 负责受控读取。`GraphStore` 把 `find_entities`、`traverse`、`list_communities` 等能力抽象成协议，先提供内存测试适配器，再提供实际适配器。

目前用 PostgreSQL 作为存储。将来要换成 Neo4j，只需替换适配器实现，不影响上层代码。

### retrieval

统一检索入口，把所有边界条件囊括进来，按各自的检索逻辑执行。

### serialize

检索出的内容需要转换为大模型可读的授权文本：对路径和数据做序列化形成结构化信息，对图查询结果做元素过滤和优化，只序列化选中的路径和社区，并过滤出通过校验的 evidence id 集合。

## RAG API 集成

`RAGResponse` 模型新增 `graph_release`、`GraphRetrievalDebug` 等字段。`rag.py` 里通过 service run API 做路由处理，包含 HTTP 入口和引用构造。生成链路从答案生成入口开始，经过置信度检查、prompt 加载，最终完成输出。

## 评测与测试

### A/B 评测

`evals/` 下的 A/B 脚本负责样本读取和分类比较：对 focal / global / multihop / factual 四类查询类型分别统计，而不是计算一个总的平均分。

### 契约测试

`tests/` 下的 contract 测试覆盖本周全套约束，共 17 项，包括表结构、schema 校验、路由行为、序列化输出契约等。

## 健康检测与演示

实验流程：

1. 检查环境变量与服务是否就绪
2. 执行 Week 13 增量迁移，为现有 PostgreSQL 存储卷添加 GraphRAG 相关表
3. 导入模拟图数据，确认表创建成功
4. 检查输入 JSON 的结构化信息：`track_id`、`event_id`、`document_id`、质量门禁等字段
5. 先用 dry-run 模式验证实体、边、社区、隔离记录，不写库
6. 加上 `release_id`、`index_release_id` 参数持久化到 PostgreSQL
7. 查询 graph list 确认多个 release 版本共存且状态正确，再分别查实体节点、关系边、社区聚合信息

验证查询：

| 验证场景 | 查询 | 预期行为 |
| :--- | :--- | :--- |
| 多跳推理 | 某产品的 SSO 登录问题及其症状和解决方案的关系链 | 直连 PostgreSQL 找到种子实体，执行三跳推理，通过 event_id 获取证据，路由边界正确 |
| 全局归纳 | 过去半年故障的所有共性 | 路由类型判定为 global，返回社区摘要或聚合图 |
| 简单事实 | 密码重置 | 路由到 hybrid 查询 |

安全演示还包括降级与「发布不可发布内容」的拒绝：用未授权的 release_id 查询会失败，用已存在的 release 重跑则验证幂等性，不需要重新构建新的图 ID。

## Recap

- 图是 Week 7 证据资产的派生层，以 graph_release 为单位原子发布，继承版本、权限和引用能力。
- schema.yaml 是图的业务宪法，加载时就做完整性校验，多层防线阻止脏数据进存储。
- 实体对齐用确定性阈值：高分自动合并、歧义区间隔离，宁可隔离不错合。
- 抽取引擎和图存储都用协议隔离，换抽取器或从 PostgreSQL 换到 Neo4j 都不影响上层。
- 查询侧先分类再路由，简单题走 hybrid，关系 / 归纳 / 多跳题走图，最后按四类题型分层做 A/B。
