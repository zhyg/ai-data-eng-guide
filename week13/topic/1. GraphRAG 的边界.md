# 1. GraphRAG 的边界

## 核心问题

Week 8 已经把「混合检索 + 重排 + 受约束生成」做完，向量 RAG 能「答得对」。但有一类问题它一定翻车：「过去半年，所有 P0 故障的共性是什么？」答案不在某几个 chunk 里，它散在 100 多份文档的关系里。这一节先解决一个比技术更重要的问题：边界——什么时候该升级到 GraphRAG，什么时候上图纯属给自己找麻烦。

真实场景：客服知识库上线向量 RAG 三个月，FAQ、故障排查答得都挺漂亮。直到业务方问「过去半年所有 P0 故障的共性是什么」，系统返回了 3 条「最相似」的工单，牛头不对马嘴。这不是模型笨，是范式不匹配。

关键判断：「答得不准就上 GraphRAG」是最常见的一笔工程债。

## GraphRAG 不是「更好的 RAG」

向量检索有一个藏在水面下的工程假设：答案藏在「语义相近的某几个 chunk」里。这个假设在 70% 的客服 / 知识问答场景成立，这也是 RAG 这套范式能跑通、能落地的原因。搞错这个定位，你要么该上不上、要么不该上瞎上。

| 维度 | 向量的主场 | 向量的死角 | GraphRAG 的起点 |
| :--- | :--- | :--- | :--- |
| 典型问法 | 「怎么重置密码」「什么是 SLA」 | 「半年 P0 故障的共性」「列出所有提到 X 的决策」「A 收购 B，B 的母公司在做啥」 | 把「关系」显式建成图 |
| 答案位置 | 就在 1-2 个 chunk | 在 chunk 之间的关系 | 检索能跨越 chunk 边界 |
| 语义相似 | = 找得到 | = 找不到 | 生成能在全局结构上归纳 |
| 占比 | 这类占大多数 | 少数但高价值 | 不是替代，是补位 |

## 向量 RAG 几乎一定失败的 4 类题型

它们有个共同点：答案的「完整性」依赖关系 / 时间 / 多源，而不是局部语义相似。

| 题型 | 具体问法 | 为什么向量必失败 | GraphRAG 怎么解 |
| :--- | :--- | :--- | :--- |
| 全局归纳 | 「过去 6 个月主要故障类型」 | 答案不在某几个 chunk，散在 100+ 文档 | 社区检测 + 主题聚合 |
| 关系遍历 | 「A 公司的子公司的供应商有哪些」 | 多跳关系向量编码不了 | 图路径遍历 |
| 交叉验证 | 「X 在合同 / 邮件 / 工单里各怎么描述」 | 同一实体跨文档语义不一致 | 实体对齐 + 多源聚合 |
| 时间序列 | 「产品 V1→V2→V3 的演进」 | 时序关系向量会丢 | 时间属性的关系边 |

关键判断：这 4 类题型一眼就能认出来——问题里带「所有 / 共性 / 分布 / 演进 / 之间的关系」这类词，基本就是向量的死角。先把业务的历史问题日志拉出来，数一数这 4 类占多少，这个比例决定该不该上图。

## 向量 RAG 的主场：这些场景千万别上图

上图 = 给自己加 3-10 倍成本，还引入一堆噪声。

| 场景类型 | 典型问法 | 为什么别上图 |
| :--- | :--- | :--- |
| FAQ / 操作类 | 「怎么重置密码」「忘了用户名怎么办」 | 答案就在 1-2 个 chunk，向量召回足够，上图 = 过度工程 |
| 定义 / 概念类 | 「什么是 SLA」「年化收益率怎么算」 | 单点知识查询，向量天然擅长，加图反而引入噪声 |
| 短对话类 | 客服对话 / 闲聊 | 上下文短、关系简单，向量 + Tool 足够，图在这儿一点用没有 |

反模式提醒：看了篇 GraphRAG 论文就全量上图，结果 80% 的查询是 FAQ 类，图一点没帮上忙，还把查询延迟从毫秒级拖到秒级、成本翻了几倍。不该上图的场景硬上，比不上图更糟。

## GraphRAG 的成本账（2024 版）

每一项都比向量贵 3-10 倍，这是过去两年把所有人吓退的原因。

| 成本类别 | 主要开销 | 相对向量 | 2024 典型量级 |
| :--- | :--- | :--- | :--- |
| 构建（一次性） | LLM 逐 chunk 抽实体 + 关系 | 5-10x | 每 1k chunk 约 $50-200 |
| 存储（持续） | 图 DB + 索引 + 元数据 | 2-3x | 同等数据存储翻倍 |
| 更新（增量） | 增量抽取 + 图结构变更 | 5-10x | 每次 update 触发图重算 |
| 查询（每次） | 图遍历 + LLM 二次推理 | 3-5x | 每查询 +1-3s 延迟 |

2024 年，微软 GraphRAG 官方 demo 里给一个数据集建一次全量索引要 $33,000。这就是为什么当年「要不要上 GraphRAG」是个让 CTO 肉疼的决定。

## 2026 的成本悬崖：LazyGraphRAG

微软 2024.11 放出的 LazyGraphRAG，是重新决定「要不要上图」的关键变量。

| 方案 | 索引成本 | 全局查询成本 | 质量 |
| :--- | :--- | :--- | :--- |
| Full GraphRAG (2024) | 基准 100%（$33k 那套） | 高（每次全图 Map-Reduce） | 高 |
| LazyGraphRAG (2024.11) | ≈ 向量（每千 chunk < $1）· full 的 0.1% | 比 Global Search 低 700 倍 | 局部题追平、全局题相当 |
| 纯向量 RAG | 最低 | 最低 | 归纳 / 多跳题几乎为 0 |

LazyGraphRAG 的思路：别在建图时就把 LLM 的钱全烧掉，把重活推迟到查询时按需做。建图只用便宜的 NLP 抽名词短语 + 社区结构，LLM 留到用户真问了才上。业内那句名言就是这么来的——「$33,000 → $33，18 个月」。

落地判断：2026 年再拿 2024 那套「贵 5-10 倍」的成本账吓自己已经过时了。先上 LazyGraphRAG 试水，它索引跟向量一样便宜，几乎没有理由不试。「要不要上图」从一道成本难题，变成了一道「值不值得多花那点查询钱」的小题。

## GraphRAG 是「派生数据资产」

第二大坑：另搭一套抽取流水线、另选一个图库、另起一个服务。结果图跟原有数据资产两张皮，契约、版本、血缘、评测全断了。

正确做法：把图建成 Week 6 数据工厂的下游派生资产——Source: `silver.chunks` → derived: `entity_node` + `relation_edge`。

| 继承项 | 具体内容 | 来源 |
| :--- | :--- | :--- |
| 契约继承 | 图 schema 也进契约，强类型 + 版本化 | Week 2 |
| 血缘继承 | 每个实体带 source_chunk_id，可反查「来自哪个文档」 | Week 7 证据链 + OpenLineage |
| 编排继承 | 图是 Dagster 资产，上游变图自动跟随，增量 / 回填 / SLO 全免费 | Week 6 |
| 评测继承 | 图增强能进评测，按题型分层打分，不是孤岛项目 | Week 11 |

### 做成 Dagster 派生资产的代码要点

- `@asset` 一加，实体抽取就成为数据工厂的一等公民，编排、回填、血缘全自动
- `ins=chunks` 显式声明上游 silver 资产，上游一变，图自动感知要重算
- `FreshnessPolicy` 让图也有 SLO，规定时间内必须刷新，跟其他资产一个待遇
- 抽取时注入 `source_chunk_id` / `source_doc_id`，每个实体都能反查来自哪个文档
- `relation_edge` / `community` / `topic_summary` 同理，全是数据资产

## 在数据架构里的位置

图只是 silver chunks 的下游，上游变、图自动跟随，向量索引和图同步演进：

Bronze 原始文档（Week 7）→ Silver Chunk + 证据（Week 7）→ Graph 图层派生（entity + edge）→ Retrieve 图增强检索（并行向量）→ Generate 图增强生成（Week 8）

关键判断：图不是链路的「另一条腿」，是 silver 那条腿上长出来的派生层。这样一来，前 12 周攒下的所有工程能力——契约、编排、血缘、评测、可观测——图全部白继承。做成独立链路，等于把前 12 周的功夫在图这儿全部重做一遍。

## Industry Signals（2026）

2024 的论文是起点，2026 的落地共识是「轻量化 + 混合 + 按题型路由」。

| 方案 / 平台 | 定位 | 2026 工程含义 |
| :--- | :--- | :--- |
| Microsoft LazyGraphRAG | 延迟建图、查询时按需用 LLM | 索引成本 = 向量，重写了成本账，首选试水 |
| Microsoft DRIFT Search | Local + Global 融合检索 | 把两种模式统一，比单独跑更全、更省 |
| Neo4j neo4j-graphrag | 官方 Python 包，已 GA | 生产落地首选存储 + 检索栈 |
| Graphiti / Zep | 双时序知识图（agent 记忆） | 解决「实体随时间漂移」 |
| Anthropic Contextual Retrieval | 给向量 RAG 加上下文 | 先试它，很多「以为要上图」的场景够用了 |

落地顺序：先用 Contextual Retrieval 把向量 RAG 榨到极限，还不行再上 LazyGraphRAG 试水，真需要复杂关系推理再上完整图 + Neo4j。一步一步来。

## 上图前的 5 个判断标准

「上图准入清单」，一项不达标就先别动。

| 判断项 | 具体问题 | 阈值 | 不达标的后果 |
| :--- | :--- | :--- | :--- |
| 题型占比 | 归纳 / 多跳类占比 | > 20% | 低于此值收益抵不过成本 |
| 数据规模 | 文档数量 | > 1k | 太少图结构没意义 |
| 关系密度 | 实体间真有结构关系 | 高（产品 / 组织 / 时序） | 低密度图意义不大 |
| 查询频率 | 主场题型 QPS | > 0.1 | 太低摊不平构建成本 |
| 工程能力 | 有没有 Week 6-12 底子 | 齐全 | 没底子上图是空中楼阁 |

用法：5 项全过 → 上 GraphRAG；只过 3 项 → 先做 PoC 跑一轮 A/B 拿数据说话；不到 3 项 → 别折腾，纯向量更稳。最后一项工程能力，也是这门课把 GraphRAG 放在第 13 周而不是第 3 周的原因。

## Recap

- GraphRAG 是为一类向量 RAG 必然失败的题型而生：全局归纳、关系遍历、交叉验证、时间序列。
- FAQ / 定义 / 短对话是向量的主场，硬上图比不上图更糟。
- 2024 那套「贵 5-10 倍」的成本账已被 LazyGraphRAG 重写，索引成本打到和向量一样。
- 图是数据工厂的下游派生资产，契约 / 血缘 / 编排 / 评测全部继承，不是另起炉灶。
- 5 个准入判断全过才上，只过 3 项先做 PoC。
