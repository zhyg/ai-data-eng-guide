# 5. AB 对比 + 适用边界

## 核心问题

前 4 节把 GraphRAG 完整做出来了，这一讲讲怎么用数据证明它值不值。

真实场景：最典型的 GraphRAG 失败不是技术失败，是上线半年后业务方问「花这么多钱上的图，效果到底怎么样」，团队拿不出数据。为什么拿不出？因为当初只看了个总体指标「F 从 0.85 涨到 0.87」就上线了，从来没按题型分开看。

关键判断：别问「GraphRAG 成不成功」，问「在哪些题型上成功、在哪些其实没必要」。

## 为什么「看总体指标」会骗你

「F=0.87 vs 0.85，涨了 2 个点，上线吧」——这是最常见的误判。这 2 个点很可能是这么来的：70% 简单题型图比向量差一点，30% 归纳类题型图比向量好很多，加权平均，略涨。真正的价值判断应该是：那 30% 归纳类涨了多少 vs 多花的 5-10 倍成本，回得来本吗？

| 错误的看法 | 正确的看法 | 决策公式 |
| :--- | :--- | :--- |
| 看总体加权平均 | 按题型分层看 | 主场题型收益 × 占比 |
| 「涨了 2 个点，上」 | 每类题单独算账 | −（图成本 − 向量成本） |
| 掩盖了局部翻车 / 翻盘 | 归纳题涨多少、成本多少 | > 0 才上 |
| 成本被平均稀释 | 主场题型占比够不够 | 让数据告诉你 |
| 拍脑袋决策 | 数据驱动决策 | 不是凭感觉 |

## A/B 实验的 4 个核心设计

缺一项结论都不可信，这是工业界判断 GraphRAG 是否上线的科学标准。

| 设计项 | 具体做法 | 为什么必须 |
| :--- | :--- | :--- |
| 并行运行 | 同 query 同时跑 Vector / Graph 两路 | 消除时间偏差 |
| 按题型分层 | 4 类（局部 / 全局 / 多跳 / 事实）分别统计 | 避免加权平均误导 |
| 多模型 Judge | GPT + Claude 互判（Week 11 交叉评审） | 消除单一 judge 的偏见 |
| 真实流量影子 | 5-10% 真实流量复制到 Graph | 收集真实分布数据，不靠造样本 |

关键判断：影子流量要特别强调。别拿自己造的 100 条评测题下结论，那跟真实用户问法差很远。把 5-10% 的真实线上流量镜像一份给 Graph 跑（只评测、不返回给用户），一两周下来拿到的才是真实题型分布。很多团队就死在「实验室数据好看、上线拉胯」这个坑里。

## A/B 实现要点

- **题型枚举固定为 4 类**：`focal` / `global` / `multihop` / `factual`
- **线程池并行跑两路**：同 query 同时提交 vector 和 graph 查询，两路同上下文、同时间，消除时间漂移偏差
- **用 Week 11 的 RAGAS 交叉评审打分**：GPT + Claude 互判，消除 judge bias
- **`by_category` 分层聚合**：这是核心，按 category 分组统计样本数、两路的 faithfulness 均值
- **`cost_overhead` 是关键决策指标**：算 `(graph_cost - vec_cost) / vec_cost`，Faithfulness +5% 但成本 +500% 不一定划算
- **跑进 Week 11 PR Gate**：任何 graph 模型 / prompt 变更都自动评测，不靠人工记得

## 典型 A/B 结果（200 样本）

| 题型 | 样本数 | Vec 忠实度 | Graph 忠实度 | 成本倍数 | 推荐 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 局部聚焦 | 70 (35%) | 0.91 | 0.88 | +450% | Vector 胜（图无意义） |
| 全局归纳 | 40 (20%) | 0.52 | 0.83 | +380% | Graph 胜（必须图） |
| 多跳推理 | 35 (17.5%) | 0.61 | 0.84 | +520% | Graph 胜（必须图） |
| 具体事实 | 55 (27.5%) | 0.93 | 0.90 | +400% | Vector 胜（图无意义） |

结论：归纳 + 多跳（37.5%）必须上图，忠实度从 0.5 出头拉到 0.83 以上，这是向量根本够不着的；局部 + 事实（62.5%）纯向量更划算，图不光没提升还多花 4-5 倍成本。所以 GraphRAG 唯一正确的用法就是按题型路由，让图只在它的 37.5% 主场上场。

## 按题型自动路由

Query 用户问题 → Classify 题型分类器（LLM + 规则）→ Route 路由（4 选 1）→ Execute（Vec / Local / Global / Multi）→ Respond 统一 RAGResponse

关键判断：这条路由链是 GraphRAG 落地的总开关。它让图在归纳 / 多跳这 37.5% 的主场题型上发力提质，在事实 / 聚焦这 62.5% 的客场题型上自动让位给便宜的向量，收益最大、成本最小。

## 题型分类器：整条流水线成本最低的一环

- **结构化输出焊死 4 类**：`category` 用 Literal 限定 focal / global / multihop / factual，同时返回 `confidence` 和 `suggested_retrieval`，永远输出 4 类之一，不会乱写
- **用最便宜的小模型**：gpt-4o-mini 比大模型便宜约 30 倍，分类一条 query 约 $0.0003。Anthropic 侧用 claude-haiku-4-5 更省，课程主线用它
- **`confidence < 0.7` 降级走向量**：防止误分类把简单题推到贵的图链路
- **「轻量 LLM 分类 + 重量级主链路处理」**：2026 Agent 工程标配，省钱又稳

## 接入已有工程的 5 类必做

不做接入，GraphRAG 半年后就是没人维护、没法定位的沉没成本。

| 工程能力 | 具体集成 | 来源 | 不做的后果 |
| :--- | :--- | :--- | :--- |
| 评测 | 题型分层评测 + golden set | Week 11 | 没法判断图是否劣化 |
| 可观测 | OTel span（Phoenix / Langfuse）覆盖图检索 + 序列化 | Week 12 | 出问题不知哪段慢 |
| 告警 | Graph 服务 SLO + 错误预算 | Week 12 L4 | Graph 挂了客户先发现 |
| 治理 | release manifest 含 graph_release | Week 8 + Week 14 | 图版本和向量版本不对齐 |
| Bad case | Graph 特有反例（错路径 / 错社区） | Week 12 L5 | 同类错反复发生 |

反模式提醒：这 5 类接入必须从上线第 1 天就做，别信「以后再加」。加在已经跑起来的 service 上，比从 0 建难 10 倍。上线时图当外挂、没接评测和可观测的项目，半年后就成了没人敢碰的黑盒，最后只能整个下线重来。

## 纳入 release manifest

图是 release 里的一等公民，继承 Week 8/9/11，所有元素原子绑定、可回滚。

| manifest 段落 | 内容 | 作用 |
| :--- | :--- | :--- |
| `graph_release` | schema_version、extractor_model、entity_count、edge_count、community_count、community_summary_version、last_full_rebuild | 把图的所有元素原子绑定，锁版本 |
| `graph_release.query_classifier` | prompt_version、confidence_threshold | 改分类器 = 改 release |
| `eval.by_category` | 每类题型的 vec_f / graph_f / mode 基线 | 按题型分层的基线锁住，下次评测必须分别看每一类，不许总体平均掩盖 |
| `rollout.auto_rollback_on` | graph_extraction_failure_rate、graph_query_p99_ms 阈值 | 图专项回滚条件，超阈值自动回滚 |

apiVersion 也要升版（比如 `omnisupport.rag/v4`），表示 manifest 结构新增了 graph_release 段。

## Industry Signals（2026）

一边是真金白银的降本，一边是「很多场景其实不需要图」的清醒。

| 来源 | 信号 | 判断 |
| :--- | :--- | :--- |
| Bloomberg / Goldman / LexisNexis | 图 + 向量混合、按题型路由，年省成本 40-60% | 金融 / 法律等强关系域，图是刚需 |
| EU AI Act | 「答案有结构化路径」比纯向量更好审计 | 监管在推图在金融 / 医疗加速落地 |
| LazyGraphRAG（微软） | 索引成本 = 向量、全局查询省 700x | 重写成本账，上图门槛大降 |
| GraphRAG vs 高级向量（社区争论） | 很多「以为要上图」的场景，Contextual Retrieval 就够 | 先榨干向量，别为上图而上图 |

2026 年，GraphRAG 在金融监管、医疗诊断、跨产品安全这类「强关系 + 强合规」的场景已经是工业刚需。但同时社区里也有越来越多声音提醒别神化图：很多「以为需要图」的场景，先上 Contextual Retrieval 把向量榨到极限、再上 LazyGraphRAG 试水，可能就够了。

## Week 13 收口：5 个判断

- **Boundary**：5 个准入判断决定上不上，2026 先用 Contextual Retrieval，再上 LazyGraphRAG 试水
- **Build**：schema-first 是第一性原理，强类型 + LLM 约束抽取 + 4 阶段实体对齐，漂移域上时序图
- **Search**：3 种模式按题型路由 + 向量兜底，2026 用 DRIFT 把 Local / Global 融合
- **Augment**：图 → 文本的翻译质量决定生成质量，3 种序列化 + 3 套模板 + 双链证据
- **Compare**：A/B 必须按题型分层，37.5% 主场上图、62.5% 客场走向量，全程接入治理

## Recap

- 看总体加权平均会骗人，必须按题型分层看效果，用「主场收益 × 占比 − 成本差」判断该不该上。
- A/B 四要素：并行运行、按题型分层、多模型 Judge、真实流量影子，缺一项结论都不可信。
- 归纳 + 多跳是图的主场，局部 + 事实纯向量更划算，按题型路由让收益最大成本最小。
- 题型分类器用最便宜的小模型，低置信度自动降级走向量。
- 评测 / 可观测 / 告警 / 治理 / Bad case 五类接入必须从上线第 1 天就做。
