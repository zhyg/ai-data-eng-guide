# 导学 06：怎么把前五讲串成一条真能跑起来的链路？

## 一句话理解

这一节把前五讲落地成代码：从上游知识块出发，按 schema 抽取、对齐、聚合社区，以一次图发布为单位事务性写入数据库，再接进已有的 RAG 服务。

## 用生活打比方

继续我们的资料室。前五讲把该想清楚的都想清楚了，这一讲讲怎么把这套流程立成常规工作。

每一次做墙都编个号，和文件目录的版本对得上。做墙的过程要么整套完成，要么整套作废，不能贴了一半就宣布可用。对齐时拿不准的卡片不硬合，挑出来单独放一格留给人工复核。抄卡片的人和管墙的人分开，两边各守一个约定，谁换都不影响对方。

来人提问先分类再决定去哪，归纳类和绕弯类上墙，其余翻手册。分类靠几条写死的规矩，结果可解释、可复核。最后立一份验收清单，每次改流程都照着核一遍。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **图发布（graph_release）** | 一次完整建图的产物编号，是所有图数据的父身份。实体、关系、社区、别名都挂在它下面，还记着这次用的是哪一版上游知识块。查任何图数据都要带上它，比如把本次抽取出的全部节点和边绑定到同一个编号下。 |
| **幂等重跑** | 同一批输入和同一个上游版本，重复跑构建流程结果一样，不会多出一份新图，比如用同一批数据再跑一次构建，库里不会重复增加数据。内容或上游版本变了，旧的编号就不能复用，必须生成新的。 |
| **事务性写入** | 一次构建的所有写库动作放在同一个事务里，任何一步失败整批都不生效，这一版图不会变成可用状态，比如写边失败时连同写好的节点也会一起撤回。避免出现半张图能被查到的情况。 |
| **隔离** | 实体对齐时判断为存在歧义、拒绝合并的记录，比如发现两个名字很像但拿不准的实体就分别保留。相似度高到一定程度才自动合并，落在模糊区间的宁可各自留着并记下原因，避免把两个不同的客户或产品错误合成一个。 |
| **抽取协议（Extractor）** | 抽实体和关系这件事只暴露一个接口，具体是大模型抽、规则抽还是用现成框架抽都藏在后面。换抽取方式不影响下游的对齐、聚合和检索。 |
| **图存储协议（GraphStore）** | 查图这件事只暴露几个固定方法，比如找实体、沿关系遍历、列出社区。底层现在用关系数据库，将来换成图数据库只要换一个实现，上层代码不动。 |
| **契约测试** | 一批检查配置和代码结构是否满足约定的测试，比如表结构对不对、schema 校验是否生效、路由行为是否符合预期、响应里该有的字段是否都在。它保证图这一层的工程约束不会在后续改动中被悄悄破坏。 |

## 避坑提醒

- **以为图数据就是可以边建边写库的**：一边抽一边写，中途失败就留下一份不完整的图，而且很难判断到底缺了什么。构建产物必须整批写入，整批成立或整批作废。
- **以为对齐不确定时随便挑一个合并就是没关系**：错合两个实体，它们的关系会全部串到一起，之后沿这些关系推出的所有结论都是错的，而且很难发现。判断不清就隔离，留给人工复核。
- **以为换图数据库就是要重写检索代码**：把查图的能力抽成几个固定方法，底层实现藏在后面，换存储只是换一个实现类。反过来，让检索代码直接写死具体数据库的查询语句，将来换存储就是一次大重构。
- **以为社区划分就是必须用大模型**：先用确定性算法把连接紧密的节点分组、按固定顺序生成摘要，没有外部依赖、结果可重复验证，先把链路跑通。等真需要更好的概述质量，再把摘要那一步换成模型生成并做版本化。
- **以为每次重跑就是都要建一份新图**：不做幂等设计，同一批输入跑两遍就多出一份图，版本越来越乱，也说不清哪一份在被使用。同一批输入加同一个上游版本必须复用原来的编号。

## 一句话总结

> **图的每一次构建都以一个发布编号为单位整体成立或整体作废，抽取引擎和图存储都藏在协议后面可以随时替换；检索前先分类路由，生成后带上原文和图两层证据，最后按四类题型分别验收。**
