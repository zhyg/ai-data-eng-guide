# 导学 01：什么样的问题，翻遍相似段落也答不出来？

## 一句话理解

GraphRAG 把文档里的实体和它们之间的关系显式建成一张图，让检索能跨过单个文档片段的边界，专门回答那些答案散落在多份文档关系里的问题。

## 用生活打比方

把知识库问答想成一个资料室。资料室里堆着上千份项目文件、会议记录、工单，有人负责回答提问。

大多数提问只要查一页就够：报销标准是多少、某个流程第三步做什么。负责人凭经验翻到最相关的那几页，抄给你，事情就办完了。

但有天领导问的是另一种问题：过去半年出过问题的项目，都有什么共同点？这时候翻"最相关的几页"没用，因为答案不在任何一页上，它藏在上百份文件互相牵连的关系里。要回答它，得先在墙上做一面关系图墙：把文件里出现的人、公司、产品、故障各写成一张卡片贴上墙，再用线把有关系的卡片连起来。这面墙就是图，做墙这件事就是 GraphRAG。

做墙很费工。所以整个第 13 周要反复问的就是这句话：这次的提问，值得为它做一面墙吗？

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **图检索增强生成（GraphRAG）** | 先把文档中出现的对象和它们之间的联系抽成一张图，检索时沿着关系走、按结构归纳，再交给大模型生成答案的做法。比如回答过去半年所有严重故障的共性是什么。 |
| **实体节点（entity_node）与关系边（relation_edge）** | 图里的两种东西。节点是文档里出现的具体对象，比如某个客户、某张工单、某个产品；边是节点之间的联系，比如「这张工单是这个客户提的」。 |
| **派生数据资产** | 由已有数据加工出来的新数据，本身也纳入统一管理。图是从已经切好的知识块加工出来的，所以它属于派生的那一层，不是独立的一套系统。比如从文档片段中提取出来的实体表格。 |
| **轻量图检索（LazyGraphRAG）** | 微软提出的轻量做法。建图阶段只用便宜的手段抽名词短语和大致分组，把调用大模型的重活推迟到用户真提问时才做，索引开销因此降到和普通的按语义相似度搜索的做法相当。 |
| **上下文检索（Contextual Retrieval）** | Anthropic 提出的做法，给每个知识块补一段说明它在原文中位置和背景的上下文，再去做向量检索。很多以为需要建图的场景，用它就够了。 |
| **上图准入清单** | 决定要不要建图的一组判断项：这类问题在总提问量里占比、文档规模、实体之间关系是否真的密、这类提问的频率、团队有没有前面几周的工程底子。比如要求需要总结归纳的问题在总提问中达到一定比例。 |

## 避坑提醒

- **以为答案不准的原因就是没上 GraphRAG**：答不准的原因很多，切块粒度不合适、召回排序没调好、提示词约束不够，都会让答案变差。GraphRAG 只解决一件事，就是答案散在多份文档的关系里。其他原因造成的答不准，上图也救不回来。
- **以为 GraphRAG 就是向量检索的升级版**：它只在特定题型上补位。查操作步骤、查名词定义、短对话这些场景，向量检索本来就答得又快又准，加上图之后不但没有提升，还会引入无关的关联，把成本和延迟一起抬上去。
- **以为上图就是另起一套独立系统**：另搭一条抽取流水线、另选一个图数据库、另起一个查询服务，结果图和原有的数据资产成了两张皮，契约、版本、血缘、评测全断掉。图应该建成已有知识块的下游，这样前面几周攒的工程能力可以直接继承。
- **以为图和向量就是二选一**：生产系统里两种检索长期并存，靠一个分类器把不同题型分别送到合适的那条路上。

## 一句话总结
