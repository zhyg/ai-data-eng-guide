# 导学 03：图已经建好了，到底该怎么在上面找东西？

## 一句话理解

图检索有三种模式：从一个实体向外扩展看邻居、把整张图分组后逐组归纳、沿着关系链往下走若干步，各自回答一类向量检索答不了的问题。

## 用生活打比方

继续我们的资料室。那面关系图墙贴满了，卡片规范、重复的也合并过了。现在有人来提问，怎么用这面墙？

三种提问对应三种用法。问「这个客户都出过哪些事」，先找到这个客户的卡片，顺着线把周围一两圈的卡片取下来，这叫从锚点向外扩展。问「出问题的项目有什么共同点」，没有起点可找，得看整面墙，做法是提前把墙划成若干区块，每堆旁边贴一张纸条概述主题，来了全局问题时取纸条汇总就行。问「这家公司的下游供应商还给谁供货」，得从一张卡片出发顺着线一步步往下走，但要立规矩：最多走几步、只走哪几种线、路径按可靠程度打分、最后还得有人看一眼讲不讲得通。

来人问「怎么重置密码」，墙上找不到起点，这时候退回去翻手册就行。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **锚点实体（anchors）** | 从提问里识别出来的、图上真实存在的那个对象，是检索的出发点。认不出锚点就说明这个问题不适合用图，该降级回向量检索。比如「客户 X 的所有工单」里的客户 X。 |
| **子图扩展（Local Search）** | 从锚点出发把周围一两层的节点和边一起取出来。用来回答聚焦在某个具体对象上的问题，开销最低，也最常用。 |
| **社区检测（Community Detection）** | 把整张图里连接紧密的节点自动分成若干组。工程上常用 Leiden 这个算法，它比早一代的算法更快也更稳，不会切出割裂的组。比如将相关联的故障类型自动归为一组。 |
| **社区摘要** | 给每一组节点预先生成的一段概述，包含这组的主题、关键事实和关键实体。它在建完图之后批量算好存入库中，查询时直接取用。 |
| **全局检索（Global Search）** | 回答归纳类问题的模式。先并行读取各组的摘要分别作答，再把各组答案汇总成一个整体结论。这样就把「通读全图」拆成了「读若干组概述再合并」。 |
| **路径遍历（Multi-hop）** | 从一个实体出发，沿着关系一步一步往下走，找出连到目标的关系链。用来回答需要绕几道弯的关系问题，也是最容易失控的模式。比如查询「A 公司的子公司的供应商」。 |
| **跳数上限（max_hops）与关系白名单（relationshipFilter）** | 遍历时的两道硬约束。前者规定一次最多走几步，步数一多取回的节点量迅速膨胀，链条太长也没人解释得清；后者规定只允许走哪几种关系类型，不设白名单则任意关系都能走，取回的东西很快偏离原本的问题。 |
| **动态推理检索（DRIFT Search）** | 微软后来提出的融合模式。用户问一个聚焦问题时，它把「这个锚点属于哪一组、这组的大背景是什么」一起带进检索起点，然后在局部和整体之间来回走，一次检索兼顾细节和背景。比如既看某个具体工单，又看这个工单所属类别的整体背景。 |

## 避坑提醒

- **以为图检索就是把图当向量库用**：只是在原来的相似度检索之外多召回几个图节点，仍然按语义相近程度挑东西，图能跨越关系找答案的本事一点没用上，建图的开销全浪费了。
- **以为图检索的最佳策略就是一种模式打天下**：同一张图，「某个客户的所有工单」要向外扩展，「故障类型分布」要分组归纳，「某公司的下游的下游」要沿链遍历，三种问法走的是三条完全不同的路。模式选错，取回的东西再全也答不对题。
- **以为社区摘要就是查询时现算的**：那样每次归纳类提问都要重新通读整张图，延迟和开销都抗不住。摘要是建完图之后批量算一次入库的产物，图有较大变动时再重算。
- **以为多跳能力就是越强越好**：不限步数的遍历在稍大的图上就能取回海量节点，把上下文撑爆、把这一次请求的开销拉高好几个量级。四道护栏（限步数、关系白名单、路径打分、语义校验）一道都不能省。
- **以为有路径就是相关**：路径在结构上走得通，语义上可能完全不相干。打分高只代表每一段关系都可靠，不代表整条链讲得通，最后还要让大模型判断一次连贯性。

## 一句话总结

> **三种检索模式按题型分开走，认不出锚点就降级回向量检索；沿关系链遍历时，跳数上限、关系白名单、路径打分、语义校验四道护栏一道都不能省。**
