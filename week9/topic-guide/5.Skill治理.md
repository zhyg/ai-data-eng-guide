# 导学 05：技能包该怎么管，才不会改一处崩一片？

## 一句话理解

Skill 治理是把技能包当正经软件产品来管：改动走审批、上线前跑回归测试、每个版本有编号能回退，还要把技能版本和数据、索引、Prompt 一起锁进发布记录，并守住"别人的代码在你机器上跑"的安全边界。

## 用生活打比方

继续我们的餐厅菜谱包。招牌菜的配方不能谁想改就改。改一个字都要走审批，先小批量试做、确认味道没跑偏，才正式更新，还要留下每一版配方，记清这周用的是哪一版。出了问题，能查到是哪次改动惹的祸，也能马上换回上一版。

当季菜单会把"这一季用哪版配方、哪版摆盘、哪版食材"一起锁定，作为一个整体发布。另外，来路不明的菜谱不能直接进后厨，得先审一遍，防止有人夹带不安全的东西进来。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **治理三大支柱** | 版本（每次改动有编号、能回退）、评测（上线前跑一批标准测试）、Registry（统一存放和发现技能的仓库） |
| **语义化版本（SemVer）** | 用"主版本.次版本.修订号"这样的编号规则标记版本，让使用方一眼看出这次改动大不大、兼不兼容 |
| **黄金测试集（golden set）** | 一批固定的标准测试用例。每次改技能都拿它跑一遍，效果一退步就不许合并，是治理里性价比最高的一步 |
| **技能仓库（Registry）** | 统一存放技能、供人和 AI 查找的地方，核心能力是管好"依赖关系"和"版本"，类似应用商店的后台。小团队用一个 Git 仓库就够，规模起来再上专门的服务 |
| **发布清单（Release Manifest）** | 一份记录，把这次发布用的数据、索引、Prompt、技能版本一起锁定，出问题能精确定位、能整体回退 |
| **信任边界** | 技能包里会跑代码，装一个来路不明的技能等于在自己机器上跑陌生人的程序。只用可信来源（自己写的、官方的、过审的），技能里如果会去联网抓外部内容，要格外警惕 |
| **四个落地面** | 技能包目前已经能装进多个环境：Claude Code（放项目或个人目录自动发现）、Claude API（请求里带技能配置）、claude.ai（网页端上传）、企业版集中分发（按团队授权加审计） |

## 避坑提醒

- **以为改技能包只是"润色文字"不用走流程**：技能是 AI 的行动手册，改手册等于改业务行为，一处改动可能让多个下游一起变样，必须像改代码一样走审批和回归。
- **以为技能包只是文档、不用测试就能上线**：不测就上线，等于拿真实用户当测试集。一批标准用例加自动回归，是治理里性价比最高的一步。
- **以为技能包只是 Markdown、很安全**：技能包能跑脚本，它的权限等于它能碰到的一切。已有安全机构发现过大量恶意技能包，要按生产服务的标准审，尤其警惕包里去联网抓外部内容。
- **以为一上来就该建"企业级技能中台"**：中小团队先用一个统一的技能仓库起步就够了，规模真起来再上更重的方案，别为治理而治理。

## 一句话总结

> **技能包是工程产品，版本、评测、仓库、发布锁定、安全边界都要配上，让每一次改动都可追溯、可回退、可信任。**
