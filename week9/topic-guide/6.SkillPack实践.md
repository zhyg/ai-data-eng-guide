# 导学 06：怎么把前几周攒下的工程能力，真正打包成技能包？

## 一句话理解

本节是工程实践课，把前几周积累的数据契约、补数、RAG 校验、Prompt 发布等能力，各自整理成一个技能包，再配上格式检查、统一的技能仓库和发布锁定，做成一套 AI 能发现、能按需加载、能被版本锁定的技能系统骨架。

## 用生活打比方

继续我们的餐厅菜谱包。前几个月摸索出来的几道招牌菜，这节课正式整理成一整套标准菜谱包，每道菜一张菜谱卡加配套。

还搭了三样东西：一张"菜谱格式检查表"，新菜谱进后厨前先过一遍，格式不合规就不让进；一个"菜品索引台"，服务员和点菜系统先看菜名索引，点到哪道才调出详细菜谱；再把"这一季用哪几版菜谱"锁进当季菜单。到这里，零散的招牌菜第一次变成了能查、能管、能锁版本的一整套。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **五个交付技能** | 把前几周的能力分别沉淀成技能包，比如数据契约检查、补数 runbook、RAG 响应校验、Prompt 发布、发布完整性检查 |
| **契约测试 / 格式门禁** | 一份格式规则，遍历所有技能包检查是否合规（名字、描述、版本、目录名对不对得上），不合规就不让进 |
| **技能注册中心（Skill Registry）** | 管理技能注册和发现的核心组件，对外提供两个基本接口：列出所有技能简介、按名字取详细内容 |
| **渐进式披露的两阶段** | 先把所有技能的简介读进内存供 AI 挑选，选中了才按名字拉取那个技能的完整内容 |
| **导出适配（OpenAI / MCP）** | 把技能的描述转换成不同平台认识的格式，方便被不同 AI 工具调用 |
| **发布清单加技能项** | 在发布记录里新增技能版本，产品上线时能说清用了哪套技能包，出问题能定位、能回退 |

## 避坑提醒

- **以为这周要写很多新业务功能**：这周基本不写新业务，重点是把已有能力打包成规范的技能包，再补上发现、加载和治理的骨架。
- **以为技能包目录整齐就算工程化了**：没有格式检查，目录只是约定俗成；有了自动检查门禁，才能保证每个技能格式合规、能被安全读取。
- **以为一定要在大模型里才能验证技能**：技能里的脚本在本地能一行命令跑通，放进大模型里也能成功，本地验证更快也更省。
- **以为注册中心该一次返回技能的全部内容**：列表接口只返回简介，取详情才按名字加载完整内容，这正是渐进式披露的设计，一次全返回就违背了初衷。

## 一句话总结

> **这周交付的是一套技能系统骨架，把前几周的工艺打包成可发现、可加载、可锁定的技能包，能通过格式检查、能被注册中心按需披露、能锁进发布清单才算就绪。**
