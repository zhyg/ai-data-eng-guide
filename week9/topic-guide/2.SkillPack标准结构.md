# 导学 02：一个技能包里到底该放哪些东西？

## 一句话理解

一个技能包就是一个目录，里面必有一份 SKILL.md（说明加步骤），外加三个可选子目录，分别放可执行脚本、参考资料和产物模板，每样东西都有明确分工。

## 用生活打比方

继续我们的餐厅菜谱包。一套完整的菜谱包，核心是一张菜谱卡：卡片顶部写清菜名和什么场合上这道菜，下面写做法步骤。再配三样东西：一套厨房设备（能直接动手干活的），一本后厨资料手册（要用到食材知识或做法示例时才翻），一叠空白摆盘图（出成品时往上摆）。

关键是分清哪样放哪。设备就放设备区，资料就归资料架，摆盘图单独一叠。全堆在操作台上，换一家分店的后厨就没人搞得清怎么开工了。放对位置，这套菜谱包才能原样搬到任何后厨。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **SKILL.md 的两部分** | 上半段是给机器读的头（叫什么、什么时候用），下半段是给人和 AI 一起读的正文（怎么做、禁止什么） |
| **元数据头（YAML frontmatter）** | 文件开头一小段结构化信息。官方只强制两项：name 和 description |
| **name（名字）** | 技能包的唯一标识，全小写、用连字符连词，比如 data-contract-lint |
| **description（描述）** | AI 判断"要不要用这个技能"的唯一依据，要同时写清做什么、什么时候用 |
| **scripts / references / assets** | 三个配套目录，口诀是"动词、名词、形容词"：能执行的脚本、供查阅的资料、做产物用的模板 |
| **幂等** | 同样的输入跑两次，结果完全一样。补数据或重试时，不会因为多跑一遍就出乱子 |
| **结构化输出** | 脚本的运行结果用 JSON 等固定格式返回，AI 能直接解读，不用靠猜 |
| **错误码** | 脚本用不同的返回值告诉 AI"哪里出了问题"，比如 0 代表成功、1 代表输入有误、2 代表规则违反，AI 据此决定是重试还是报错 |

## 避坑提醒

- **以为 SKILL.md 越详细越好，什么都往里塞**：正文太长会拖慢 AI 加载。参考资料该放 references，模板该放 assets，正文只留步骤。
- **以为 references 和 assets 是一回事**：references 是"读来理解"的资料（输入侧），assets 是"拿来生成成品"的模板（输出侧）。混在一起，技能包就没法治理。
- **以为脚本随便丢几个就行**：脚本要能从技能包里单独拿出来，在一台干净机器上一行命令跑通。还得满足幂等、输出结构化 JSON、用错误码区分失败类型这几个要求，不能只靠打印。
- **以为要装框架或特殊环境才能用**：技能包不绑任何运行时，就是文件加 Markdown。这正是它能跨工具搬走的根本原因。

## 一句话总结

> **技能包的可移植性来自它极简的固定结构：一个目录、一份 SKILL.md、三个各司其职的子目录，把东西放对位置比写得多更重要。**
