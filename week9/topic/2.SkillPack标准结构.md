# 2. Skill Pack 标准结构

## 核心问题

90% 团队第一次写 Skill 都是把代码、文档、模板、Prompt 全塞进一个文件夹，SKILL.md 写成两千行大杂烩，换个工具就跑不起来，想改一行得通读全文。Skill 难看不是因为它复杂，是因为没人告诉他们：这东西有标准结构（Anthropic 标准里规定的）——scripts 放动词、references 放名词、assets 放形容词，该放哪放哪，简单到不可思议。

## Skill 的本质是「一个目录」

不需要框架、SDK、特殊运行时，每个组件都有明确职责：

| 组件 | 职责 |
| :--- | :--- |
| SKILL.md | 给 LLM 的入口：元数据 + 指令 |
| scripts/ | 给系统执行的可运行物 |
| references/ | 给 LLM 按需检索的资料库 |
| assets/ | 给产物提供的模板 |

简单结构承载复杂能力，不绑任何运行时——这是 Skill 能「跨工具搬走」的根。结构越简单，越可移植。

## SKILL.md 由两部分组成

一份给机器，一份给人。YAML 头决定「何时用」，正文决定「怎么做」：

- **YAML Frontmatter**（机器读，决定何时激活）：name 唯一标识、description Agent 发现依据。官方只强制这两个字段。
- **Markdown 正文**（人 + Agent 双观众读）：触发 / 反触发条件、执行步骤 + 约束 + 禁区、正反例。
- **双观众阅读**：工程师 review 看正文，Agent 加载看两部分；改 = 改 .md 走 PR，Git 跟踪 = 天然版本化。

「改 .md 走 PR」这一条，就是 Skill 工程化的命门：工艺第一次能像代码一样被 diff、被 review、被回滚。

## Frontmatter：官方只强制 2 个字段

别被一堆字段吓到，要把团队扩展字段和 spec 必填字段分清楚：

- **name**：≤ 64 字符，小写 / 数字 / 连字符，禁用 anthropic、claude 保留词
- **description**：≤ 1024 字符，第三人称，必须同时写清「做什么」+「何时触发」。它是 Agent 发现的唯一依据——写不好就找不到，写太宽就误激活
- **spec 可选字段**：只有 license / compatibility / metadata / allowed-tools（实验）
- **团队工程化扩展（非必填）**：version（SemVer，治理用）、inputs、outputs、requires、permissions 等，都是团队自加

## scripts / references / assets——三者边界别混

一句口诀：动词 / 名词 / 形容词。

| 目录 | 装什么 | 谁读它 | 何时加载 |
| :--- | :--- | :--- | :--- |
| scripts/ | 可执行代码（.py / .sh） | 系统运行时执行 | 执行时按需调用 |
| references/ | 规范、案例、资料（.md） | LLM 检索补上下文 | LLM 决定要不要读 |
| assets/ | 模板、初始化文件 | Skill 生成产物时用 | 生成阶段加载 |

最容易混的是 references 和 assets：references 是「给 LLM 查的资料」（如 ODCS spec、正反例），assets 是「Skill 生成产物的模板」（如空白契约 yaml）。一个是输入侧、一个是输出侧。记死这条——你要「读它来理解」的放 references，你要「拿它来生成」的放 assets，别让 SKILL.md 自己膨胀。

references/ 只放真会用到的 5-10 篇，多了反而拉低检索效率；assets/ 放产物模板，Skill 把变量填进模板出产物。

## scripts/ 的 4 个设计要点

scripts 是 Skill 里工程化要求最高的部分，不是「丢几个脚本」：

1. **幂等可重入**：同样输入跑两次结果一致，补数 / 重试场景必须如此（Week 6「3 层幂等」同样适用）
2. **结构化输出**：输出 JSON 不要 print，LLM / 下游能直接 parse，argparse + json.dumps 起步
3. **明确错误码**：0 成功 / 1 输入错 / 2 规则违反，让上游决定重试 / 报错 / 升级，区分「能不能重试」
4. **零外部依赖**：能用标准库就用标准库，必须用三方就在 requirements 显式声明，依赖多 = 跨环境跑不起来

判 scripts 好不好就一条：把它从 Skill 里抠出来，能不能在一台干净的机器上一行命令跑通。跑不通就不算工程化。

生产级 script 的要点：docstring 写明 exit code（Agent 才知道怎么解读结果）；argparse 参数与 SKILL.md 的 inputs 严格对应；输出全部结构化 JSON，Agent 直接 parse 不靠猜；exit code 区分「输入错」和「内容错」，决定能不能重试；只用标准库 + 必要三方库，搬到任何环境都能跑。

## 五个组件如何协作

各司其职、按需组合，放错位置就不可治理：

Frontmatter（匹配查询） → Markdown（LLM 理解任务） → References（按需查规范） → Scripts（执行 + 回结构化结果） → Assets（填模板出产物）

这条链是 Skill 设计的核心：发现靠 frontmatter、执行靠正文、补上下文靠 references、干活靠 scripts、出产物靠 assets。任何一个职责放错位置，整个 Skill 就变得不可治理。
