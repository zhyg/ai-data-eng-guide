# 6. Skill Pack 实践

## 核心目标

本节是第九周的工程实践课，内容相对简单：不写新的业务功能，而是把前八周积累的工程能力封装成可被 Agent 发现、按需加载、并由发布清单锁定的 Skill Pack。目标是确保 AI 助手按照已定义的工程规范、脚本和模板工作，并加强安全边界。整周边界是「显性执行」——展示 Skill Pack 可以携带脚本、模板和检查逻辑，不包括远程自动破坏性测试。

## 五个交付 Skill：把前八周固化成资产

前八周的 SOP、工程规范和经验被固化为 Agent 使用的 Skill：

| Skill | 来源 | 职责 |
| :--- | :--- | :--- |
| data-contract-lint | 第二周数据契约输入控制面 | 检查数据契约、PII、许可证和提交质量门禁 |
| ingest-backfill-runbook | 第三到第六周采集 / 入湖 | 规划 Replay 或补数，限制补数范围、确保幂等与回滚、记录证据 |
| rag-contract-check | 第八周 RAG | 检查 RAG 响应的 citation、evidence_id、release_id、trace_id |
| prompt-release | 第八周 Prompt | 规范 Prompt 版本发布与回滚 |
| release-check | 第九周提前引入（14 周后深入） | 检查数据、索引、Prompt、Skill、Eval 是否绑定完整 |

rag-contract-check 的核心是让 RAG 不仅回答问题，还能证明答案来源。每个 Skill 都来源于课程中的具体实践。

## 整体架构

整条链路从构建到发现再到治理形成闭环：

Skill 构建（SKILL.md + 三件配套） → 契约测试（schema 门禁） → 注册中心（发现 / 渐进式披露） → 发布清单锁定（治理）

Skill 代码位于 skills 目录下，每个 Skill 以 SKILL.md 为入口文档：上半部分是 YAML frontmatter（给 Agent 的系统提示，常驻内存），name 是唯一标识，description 作为搜索元数据决定搜索命中，not_for 防止误触发、明确边界，inputs / outputs 定义输入输出与验收方式；激活后的正文是给 Agent 的操作步骤和安全边界。以 data-contract-lint 为例，SKILL.md 负责说明和路由，scripts 负责执行脚本，references 包含 Agent 检索所需的深度上下文，assets 提供输出模板。

## 契约测试：Skill 的质量门禁

企业工程中文档本身也是一种数据结构，具有契约性质。Skill Pack 未来可能被 Codex、Claude Code、MCP 客户端或内部平台读取，因此 name、version、description 等字段不能随意填写。通过 skill-pack.schema.json 定义契约 schema，把这些字段从建议性规范变为强制性要求。

契约头部包括 $schema、title 和必填字段（name、description、version）。例如 name 字段必须符合正则表达式，且描述要匹配目录名称。这一模式类似第二周的 data-contract，最终作为质量门禁使用——没有它，Skill 目录只是约定俗成；有了它，就能进行工程化测试，确保每个 Skill 格式合规。

## Skill 注册中心

注册中心由 skill_registry.py 管理（位于 service/tool_api/app/skills 下），是第九周的核心代码，类比微服务中的服务注册中心，用于服务发现和元数据拉取。

**渐进式披露的两个阶段**：
1. 第一阶段只读元数据——把所有 Skill 的 name / description 拉取到内存，Agent 进行任务推理时扫描这些元数据，匹配适合当前任务的 Skill
2. 匹配完成后，Agent 通过接口按需拉取该 Skill 的详细信息（正文、模板、证据引用）并执行

**分层数据模型**：
- skill_meta：name + description 两个必填字段（及其他非必填），必须满足契约要求
- skill_detail：元数据 + body（正文），以及 scripts / references / assets 三部分

Registry 用 Pydantic 模型校验 name、计算 digest 指纹，对外提供 discover / get_meta / get_skill / search 等开放接口，并支持面向 OpenAI 与 MCP 的适配导出：
- **openai_tool_exports**：导出 OpenAI function tool 的激活描述（返回 function 激活描述与参数属性，不是业务动作执行结果）
- **mcp_tool_exports**：MCP 式的描述导出，标注 read-only 等 event mode

## HTTP API 与服务集成

Registry 配好后，通过 routers/skills.py 封装成 REST API（类似 Java 的 service 实现），在 FastAPI 中挂载到 API v1，共 4 个接口：

| 接口 | 作用 |
| :--- | :--- |
| /api/v1/skills | 返回 Skill 元数据列表（含渐进式披露各阶段描述、release_id、count），当前 count=5 |
| /api/v1/skills/{name} | 按 name 加载具体 Skill 详情（digest、body、scripts、reference、asset 索引带 release_id） |
| /skills/exports/openai | OpenAI 导出接口，返回 function 激活描述 |
| /skills/exports/mcp | MCP 导出接口；无对应技能时返回 no such skill 给 Agent，避免乱打 |

main 函数是服务启动总入口，新增的 skill router 在此挂载。整个 tools API 承载工单工具、KPI 工具、HITL 和审计功能，在企业级服务中扮演业务层 / 后台服务角色。

## Docker 与配置

infra 中的 Docker Compose 把仓库里的 skills 目录以只读方式挂载进容器的 /workspace/skills（容器内默认路径通过环境变量注入），因此 tools API 无需将技能包打进镜像即可读取最新的 Skill configs。相关配置包括 skill_registry.py、metric_registry.py 和 release_id。

## 发布清单锁定

contracts 的 release 部分涉及一个 manifest schema 文件，不仅用于运行时发现技能，还能把技能版本锁定到发布清单。第九周在发布清单中新增 skill_id，产品发布时不仅能知道用了哪些数据、索引和 Prompt，还能明确 Agent 选择了哪套 Skill Pack；eval_summary 和 rollout_notes 作为发布证据。

## 测试与验收

测试目的不是形式上的美观，而是防止有人添加不合规的 Skill：

- **契约测试（Skill Pack shape）**：遍历整个 skills 文件夹下的所有 SKILL.md，检查 frontmatter 是否符合 schema、目录名是否与 SKILL.md 中的 name 一致，并确保每个 Skill 具备 not_for、outputs、scripts、references、assets 的正确结构；当前 5 个白名单项目，可做破坏性测试验证格式（演示时正反面测试，本地三个 pass 通过）
- **manifest-skill 绑定测试**：验证技能版本与发布清单的绑定
- **集成测试（skill_registry）**：验证注册表行为符合渐进式披露设计——list 只能返回元数据不能返回主体内容，get_skill 才按需加载完整内容；另有 OpenAI 与 MCP 的导出测试（旁路运行 + endpoints 测试，四个 pass 通过）

老师课堂原则：不一定非要在大模型中测试，本地 Python 脚本能跑通，在大模型中也能成功。本地演示中 data-contract-lint 挂载契约文件校验、第二第三个 Skill（含从 assets 做模板输出）均状态 OK。启动服务后可用浏览器 / Postman 查看接口：先查健康度（这一步不过后续无法进行），再看 /api/v1/skills 元数据（count=5 与数据一致），最后按 name 查看某个 Skill 的正文与索引，以及导出接口返回的激活描述。
