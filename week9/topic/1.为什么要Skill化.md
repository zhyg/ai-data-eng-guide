# 1. 为什么要 Skill 化

## 核心问题

团队最值钱的不是代码，是那些没人沉淀的「工艺」（流程、规范、模板、脚本），而它们一直在随人走。本节讲清楚：为什么「流程靠 Confluence、规范靠老师傅」在 LLM 时代彻底走不通，Skill 跟 Tool / Prompt / Workflow / MCP 的本质区别，一个 Skill 到底长什么样，以及用 7 个信号判断团队是不是到了 Skill 化的拐点。

真实场景：组里做得最好的「补数 SOP」全靠一个老工程师，他离职两个月后，新人翻遍 Confluence（文档停在半年前、脚本散在三个仓库），关键那句「跑之前先锁分区」只在他脑子里，结果补错一张维表，下游 6 个看板 GMV 对不上，排查了一整天。工艺不是写在 Confluence 里，是封进一个能跑的包。

## Skill as Pack：AI 工程化的第三次跃迁

Skill = 软件工程方法 × 知识管理的融合形态，把流程、规范、模板、脚本这些「非代码软件资产」，第一次像代码一样工程化。它和前两次跃迁同代际：

| 跃迁 | 含义 | 时间线 |
| :--- | :--- | :--- |
| Data as Code | 数据像代码一样版本化 | 2020-2023 已普及 |
| Prompt as Code | Prompt 像代码一样工程化 | 2023-2024 正普及 |
| Skill as Pack | 工艺打包成可移植对象 | 2025+ 刚起步 |

三层是叠加不是替代：没有 Data as Code 的版本化，Skill 里的脚本照样不可复现。Skill 站在前两层的肩膀上（L1 Data as Code → L2 Prompt as Code → L3 Skill as Pack）。

## 没有 Skill 标准之前——知识散在 7 个地方

它们合起来是团队的「非代码资产」，却没一个被工程化对待：

| 知识载体 | 常见痛点 | 真实例子 |
| :--- | :--- | :--- |
| Confluence / Wiki | 过期最快、无版本、没人维护 | 「补数 SOP」半年没更新 |
| 代码注释 | 只服务这个项目，跨项目难复用 | ETL 脚本里那句「小心 X 字段」 |
| Prompt 模板 | 工具绑定，OpenAI / Claude 各一份 | 一份 prompt 跨工具不能用 |
| 口口相传 | 人在流程在，人走流程消失 | 「找老师傅就行」文化 |
| Slack / 群历史 | 搜不到、上下文全丢 | 半年前的关键决策再也找不到 |
| 内部脚手架 | 自研框架黑盒，迁移成本高 | 「我们自己的 Agent 框架」 |

Skill 标准的目标，就是把这 6-7 类散落资产收拢成「一类对象」——一个目录、一份 SKILL.md，能被 Agent 发现、被 Git 治理、跨工具搬走。

## Skill 跟 Tool / Prompt / Workflow / MCP 差在哪

Skill 不替代它们，而是把它们组合起来的「打包格式」：

| 对象 | 解决什么 | 跟 Skill 的关系 |
| :--- | :--- | :--- |
| Tool / Function | 让 LLM 调一个具体函数 | Skill 内部可以调它 |
| Prompt 模板 | 约束单次输出 | Skill 可以把它内嵌 |
| Workflow | 编排端到端流程 | Skill 可封装，但不绑工具 |
| MCP Server | 连接外部系统 / 工具 / 数据 | 互补：MCP 管「连接」，Skill 管「怎么用好」 |
| Skill Pack | 把工艺打包成可移植对象 | 把上面这些组合起来的容器 |

2026 架构共识：MCP 是「神经系统」（接触世界），Skill 是「心智剧本」（接触后怎么干漂亮），subagent 是「隔离的专精脑」，三者叠加才是最强解。成本铁律：能用一个 Markdown 解决，就别上一个部署的服务。

## 一个 Skill 长什么样——简单到出乎意料

没有 SDK、没有运行时，就是文件夹 + Markdown。本质就这些：1 个目录 + 1 份 SKILL.md（必），加上 3 个可选子目录（scripts / references / assets）。

- **YAML 头**是给 Agent 看的元数据，决定「什么时候用它」
- **正文**给「人 + Agent」一起读：工程师能 review，LLM 能执行
- **scripts/** 把「知识」变成「可执行」，这就是工艺打包

## Agent Skills 已经是 GA 的开放标准

别再说「在观望」，标准已经收敛：

| 时间 | 事件 | 工程含义 |
| :--- | :--- | :--- |
| 2025.10.16 | Anthropic 首发 Agent Skills（beta） | Claude / Claude Code 原生支持目录发现 + 渐进加载 |
| 2025.12.18 | 开源为开放标准 agentskills.io | 不再绑 Anthropic，MCP 同期捐 Linux 基金会 |
| 2026.02 | 企业管控 + 合作伙伴技能目录上线 | Atlassian / Figma / Canva / Notion / Stripe / Zapier |
| 2026 上半年 | Codex / Cursor / Gemini CLI / Copilot 等 30+ 跟进 | SKILL.md 成跨厂商事实标准，仓库约 15 万 star |

选择不再是「要不要 Skill 化」。SKILL.md 正在成为「Agent 界的 REST」，标准已收敛，自己再造一套就是纯工程债。

## 什么时候该开始——7 个信号自测

中 3 条以上，就别拖了：

| 信号 | 具体表现 | 严重度 |
| :--- | :--- | :--- |
| 流程靠「找老师傅」 | 关键操作没有可执行文档 | 高 |
| 同一规范多份副本 | 不同项目各写一份契约检查 | 高 |
| 跨工具迁移痛 | OpenAI / Claude / Cursor 各做一遍 | 高 |
| Runbook 不可执行 | Markdown 写着，但没人照它做 | 中 |
| 新人 onboarding 慢 | 没有「照这个做」的标准包 | 中 |
| 合规要求出现 | 审计要看「流程文档 + 执行证据」 | 高·必须做 |

Skill 化不是「高级技巧」，是团队规模化的必要基建：5 个人的小队可以靠脑子，30 个人 + 多项目 + 要过审计时，没有 Skill 标准必乱。

## 本周逻辑：从认知到治理

Week 9 五节课的内在逻辑是一条链，最终接到 Week 10 的「受控 Agent」：

Why（范式认知） → Pack（标准结构） → Load（渐进加载） → Author（工程写作） → Govern（治理闭环）

Skill 是 Agent 的「行动手册」，Agent 是执行者。Week 10 起两者合体才是「能办事的 AI」，没有 Skill 标准的 Agent，必然走不远。
