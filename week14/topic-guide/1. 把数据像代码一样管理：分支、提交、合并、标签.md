# 导学 01：数据被覆盖着改，出错了还回得去吗？

## 一句话理解

给数据湖加一层版本管理，让数据改动可以拉分支隔离开发、提交留痕、打标签锚定版本、评审后合并、出错回退。

## 用生活打比方

这一周我们用「工厂改生产标准」来串起所有概念。

车间里每道工序都照一份现行作业标准干活：用哪批原料、按哪版配比、设备参数调到多少、成品怎么检验，全写在上面。规矩有两条，现行版只有一份挂在墙上，所有旧版本归档留着盖上作废章，谁都不许在现行版上直接涂改。

要改标准就另起一份修订稿，在试制线上按它做几批，检验和评审通过了才批准发布成新版本，再把现行版标识指到新版本上。发现新版本有问题，把标识指回上一版，车间立刻照旧版干活。

很多团队管数据的方式是直接在现行版上改，改完旧的那份就没了。这一讲讲怎么把工厂这套版本规矩搬到数据上。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **数据 PR** | 数据改动也走一遍评审再合并的流程：在分支上改完，跑一遍质量评测和影响范围检查，由另一个人审过才允许合进正式数据。 |
| **写时复制（copy-on-write）** | 拉分支时不真的复制数据，只记下和原来一样，等哪块数据被改了才单独存一份改动。所以拉分支几乎不花时间也不占空间。 |
| **时间旅行（time travel）** | 数据表自带的能力，可以读到这张表在过去某个时刻的样子。能查历史，但所有人共用同一条主线，没法各拉一份并行改再合并。 |
| **湖层分支管理（lakeFS）** | 加在数据湖之上的一层版本管理，让数据像代码一样能开分支、提交、合并、回退。它覆盖在存储层之上，用写时复制开分支几乎零成本，不用换掉现有的数据表。 |
| **数据表格式（Iceberg）** | 管单张数据表的字段演进和历史快照的那一层。它和湖层分支管理不是同一层，表就存在分支上，生产里同时用，不是二选一。 |
| **准入清单** | 上这套数据版本管理之前要逐项核对的判断项：团队里做数据的人有多少、数据每周改动频不频繁、近期有没有因为回滚困难吃过亏、有没有代码评审的工程习惯、监管是否要求提供数据版本审计。 |

## 避坑提醒

- **以为数据版本管理就是定期备份**：备份只能在出大事故时把整批数据捞回来，粒度粗、时延高，也没法在上面做开发。想在不影响线上的前提下改一批数据、验证完再合并，备份帮不上。
- **以为能查历史版本就等于能开分支**：查历史只是读到过去某一刻的样子，改动仍然只有一条主线，一个人改就影响所有人。分支是各拉一份并行改、互不干扰、评审后再合并。
- **以为上了数据分支就要换掉现有的数据表格式**：两者管的是不同层。表格式管单张表的字段演进和历史时刻，分支层管整个数据湖成套的隔离与合并，生产里同时用，表本身就存在分支上。当成二选一会白丢一半能力。
- **以为治理工具越先进就越该早上**：团队人少、数据改得少、也没吃过回滚的亏，硬上一套版本管理，维护它的成本会比业务本身还重。先逐项核对准入清单，多数项不达标就先把现有的历史查询能力用足。
- **以为数据改动不用评审**：代码改了公共接口要让调用方过一遍，数据改了同样会让下游算错、答错。数据合并前要有另一个人审，并且附上质量评测结果和影响范围。

## 一句话总结

> **真上了这套版本管理就把规矩立死：数据改动只在分支上做，合并必须有人审，每次发布都打标签，出错时直接指回上一个标签，不用连夜从备份里拼数据。**
