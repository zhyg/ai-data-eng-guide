# 导学 05：新版本怎么上，才不用全组守着屏幕？

## 一句话理解

每次改动都走完整发布流程，但流程本身分档放量、按预先定好的规则自动判断升档还是回退，出问题时只切换一次发布编号就能退回上一版。

## 用生活打比方

继续我们的工厂。新版标准批下来了，怎么推到全厂。

有的工厂等季度检修一次性换：攒了三个月的改动，配比、参数、工序一起换，换完全组守在线边上看有没有出事。真出了事，一堆改动混在一起，说不清是哪一项的问题。

正确的推法是分档：先一个班组试行，只看安全项和废品有没有立刻出问题；没问题扩到一条线，这时候样本够了，开始看质量指标；再扩到过半产能，连成本和交付一起看；最后全厂。每一档看什么、看多久、达到什么条件才升档，事先都写死，到点照规矩判，不靠谁的经验拍板。

要退也简单，把墙上的现行版标识指回上一版就行。整套配套材料本来就是按包管理的，指针一换，全厂立刻照旧包干活，不用把每份材料一张张换回去。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **三种发布模式（Big Bang / Blue-Green / Canary）** | 一次性全量替换风险最高，出事影响所有用户，回退代价也最大；两套环境整体切换能快速退回，但没有渐进过程，而且要多养一套环境；分档放量按小比例逐步扩大并自动判断是否继续，风险最低，是这类系统的首选。 |
| **四阶段 Canary** | 放量分成四档：先放一小部分流量，再扩大，再过半，最后全量。每一档要看的指标和最少观察时长都不一样。 |
| **决策输出（promote / hold / rollback）** | 自动判断每隔几分钟跑一次，只输出三种结果：升到下一档、维持当前档继续观察、立刻退回上一版。 |
| **基线对比（baseline）** | 判断退化不看绝对数值，而是拿新版本的指标和上一个稳定版本在同样时间窗内的指标比。用绝对数值判断的话，正常的流量波动和季节性变化都会被误判成退化。 |
| **最少观察期（min_observe）** | 每一档强制要求的最短观察时长，没到就算指标全绿也只能维持不升档。防止刚放量几分钟看着正常就草率往上推。 |
| **红线优先** | 只要碰到红线，任何一档都立刻退回，不等观察期走完，也不管其他指标有多好。质量指标变好不能抵消红线违规。 |
| **在线大模型评测门禁（LLM Eval Gate）** | 在放量过程中对真实流量抽样跑一次质量评测，把结果当成升档的准入条件。系统层面的延迟和错误率正常、答案质量却掉了的情况，只有这样才拦得住。 |

## 避坑提醒

- **以为攒成大版本一次上更稳**：改动越攒越多，出事的时候一堆改动混在一起，分不清是提示词、数据还是模型引起的，只能整批退回。每次改动小、发布频繁，反而出事也是小事，一眼能看出是哪次引入的。
- **以为灰度就是放上去跑够时间再看总体指标**：一档跑到底的做法风险更大。刚放量时样本量小，质量类指标噪声大，拿它做决策就是误判。要先看能一票否决的硬红线快速止血，流量上去样本够了再逐步把质量、业务、成本加进来。
- **以为判断退化就是拿指标跟固定阈值比**：固定阈值挡不住正常波动，容易在没问题的时候误报，也可能在真退化的时候因为阈值定得松而漏报。要跟上一个稳定版本在同样窗口的表现比。
- **以为回退就是把旧代码重新部署一遍**：重新部署要回退代码、重启服务、重建索引，慢的时候要按小时算。前面几讲把六类东西绑进一个发布编号，就是为了让回退变成切换一个指针的事。切完还要立刻做一次健康检查，避免退到一个本身就有问题的旧版本上。
- **以为升到全自动发布要重做基础设施**：多数团队停在代码能自动部署、数据和提示词还得手动改这一档。往上走需要的只是把数据分支、发布清单、影响分析、分档放量、回退引擎这几件已有的工具串成一条自动链，工具本身都是现成的。

## 一句话总结

> **把发布做成高频小步：分档放量、每档指标层层加码、红线一票否决、判断由程序按固定规则跑，回退靠切换发布编号并在同一个事务里完成，全程记审计日志并通知值班人。**
