# 导学 03：改一个字段之前，怎么知道会影响到谁？

## 一句话理解

把从原始文档到最终答案的每一段依赖关系都自动记录下来，改动之前先自动算出会影响哪些下游，并把这份影响报告卡在评审环节上。

## 用生活打比方

继续我们的工厂。有人要改一份上游的通用标准，比如某种原料的规格。

没有引用清单的工厂只能开会：把各条产线的负责人叫来，一个个问你们用不用这种原料。问一圈下来半天过去，还是会漏掉某条不常开的线，等那条线开工做出废品才发现。

有引用清单的工厂另一套做法：翻一下这份标准被哪些下游标准引用过、这些标准又用在哪些产线和检验项上，清单当场出来，还标出哪几条是关键工序。关键工序受影响的话，改动得由那道工序的负责人签字才能发。

上游不可能记得住谁在用自己的东西，所以这件事只能靠机器记账，不能靠开会通知。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **血缘** | 机器自动记录下来的依赖关系账本：某份数据是从哪来的、被谁加工过、又被谁用了。有了它才能反查一个答案的来源，或者正查一个改动的去向。 |
| **三个查询方向（Upstream / Downstream / Lateral）** | 向上查一个答案是从哪些数据来的，用于事后复盘和审计；向下查改了这个东西会影响谁，用于改动前评估；横向查还有谁在用同一个字段，用于协调改造。 |
| **五个层次（Source / Data / Index / Service / Action）** | 依赖关系要一路记到底才算全链路：原始文档和数据库表、加工好的数据资产、检索用的索引、对外提供服务的程序、以及自动程序做出的每一个动作。 |
| **列级血缘** | 记账要精确到单个字段，比如某张表里的状态字段被哪些下游用了。只记到表这一级，改一个字段时算出来的影响范围会准确度差很多。 |
| **影响分析** | 一条命令自动沿依赖关系一层层往下找出所有下游，按类型汇总，标出其中的高危项，并给出建议动作：需要协调改造还是通知一声就行。列进最高两级的下游必须先协调改造再上线。 |
| **变更类型（change_type）** | 改动的性质分三种，风险不同：会破坏原有约定的改动风险最高，只改名字的次之，只新增字段不动老字段的风险最低。风险等级要按这个来判。 |
| **血缘协议与动作扩展（OpenLineage / AgentActionFacet）** | 记账用的通用协议，各类调度和计算工具都能直接往里发事件，所以账本能跨工具打通。协议留了自定义字段的位置，把自动程序做的动作也记进去：它调了哪个工具、依据是哪些证据片段、改了哪些数据、用的哪个发布编号。 |
| **负责人（owner）** | 每一份数据资产上都要登记谁负责。影响报告里查出受影响的下游，能直接找到人，不然报告出来了也无人响应。 |

## 避坑提醒

- **以为血缘就是画一张关系图挂到文档里**：手画的图只在画完那一天是对的。数据流水线天天在改，几个月没人更新，那张图就成了废纸，还会误导人。账本必须由流水线运行时自动生成。
- **以为记到表这一级就够了**：只知道这张表影响那张表，改一个字段时算不出到底谁在用这个字段，影响范围会大量误报和漏报。记账要精确到字段。
- **以为工具装好了就等于用上了**：影响分析要靠人主动想起来去查的话，总会有人忘。它必须卡在数据改动的评审流程里自动运行，报告是评审的必读材料，高危项还要下游负责人签字。
- **以为账本只用记数据流动就够了**：现在自动程序也会动手改数据。不把它的动作记进账本，改坏了连是谁改的都查不出来，它依据哪些证据做的判断也追不回来。
- **以为查出受影响的下游就算完成了**：报告上列着一串系统名字却不知道找谁，出了故障没人响应，报告等于没出。每份数据资产都要有登记在册的负责人。

## 一句话总结

> **影响分析要做成自动跑的评审门禁：账本由流水线自动生成、精确到字段、覆盖到自动程序的动作，报告里的高危下游必须由对应负责人签字才能合并。**
