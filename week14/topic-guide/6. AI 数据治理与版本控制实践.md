# 导学 06：这一套治理制度，怎么才算真跑起来了？

## 一句话理解

这一节把前五讲落地成一条发布控制链路：由声明和真实产物编译出一份不可变的发布清单，过三道校验后注册入库，线上只保留一个生效的发布编号，之后的放量、回退、审计、合规材料都围绕这个编号展开。

## 用生活打比方

继续我们的工厂。前五讲把该想清楚的都想清楚了，这一讲讲怎么把它立成制度并跑通一遍。

编号不由人填，交给文管室按规则生成，同时把这一包材料整体算一个封口标记贴上。发下车间之前先过三道关：材料格式对不对、内容之间对不对得上、这个环境允不允许发。上生产还要多两道，人工审批和签章。

发出去的包归档就不许再动，墙上只留一个现行版标识。要退回上一版，就把标识指向旧包，台账上再追加一笔，写清是谁在什么时候因为什么退的。新包不销毁，标识上的次数也照常往上加。台账只增不改，只有那个现行版标识可以变。

试行期的观察单上要写明它是给哪一版做的。上一版的观察单不能拿来给新版放行，这是两回事。

外部审核要材料的时候不再临时拼，从归档的包一路往下核对，材料齐不齐、封口标记对不对得上，一次生成。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **候选声明、生成器与不可变清单（spec → generator → manifest）** | 人写的那份声明只是一次发布的申请，写明这次打算用哪些东西。生成器据此从各处读取真实产物、补上代码版本和时间戳、逐项算摘要、生成编号，输出一份不可变的清单。编号和摘要都由生成器产出，人不许手填，生成之后不再修改。 |
| **原子指针与代次（generation）** | 线上只保存一个当前生效的发布编号。发布就是把这个编号换成新的，回退就是换回旧的，六类东西跟着一起切，服务也读同一份清单，所以数据和索引不会一个新一个旧。代次是这个编号被切换过多少次的计数，回退时它继续往上加，每次切换都在记录里留下痕迹。 |
| **政策校验（policy）** | 检查跨字段的规则和环境规则，通过就允许发布，不通过要给出拒绝原因。比如六类东西必须都齐、索引必须绑在同一份数据版本上、评测和业务指标必须达标、至少要有一条红线，生产环境还额外要求人工审批和签名。 |
| **四重校验与前驱链** | 注册入库之前依次核对格式、摘要、签名、政策，再核对它接在哪一次发布后面。同一个编号配同一份摘要重复提交视为重试，结果一样；同一个编号配不同内容则直接报冲突。 |
| **爆炸半径（blast radius）** | 发布前算出这次改动会牵动的范围。做法是把清单里的各类组件映射成对应的发布动作，数据和模型这类改动优先级最高，其余次之，重复项去掉。 |
| **追加型事件表（release_rollout_event / release_audit_event）** | 放量决策和人的操作各自记在一张只能往后追加的表里，写进去就不能改。发布记录本身也不可改，整个体系里唯一允许更新的就是那个当前生效编号。 |

## 避坑提醒

- **以为发布就是把写好的配置文件存进仓库**：人写的那份只是申请，里面既没有编号也没有摘要。工具要补上代码版本、时间戳，把引用到的产物逐个读出来算摘要，再组装成清单。少了这一步，清单和它声称锁定的东西对不上，后面所有校验都是空的。
- **以为内容一样算出来的摘要就一定一样**：字段换个顺序、多一个空格、编码方式不同，算出的摘要就变了。校验时会误报被篡改，真被改了反而可能因为对不上而无法定位。算摘要前必须先统一写法。
- **以为格式校验能顺带管住业务规则**：格式校验只负责结构对不对、字段类型和日期时间写法合不合法。六类组件齐不齐、索引有没有绑在同一份数据上、指标有没有达标，这些是另一层的事。混在一起写，失败时分不清是格式问题还是规则问题。
- **以为回退就是把新版本删掉或者把计数改回去**：删记录和改计数会破坏历史，事后查不出这次事故发生过什么。回退要保留新版本的记录，只把生效编号指回旧版，并且追加一条写明原因和触发者的事件。
- **以为放量观测数据可以拿来给别的版本放行**：观测数据属于特定的那一次发布。放量决策要先核对观测数据里的发布编号和清单摘要，对不上就拒绝，否则会拿上一版表现良好的数据把新版放上去。

## 一句话总结

> **发布链路要做到清单不可改、事件只追加、只有生效编号可切换，编号和摘要一律由工具生成，放量决策必须先核对归属再按红线优先判断，最后从归档产物递归核对生成合规证据包。**
