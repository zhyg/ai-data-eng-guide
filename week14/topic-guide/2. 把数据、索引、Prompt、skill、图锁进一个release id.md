# 导学 02：同一份代码，为什么今天和昨天答得不一样？

## 一句话理解

一次发布要把数据、索引、提示词、模型、技能和图这六类会变的东西同时锁进一个发布编号，拿这一个编号就能完整还原当时的运行现场。

## 用生活打比方

继续我们的工厂。发布一版新标准，发下车间的从来不只是一张作业标准。配比表、检验标准、记录表单、操作培训材料要一起下发，缺一份车间就干不成活。

所以工厂的做法是把这些配套材料打成一个版本包，给包编一个号。车间照包干活，检验照包判合格，出了问题查这个包，回退也是整包退。谁要是把标准发下去、配比表还留着上个月的旧版，做出来的东西一定不对，但两份材料单看又都是正常的，很难查。

包上还要封口盖章，避免有人抽走或替换里面某一页。原料要附合格证，说明它是哪家哪批、检验过什么项目。

传统软件发布只锁代码就够了。AI 系统同一份代码配不同的数据、提示词、模型，行为会差很远，所以要锁的是这一整包。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **发布编号（release_id）** | 一次发布的唯一名字，也是排查问题时的主键。用户报一个回答有问题，拿这个编号就能查出当时用的是哪份数据、哪版提示词、哪个模型。 |
| **发布清单（release manifest）** | 一份记录这次发布锁了哪些东西的文件，逐项写清数据、索引、提示词、模型、技能、图各自的版本，外加这次的评测结果、业务指标、灰度与回滚策略、审批人。 |
| **原子绑定** | 六类会变的东西必须在同一次发布里一起锁定、一起生效、一起回退，不允许各自单独改版本。分开管的话，两个东西各自看起来都正常，凑在一起的行为却是错的。 |
| **快照钉死（pin）** | 模型要写到带日期的具体版本，不写会随时间滚动指向新版本的那种通用名字。用通用名字的话，供应商悄悄换了模型，你的系统行为变了却查不出原因。 |
| **摘要（digest）** | 把清单内容整体算出的一串固定长度字符。内容动一个字，这串字符就变，用来证明清单没被人改过。 |
| **模型卡与系统卡（Model Card / System Card）** | 模型供应商随版本一起发布的说明材料，写清这个模型能干什么、有哪些限制、有什么风险、做过哪些评测。发布时随清单一起留档。 |
| **制品签名** | 给清单、索引、模型这些产物加上一层加密签名，之后任何人都能验证它从签名那一刻起没被动过。 |
| **自动回滚条件（auto_rollback_on）** | 在清单里预先写明哪些指标退化到什么程度就自动回退，比如出现个人信息泄露就零容忍立刻回退，答案忠实度掉到线以下也回退。 |

## 避坑提醒

- **以为数据、提示词、模型各自记好版本就够了**：各自记版本只能回答单个东西的历史，回答不了某一刻它们的组合是什么。追查一个具体回答时，四五个东西各有各的版本记录，谁也说不清那一刻是哪种搭配，只能靠人拼。
- **以为模型名字写通用的那种就行**：通用名字会随时间指向不同的模型版本。供应商换了权重，你的代码、数据、提示词一个字没动，答案却变了，排查时会一直往自己的改动上找原因。
- **以为清单可以手写维护**：手写一定会漏字段、写错版本号。清单要由工具自动去各处收集当前版本、自动跑一遍发布前评测、自动算整体摘要，工程师只负责按一下发布。
- **以为清单做出来存进仓库就算完成了**：清单必须被真正用起来才有价值。服务启动时要读它，链路追踪的记录里要带上发布编号，评测要锁定它跑，审计要导出它，回退要靠它切换。少接一处，出事时就会对不上号。
- **以为锁定版本就等于证明没被人动过**：锁定只说明当时绑了哪些版本，说明不了这些产物中途有没有被替换。要额外给清单和模型加签名、把模型钉到带日期的版本、随发布留存模型说明材料。

## 一句话总结

> **发布编号要能当主键用：由工具自动生成清单、算整体摘要、加签名，并且让服务、追踪、评测、审计、回退五处都真正读它。**
