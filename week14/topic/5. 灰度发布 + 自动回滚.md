# 5. 灰度发布 + 自动回滚

## 核心问题

前 4 节建好了「版本 + 影响 + 合规」，但客户面对的不是 manifest，是 production 流量。这一讲让「AI 系统上线」从「祈祷」升级为「工程」。

真实场景：太多团队搞「季度大版本」——攒三个月的改动，prompt、数据、模型一次性全换，选个周五晚上全量上线，然后全组守在屏幕前祈祷别出事。这不叫工程，这叫赌博。

关键判断：正确做法反过来——每一次变更，哪怕只改一个 prompt 字符，都走完整发布流程，但流程要快、要自动：Canary 5% → 25% → 50% → 100%，每一档机器自动看指标决定升还是回，全程半小时、零人工守候。

本节四件事：

1. 为什么「高频低风险」比「低频高风险」是 10 倍的工程进步
2. 3 种发布模式怎么选，4 阶段 Canary 每阶段看什么指标
3. Canary 自动决策框架 + 秒级回滚引擎，半夜 3 点也能自己 promote / rollback
4. 2026 工具：Argo Rollouts / Flagger / OpenFeature + 在线 LLM 评测门禁

## Release often, release small

传统 SRE 有句老话：release often, release small——越频繁反而越安全，因为每次改动小，出事也是小事，一眼能看出是哪次改的。AI 团队却常常反着来：憋大版本、一次改一堆，出事就是大事，还根本分不清是 prompt 的锅、数据的锅还是模型的锅。

| 模式 | 做法 | 风险 | 成本 / 代价 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| Big Bang（反） | 一次性 100% 替换，「季度大版本」 | 极高 | 回滚代价极高 | 反模式，避免 |
| Blue-Green | 新版本部署完后 100% 切 | 中（无渐进） | 2x 基础设施 | 基础设施类 |
| Canary（推荐） | 5 → 25 → 50 → 100% 渐进，自动决策升档 | 最低 | 与流量成正比 | AI 系统首选 |

## 4 阶段 Canary

一刀切的「Canary 跑 1 小时」反而风险更大，必须分阶段精细化。

| 阶段 | 流量 | 观察时长 | 关键指标 | 升档条件 |
| :--- | :--- | :--- | :--- | :--- |
| Stage 1 | 5% | 15-30 min | 红线（P0 / 合规 / 严重错） | 无 P0 + 无合规违反 |
| Stage 2 | 25% | 1-2 h | + 质量（faithfulness） | 指标不显著退化 |
| Stage 3 | 50% | 2-4 h | + 业务指标 + 成本 | SLO 全部 pass |
| Stage 4 | 100% | N/A | 持续监控 | 全量发布完成 |

关键判断：每阶段的关键指标是层层加码的——5% 时只看红线（快速止血），越往上看得越全（质量、业务、成本）。为什么不一上来全看？因为 5% 流量样本太小，质量指标噪声大，拿它做决策就是误判。先看能一票否决的硬红线，流量上去了、样本够了，再看软指标。这个顺序是 Canary 精细化的精髓。

## Canary 自动决策框架

不靠人工守，半夜 3 点也能跑。每 5 分钟跑一次，输出 promote / hold / rollback 三种决策。判定逻辑按优先级排列：

1. **采集两组指标**：当前 canary 版本和上一个稳定版（baseline）各取 15 分钟窗口的指标。
2. **红线优先**：任何 stage 触碰红线立即 rollback，不等观察期，理由里带上具体违反项。
3. **阶段特定检查**：按阶段配置逐项比对，且用「相对 baseline 的退化幅度」而不是绝对阈值。以 `_rate` 结尾的指标（越低越好）超出 baseline 允许倍数就回滚；质量类指标（越高越好）跌破 baseline 允许比例就回滚。用相对对比是为了避免季节性和流量波动造成误判。
4. **最少观察期**：阶段开始至今不足配置的最小观察时长就返回 hold，防止「5 分钟一切正常」就草率升档。
5. **全部通过才 promote**：升到下一档。

阶段配置按 stage 分别定义：Stage 1 只查红线，Stage 4 查所有 SLO，逐级精细化。

## 3 种回滚机制：速度差 100 倍

| 机制 | 具体做法 | 速度 | 依赖 |
| :--- | :--- | :--- | :--- |
| 重部署回滚 | 回退代码 + 重启 + 重建索引 | 小时级 | 基础设施 |
| 配置切换 | 改配置 + 滚动更新 | 分钟级 | 配置中心 |
| release_id 切换 | 切 router 指向旧 release_id | < 60 秒 | Week 14 整套基础 |

这 100 倍的差距怎么来的：重部署要重建一大堆东西，慢；配置切换快一点；而 release_id 切换之所以能做到 60 秒内，是因为前 13 周把 6 类对象都原子绑进了一个 release_id——回滚时只需要把 router 的指针从新 release 切回旧 release，一个指针的事。

Week 14 前面那些绑定、血缘、manifest，看着琐碎，但它们全部是为了这一刻：出事时你能在客户还没骂完之前一键切回去。一个中等体量的 C 端服务，P0 故障每分钟损失常在 $500 到 $5,000，4.7 秒和 3 小时的差就是几十万的差。

## 秒级回滚引擎

Week 14 整周工程的最终输出：一份 release_id 锁定 = 一次原子切换。引擎的执行要点：

1. **加载目标 manifest 并校验状态**：目标 release 必须是 archived 或 stable，不能切到一个从未健康过的版本。
2. **6 类对象在一个事务里切换**：事务内把流量 router 指向目标 release，data 切到目标的 lakeFS tag、index 指向目标的 pgvector 快照、prompt / model / skill_pack / graph 全部一起切。部分成功等于大事故，所以必须同一事务。
3. **失效缓存**：服务配置和 release 指针相关缓存全部 invalidate。
4. **10 秒健康观察窗**：切换后立刻验证错误率低于阈值，防止「切到一个本身就有问题的旧版本」。
5. **写审计日志**：记录事件类型、从哪个版本到哪个版本、原因、触发者、耗时，事后可复盘。
6. **通知 oncall**：回滚必须让人知道，即使是机器自动触发的。

典型输出：回滚在 4.7 秒内完成。对比没治理团队的 30 分钟到 3 小时，这就是「工程治理 ROI」最直观的数字。

## AI 系统发布成熟度的 5 级

| 等级 | 具体表现 | 回滚耗时 | 事故频率 |
| :--- | :--- | :--- | :--- |
| L0 · 手动 | 手敲命令 / 改配置 | 小时级 | 月 1-3 次 |
| L1 · CI/CD | 代码自动部署，数据 / Prompt 手动 | 30 分钟 | 月 1-2 次 |
| L2 · 蓝绿 | 完整版本切换，无渐进 | 分钟级 | 季 1-2 次 |
| L3 · Canary 半自动 | 分阶段但人工守 | < 10 分钟 | 半年 1 次 |
| L4 · Canary 全自动 | 5-100% 全自动决策 | < 1 分钟 | 年 1 次 |

大部分团队都在 L1 到 L2 之间：代码能自动部署了，但数据、Prompt 还是手动改、手动回滚。从 L2 升到 L4 不需要重做基础设施，需要的只是把 Week 14 这五节的工具（lakeFS + manifest + 影响分析 + Canary + 回滚引擎）组装起来。工具都是现成的，差的是「把它们串成一条自动链」的决心。

## 完整发布工作流

Week 1-14 所有工程能力收口成「按一下 release，剩下全自动」：

PR Merge（lakeFS + Git，评测通过）→ Generate（release manifest 自动生成）→ Approve（影响分析 + 多人审）→ Canary（4 阶段灰度自动决策）→ Stable（100% + 白皮书自动生成）

关键判断：工程师在 PR 里点一下 merge，后面全自动——lakeFS 合分支、生成 manifest、跑影响分析、多人审批、4 阶段 Canary 自动决策、100% 后自动生成合规白皮书。从「点 release」到「100% 流量稳定」，全程 60-120 分钟、零人工守候。

## Industry Signals（2026）

工具早已开箱即用，2026 关键不是工具，是建立「频繁低风险发布」的工程文化。

| 来源 | 做法 | 给你的启示 |
| :--- | :--- | :--- |
| Google SRE | Canary + 自动决策 + 错误预算 | 本周所有理论的基础，直接照搬 |
| Argo Rollouts / Flagger | K8s 上把渐进发布做成 GitOps | 改个 yaml，系统自动 Canary，别手写 |
| OpenFeature (CNCF) / LaunchDarkly | 特征开关标准 + 灰度 SaaS | 不想自建灰度的团队，直接用 |
| 在线 LLM 评测门禁 | Braintrust / LangSmith 把评测卡进发布 | 2026 新增：Canary 阶段跑在线评测当门禁 |

2026 有个 AI 专属的新东西值得注意：把「在线评测」直接卡进 Canary 门禁。传统 Canary 看的是延迟、错误率这些系统指标，但 AI 系统真正的风险是「答得对不对」，这是个软指标。所以现在成熟团队在 Stage 2/3 会挂一个在线的 faithfulness 抽样评测，质量掉了自动回滚，这是 Week 11 评测和 Week 14 发布合体的最新形态。工具都现成了，难的从来不是工具，是敢不敢把「季度大版本」的旧习惯改掉。

走完这一周，Copilot 第一次真正具备了「持续演进 + 监管可审 + 事故可控」的工程级治理能力，这就是「实验室 demo」和「能上生产、能卖钱的产品」之间那道最难跨的坎。

## Recap

- release often, release small：高频小改动比低频大版本安全一个量级，Canary 是 AI 系统的首选发布模式。
- 4 阶段 Canary 的指标层层加码：5% 只看能一票否决的红线，流量上去样本够了再看质量、业务、成本。
- 自动决策的优先级是红线 → 相对 baseline 的退化比对 → 最少观察期，用相对对比避免波动误判。
- 回滚速度差 100 倍的根因就是原子绑定：切一个 release_id 指针 vs 重建一堆东西。
- 回滚必须 6 类对象同事务切换 + 10 秒健康校验 + 全程审计 + 通知 oncall。
- 从 L2 升 L4 不用重做基础设施，把本周五节的工具串成一条自动链就行。
