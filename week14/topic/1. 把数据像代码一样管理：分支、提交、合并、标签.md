# 1. 把数据像代码一样管理：分支、提交、合并、标签

## 核心问题

前 13 周把 RAG、Agent、评测、可观测、GraphRAG 全建出来了，但还差最后一根工程主线：业务说「昨天回答没问题、今天突然不对」，你能在 5 秒内回到「昨天那套数据 + 索引 + Prompt + 模型」吗？

这一讲用 lakeFS 把 Git 模型搬到数据上，让数据变更像代码一样可 PR、可回滚、可灰度。

真实场景：一份产品手册被覆盖式更新，当晚 RAG 就开始答错，客户投诉一片。团队想回滚，可数据是覆盖式更新的，旧版本根本没留，只能连夜从三天前的备份里捞、手工拼，折腾到凌晨四点。

关键判断：代码要是这么管（不开分支、直接改主干、出错没法 revert）早被开除了。可数据，大部分团队至今还这么干。

本节四件事：

1. 为什么 2026 年产线数据还在用「覆盖式更新 + 备份」是一笔工程债
2. 数据治理三代演进，大部分团队卡在「快照」这一代，差在哪
3. Git 模型怎么 1:1 搬到数据：Branch / Commit / Tag / Merge / Revert
4. lakeFS 和 Iceberg / Polaris 是「组合」不是「替代」，2026 的目录格局怎么选

## 数据治理的下一步不是「更精细的备份」

传统数据治理这些年走了三步：数据备份 → 数据快照（Iceberg time travel）→ 数据资产化（Week 6）。但有一道根本的工程鸿沟一直没填：代码那套「开分支、隔离开发、PR 合并、一键回滚」的能力，数据一直没有。

| 能力 | 代码世界（早就有） | 数据世界（以前没有） | lakeFS 补齐（2024 起） |
| :--- | :--- | :--- | :--- |
| 开发隔离 | `git branch` 开发 | 覆盖式更新 | 数据也能开分支 |
| 变更评审 | PR review 合并 | 一改影响所有人 | 数据 PR + Merge |
| 回滚 | `git revert` 回滚 | 出错只能捞备份 | 数据 revert 秒级 |
| 版本锚定 | tag 锚定版本 | 版本靠文件名 | tag = release 锚点 |
| 心理成本 | 出错零压力 | 出错就是事故 | 数据变更零压力 |

## 数据版本治理的 3 代演进

| 代际 | 核心能力 | 解决什么 | 局限 |
| :--- | :--- | :--- | :--- |
| G1 · 备份 | 定期复制全量数据 | 出大事故能恢复 | 粒度粗 / 时延高 / 不能开发 |
| G2 · 快照 | Iceberg / Delta time travel | 可读历史时刻数据 | 主分支唯一 / 一改影响所有人 |
| G3 · 分支 | lakeFS Git-like branches | 并行开发 + 隔离 + 合并 | 需要工程化 PR 流程配合 |

关键判断：升到 G3 不用换掉你的 Iceberg，也不用换 S3。lakeFS 是「覆盖在 S3/HDFS 之上」的一层元数据，用 COW（copy-on-write）开分支几乎零成本、零复制。托管版 lakeFS Cloud 每月几百美金起、自托管开源免费。它是加一层，不是推倒重来。

## Git 模型搬到数据：概念 1:1 对应

| 概念组 | 对应到数据 |
| :--- | :--- |
| Branch · 分支 | main 生产数据、staging 预上线、experiment 实验；分支间互相隔离，改动不影响别人 |
| Commit + Tag | commit 是一次数据变更；tag 是可寻址版本号（如 `release-2026-05-18`），作为 release manifest 锚点，不可变 + 可回滚 |
| Merge + Revert | merge 把分支合并，revert 撤销某次变更，配套 PR review，保留完整历史，可审计 + 可追责 |

这套映射最大的价值是「零学习成本」。团队里只要有人会用 Git，他就会用 lakeFS，同样的心智模型：开分支干活、提交、发 PR、审、合、错了 revert。工程师不用重新学一套黑话，这是它能落地的关键。

## lakeFS 数据分支工作流：数据 PR 长什么样

从开分支改数据，到评测、影响分析、合并、秒回滚，一条命令链走完：

开分支（不碰生产）→ 在分支上更新数据（Dagster / Spark / Python）→ 提交并把数据变更绑到代码 PR → 在分支上跑评测 + 影响分析 → PR 合并（两人审 + 自动回归）→ 出问题秒回滚

各步骤的工程要点：

| 步骤 | 要点 |
| :--- | :--- |
| `branch create` | COW 开分支不复制数据，立刻可用，几乎零成本、零等待 |
| `commit --metadata git_pr=PR-142` | 把数据变更和代码 PR 绑一起，这是本周治理的核心 |
| `eval run --branch` | 在分支上跑评测，不影响生产用户，Week 11 的评测搬到分支上做 |
| `merge --reviewer` | 数据变更走「两人审」，和代码 PR 同等严肃 |
| `revert` | 出错切回上一个 commit，用户感受不到中间过程 |

评测输出示例：faithfulness 0.91 vs 0.89（+0.02）通过，受影响 chunks 1,247。

## lakeFS ≠ Iceberg：不是替代是组合

很多工程师以为「上 lakeFS 就要换掉 Iceberg」，错，它们各管一层。

| 层级 | 解决什么 | 工具代表 | 在 OmniSupport 里 |
| :--- | :--- | :--- | :--- |
| Storage | 存原始字节 | S3 / GCS / HDFS | 存所有 Parquet / JSON / 文档 |
| Table Format | 表 schema / 快照 / 演进 | Iceberg / Delta / Hudi | silver / gold 表用 Iceberg |
| Repo / Branch | 跨表跨格式的分支隔离 | lakeFS | main / staging / experiment |
| Catalog | 统一目录 + REST + 多引擎 | Polaris / Unity / Nessie | 2026 新格局 |

关键判断：Iceberg 管「表级快照 + Schema 演进」，lakeFS 管「整个湖的 git 层 + 跨表分支隔离」，两者是不同层，生产里并存——Iceberg 表就存在 lakeFS 分支里。把它们当成「二选一」，就白白丢了一半能力。这是本周第一个要纠正的直觉。

## Industry Signals（2026）

Data as Code 已是工程基线，所有主流 Lakehouse 都内嵌「数据分支」，这不再是先进做法，是准入门槛。

| 方案 | 定位 | 2026 现状 / 建议 |
| :--- | :--- | :--- |
| lakeFS | Git for Data（湖层分支） | 开源、S3 兼容，数据 PR / Merge / Revert 首选 |
| Apache Polaris | Iceberg REST 目录 | 2026-02 升为 Apache 顶级项目，多引擎互通 |
| Unity Catalog (OSS) | 治理 + 血缘 + 目录 | Databricks 开源捐 Linux 基金会，上 Databricks 首选 |
| Project Nessie | Iceberg 原生分支 | 全 Iceberg 团队的 git-like 分支引擎 |
| Snowflake Git 集成 | 仓库内建 Git | 全 Snowflake 团队用 |

2026 的大变化是开放目录标准打通了：Polaris 今年 2 月升为顶级项目、Unity Catalog 也开源了，两者都实现 Iceberg REST API，Flink / Spark / Trino / StarRocks 一份目录到处用。建议：湖层分支用 lakeFS，目录用 Polaris 或 Unity（看你在不在 Databricks 生态），别再自己造目录胶水，这层 2026 已经卷完了。

## 上不上 lakeFS 的 5 个判断标准

为痛点而上，不为先进而上。这是准入清单，符合 3 项以上再上。

| 判断项 | 具体问题 | 阈值 | 不达标就别上 |
| :--- | :--- | :--- | :--- |
| 团队规模 | 数据 / AI 工程师数量 | > 5 | 太少没必要工程化 |
| 变更频率 | 数据更新 PR / 周 | > 5 | 低频用 commit / script 够 |
| 事故痛点 | 「回滚困难 / 一改全断」事故 | 近半年 > 3 次 | 不痛就不用上 |
| 工程能力 | Git PR 文化 / CI 经验 | 齐全 | 没基础 lakeFS 也用不起来 |
| 监管压力 | 需提供「数据版本审计」 | 是 | 是 = 必须，否 = 加分 |

用法：符合 3 项以上上 lakeFS；只符合 2 项先用 Iceberg time travel 撑半年再看；不到 2 项别折腾。太多团队痛点还没到就急着上一堆治理工具，结果工具比业务还重，这叫过度工程，老板一算 ROI 就砍了。

## Recap

- 数据治理的下一步不是更精细的备份，是把 Git 模型（branch / commit / merge / tag / revert）完整搬到数据上。
- 三代演进：备份 → 快照 → 分支。大部分团队卡在 G2 快照，升 G3 只是在 S3 上加一层元数据，不用换 Lakehouse。
- lakeFS 的落地关键是零学习成本：会 Git 就会用它，心智模型完全一致。
- 数据 PR 的核心是把数据变更用 metadata 绑到代码 PR，并在分支上跑评测和影响分析，不碰生产用户。
- lakeFS 和 Iceberg 是不同层、生产里并存，Iceberg 表就存在 lakeFS 分支里，别当成二选一。
- 上不上看痛点清单，符合 3 项以上再上，不痛别折腾。
