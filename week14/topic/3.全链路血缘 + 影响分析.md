# 3. 全链路血缘 + 影响分析

## 核心问题

Week 6 / 12 学过血缘，这一讲升级到「AI 全链路影响分析」：改字段之前先看「会炸到哪 47 个服务」。

真实场景：上游 PM 周一开会说「下周准备给 ticket.status 加个枚举值」，听着人畜无害。没血缘的团队拉个会评估三小时、挨个问五个组、结果上线后还是漏了某个下游 dashboard，当天报表全空。有血缘的团队，工具 30 秒渲染出影响图：9 个 RAG 服务 + 23 个 dashboard + 5 个 Agent Skill 受影响，其中 8 个是 P0/P1，直接 @ 到对应负责人。

关键判断：血缘要从「事后查」升级成「改之前秒看下游影响」。

本节四件事：

1. 为什么「上游开会通知下游」这套在 AI 时代根本行不通
2. 血缘的 3 个查询方向（向上 / 向下 / 横向）各回答什么工程问题
3. AI 时代血缘的 5 个层次，从原始文档一路打通到 Agent 动作
4. 2026 血缘现状：OpenLineage 进 CNCF、列级血缘成标配、把 Agent 动作也纳进来

## Prevent, not inspect

90% 的 AI 重大事故都是同一个公式：

「上游改了一个东西」+「下游没人知道」= 事故

这个公式没法用「上游开会通知下游」来破，因为上游根本不可能知道下游有谁在用、用了哪个字段。真正的解法只有一个：建立机器可读的全链路血缘 + 自动影响分析。上游改任何东西之前，工具自动生成「影响报告」，把受影响的下游 service / dashboard / Agent / Skill 全列出来。

### 3 个查询方向

| 方向 | 回答的问题 | 路径 | 解决什么 | 实现 | 产出 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Upstream · 向上 | 「这答案是哪来的」 | 从 Agent / Service → 数据源 | 故障复盘 / 合规审计 | OpenLineage 反向遍历 | data → answer 全链 |
| Downstream · 向下 | 「改了它影响谁」 | 从字段 → 所有下游消费 | 变更影响分析 | OpenLineage 正向遍历 | 受影响下游清单 |
| Lateral · 横向 | 「还有谁用这字段」 | 一个字段的同代消费者 | 协调改造 / 共享 | DataHub 共用查询 | 同代消费者清单 |

## AI 时代血缘的 5 个层次

传统血缘只到「数据」层，AI 时代还要往下打通到 Service 和 Agent 动作。

| 层级 | 记录什么 | 工具 | 关键 ID |
| :--- | :--- | :--- | :--- |
| Source | 原始文档 / API / 数据库表 | OpenLineage | doc_id / table_id |
| Data | 数据资产（Iceberg / Lakehouse） | OpenLineage + DataHub | asset_id（列级） |
| Index | 向量库 / ES / 图 | Custom span | index_release_id |
| Service | RAG / Tool / Skill | OTel + Week 12 | service_name |
| Action | Agent 决策动作 | Custom + OpenLineage | trace_id |

关键判断：5 层要用同一个图谱平台（DataHub / OpenMetadata）串起来，改任何一层都能秒级反查「上下文 + 影响」。2026 特别强调 Data 层要做到「列级血缘」——不是「这张表影响那张表」，而是「tickets.status 这一个字段影响哪些下游」，粒度差一级，影响分析准确度差十倍。

## 影响分析的自动化实现

一条命令，递归 5 层下游，按类型聚合，标出 P0/P1 高危。实现要点：

1. **递归找所有下游消费者**：调用图谱平台客户端，深度设为 5，消费者类型覆盖 dataset、dashboard、rag_service、agent_skill、ml_model、dbt_model。跨多层血缘自动遍历，不用工程师手查。
2. **按变更类型算风险等级**：`breaking` 变更下游本身是 P0 就判 P0、否则 P1；`rename` 变更看依赖里是否引用了具体字段路径，是则 P1、否则 P2；`additive` 变更一律 P3。变更类型分级复用 Week 8 的契约演进概念。
3. **出报告**：报告含总下游数、高危清单（P0/P1）、以及推荐动作——breaking 是 `coordinate`（必须协调），其他是 `notify`（通知即可）。
4. **每项都带 owner**：受影响的每个下游都记录负责人，能直接路由到人。

典型输出：总下游 47 个（rag_service 9、dashboard 23、agent_skill 5），高危 8 个（P0 两个、P1 六个），推荐动作 coordinate。

CI 集成是关键：数据 PR 一提交自动跑，Reviewer 看着「影响范围」决定批不批。这套让「上游变更」从「开会问一圈」变成「看一份报告」，决策速度提升 10 倍。

## 把 Agent 动作也纳入血缘

传统血缘只追「数据流」，AI 时代必须追到「Agent 改了哪些数据」。做法是扩展 OpenLineage 的 facet 机制：

| 要点 | 说明 |
| :--- | :--- |
| AgentActionFacet | OpenLineage 的标准扩展点，在标准协议之上加 AI 专用字段：action_type（rag / tool / skill）、tool_name、release_id、approver |
| inputs = chunk_ids | 把 Agent 决策的「依据」（证据 chunk）纳入血缘，上游一改就知道哪些决策受影响 |
| outputs = 被改的数据 | Agent 改了哪些数据，下游报表 / 视图能反向追溯 |
| 装饰器自动注入 | 用装饰器包住工具函数自动发 lineage 事件，业务代码不动，复用 Week 12 的 instrumentor 模式 |
| run_id = trace_id | 血缘事件的 run 直接复用 Week 12 的 trace_id，两套体系对得上号 |

一次完整血缘链路：用户 query → chunks → tool_call → ticket 变更

2026 意义：Agent 会「动手改数据」，不把动作纳入血缘，出了事你连「谁改的」都查不到。

## Industry Signals（2026）

协议 + 平台双层：OpenLineage 是协议，DataHub / OpenMetadata 是图谱平台。

| 工具 | 层级 | 特点 | 适用 |
| :--- | :--- | :--- | :--- |
| OpenLineage | 协议（CNCF） | 事件级、跨工具通用、列级血缘 | 所有 AI 项目都该用 |
| Marquez | 基础后端 | OpenLineage 参考实现 | 小团队 / 自托管入门 |
| DataHub | 图谱平台 | LinkedIn 出品 + 影响分析 UI | 中大型企业 |
| OpenMetadata | 图谱平台 | 更现代 + 强 UI | 中型团队 / 自托管首选 |
| Monte Carlo / Bigeye | 数据可观测 | 血缘 + 异常告警 + 影响范围 | 大企业 / 要产品级 |

2026 推荐：OpenLineage 协议（已进 CNCF，Airflow / dbt / Spark / Flink 全原生支持）+ OpenMetadata 平台，开源、跨工具、可控，是中小团队最优组合，零 license 费。商业数据可观测（Monte Carlo 一类）年费常在 $50,000 以上，预算紧就用开源栈。选型别纠结：协议跟 OpenLineage、平台看规模挑一个图谱库，千万别手画 Confluence 血缘图，那玩意儿画完第二天就过期了。

## 影响分析驱动的 PR 工作流

类比：代码 PR 必跑 unit test，数据 PR 必跑影响分析。

Create（数据 PR，标记变更字段）→ Analyze（影响分析，输出受影响清单）→ Route（按 owner 路由，通知下游）→ Review（高危需下游批，P0/P1 owner）→ Merge（合并 + 通知，写 release manifest）

关键判断：这条工作流把「上游单方面改」变成「按影响范围协调」，这是数据治理从混乱到有序最关键的一步。规则很硬：影响范围里只要出现 P0/P1 下游，这个 PR 就必须由那个下游的 owner 点头才能合并。就像代码里改了公共接口必须让调用方 review 一样。

## Anti-Patterns：血缘 + 影响分析的 5 个反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 手动维护血缘 | 画 Confluence 图 | 永远过期 | OpenLineage 自动生成 |
| 只到表级血缘 | 不到字段级 | 改字段不知影响谁 | 列级血缘 + DataHub |
| 影响分析不接 PR | 工具有但人忘了用 | 事故照旧 | CI 强制运行 + 报告必读 |
| Agent 动作不入血缘 | 只追数据流 | Agent 改的数据查不到 | 扩展 OpenLineage facet |
| 血缘没 Owner | 看到下游不知找谁 | P0 故障无人响应 | 每个 asset 必含 owner |

踩坑提醒：太多「血缘项目」轰轰烈烈启动、半年后无疾而终，复盘下来几乎都是同两个原因——一是手动维护（画个图挂 Confluence，三个月没人更新就成了废纸），二是有工具但不接 PR（人总会忘记去查）。血缘必须「自动生成 + 强制卡在 PR 上」，靠人的自觉这事一定黄。

## Recap

- 血缘的最大价值不是事后查，是改东西之前秒看下游影响，事故公式「上游改了 + 下游没人知道」只能靠机器可读血缘来破。
- 三个查询方向各有用途：向上做复盘和审计，向下做变更影响，横向做协调改造。
- AI 时代血缘要打通 5 层（Source / Data / Index / Service / Action），Data 层必须做到列级，粒度差一级准确度差十倍。
- 影响分析要自动递归 5 层、按变更类型分级 P0-P3、每项带 owner，并强制卡在数据 PR 的 CI 里。
- Agent 动作要用 OpenLineage 自定义 facet 纳入血缘，inputs 记证据 chunk、outputs 记被改数据。
- 选型：协议跟 OpenLineage（已进 CNCF），平台按规模选 OpenMetadata 或 DataHub，不要手画血缘图。
