# 2. 把数据、索引、Prompt、skill、图锁进一个 release id

## 核心问题

Week 8 讲过 release manifest，Week 9-13 每周加一类对象，这一讲收口：AI 系统的一次发布，必须把 6 类对象锁进一个 release_id。

真实场景：线上一条回答出了问题，合规部门追过来问「这条回答，当时用的是哪份数据、哪个 Prompt、哪个模型？」负责的工程师当场卡壳——数据是运维改的、Prompt 是他自己前天调的、模型上周升过、索引又是另一个人重建的，四五个东西各自有各自的版本，谁也说不清那一刻它们是什么组合。查了整整两天才拼出现场。

关键判断：客户报任何一个 bad case，你只要拿这一个 ID，整个「现场」瞬间完整恢复。这才叫 production-grade。

本节四件事：

1. 为什么「分别版本数据 / 索引 / Prompt / 模型」在生产里几乎一定踩坑
2. release manifest 的 6 大对象 + 9 大段落，每段对应前面某一周
3. release_id 命名规范 + 自动生成器，为什么绝不能手写
4. 2026 供应链可信：model / system cards + 快照钉死 + Sigstore 签名溯源

## 一次发布 = 6 类对象的原子绑定

传统软件 release = git tag = 一个 commit hash，代码定了行为就定了。AI 系统不一样：同一份代码，换一份数据、换一个 Prompt 版本、换一个模型快照，行为可以天差地别。所以 AI 的一次发布，必须把这 6 类对象一起锁死。

data + index + prompt + model + skill + graph = ONE release_id

| 组 | 对象 | 锚定方式 | 影响 | 来源周 |
| :--- | :--- | :--- | :--- | :--- |
| DATA · 数据 + 索引 | 数据、向量 / ES 索引 | lakeFS commit / tag，pgvector / ES snapshot | 召回内容 | Week 6 / 14 L1 |
| INFERENCE · 推理 | Prompt、模型 | prompt v3.2.1（Jinja）、model 快照钉死 | 生成行为 | Week 8 |
| AGENT · 智能体 | Skill、图 | skill_pack v1.4、graph schema v1.2 | 执行 + 归纳 | Week 9 / 13 |

三个问题对应三组对象：「用了哪份数据」「用了哪个推理」「用了哪些工艺 / 关系」。

## 统一 release manifest：9 大段落

release_id 是这一切的「主键」，拿这一个 ID 整个现场完整恢复。manifest 的 9 段把前 13 周一网打尽：

| 段 | 内容 | 对应周次 |
| :--- | :--- | :--- |
| 1. data | lakeFS tag + Iceberg snapshots | Week 6 / 7 / 14 |
| 2. index | pgvector snapshot + chunk 策略版本 | Week 7 / 8 |
| 3. prompt | rag_answer、intent_router 各自版本号 | Week 8 |
| 4. model | generator + reranker，写到日期版本 | 快照钉死 |
| 5. skill_pack | 版本 + digest | Week 9 |
| 6. graph_release | schema 版本 + 实体数量 | Week 13 |
| 7. eval | 评测集版本 + faithfulness 基线值 | Week 11 |
| 8. business_slo | 首次解决率、CSAT 等业务指标 | Week 10 |
| 9. rollout | 灰度策略 + auto_rollback_on 条件 | Week 14 L5 |

metadata 段还带 `released_by` 和 `approved_by`，上线必须「代码 + 数据 + 合规」三方审，不能单人决策。

关键要点：

- **release_id 是主键**：拿这一个 ID，整个现场完整恢复。
- **model 快照钉死**：别写 `gpt-4o` 这种滚动别名，要写到日期版本（如 `openai/gpt-4o-2024-08-06`、`BAAI/bge-reranker-v2-m3@2024-06`），否则供应商悄悄换权重你都不知道。
- **auto_rollback_on 显式声明退化条件**：既含 PII（合规红线，阈值 0），也含 faithfulness（质量底线，如 < 0.86）。

## 供应链可信（2026 治理新维度）

不只「绑了什么」，还要「证明没被动过」。模型 / 数据也是「依赖」，也需要 cards + 签名 + 溯源，跟软件供应链一个道理。

| 能力 | 做什么 | 2026 工具 / 标准 |
| :--- | :--- | :--- |
| Model / System Card | 模型能力、限制、风险、评测随 release 附上 | Anthropic / OpenAI system card，已成发布标配 |
| 快照钉死（pin） | 模型写到日期版本，禁用滚动别名 | claude-opus-4-8 / gpt-4o-2024-08-06 |
| 制品签名 | 给 manifest / 索引 / 模型加密签名防篡改 | Sigstore / cosign，ed25519 |
| 供应链清单 | AI 版 SBOM：列全数据源、模型、依赖 | SLSA + AI-BOM，监管开始要 |

以前我们只关心「绑了哪些版本」，现在监管和安全还要你证明「这些版本没被人偷偷改过」。道理跟软件供应链一样——npm 装个包都要查签名了，模型、数据这种更要命的依赖不该裸奔。

落地判断：manifest 生成后用 cosign 签一下、模型一律 pin 到日期快照、每个 release 附上 model card。这三件小事，2026 做合规审计时能省掉一大堆扯皮。

## release_id 命名规范

看似小事，决定 6 个月后你能不能查得动。

| 策略 | 示例 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 纯时间戳 | 2026-05-18T15-00-00Z | 简单 + 唯一 | 人读不出「是什么」 |
| SemVer | v3.2.1 | 人友好 | 不可单调递增 / 易冲突 |
| Hybrid（推荐） | rag-v2026.05.18-001 | 可读 + 可解析 + 单调 | 需要工程约定 |
| UUID | rel-a3f4b2c1d5e6 | 完全独立 | 不可读 / 不可排序 |

直接抄 Hybrid：「服务名-v日期-序号」。既人友好（一眼看出是哪天哪个服务的第几个版本），又机器友好（可解析、可单调排序）。别用纯 UUID，半年后出事故，面对一屏 `rel-a3f4b2c1` 根本不知道哪个在前哪个在后。

## Release Manifest 自动生成器：绝不要手写

手写必漏、必错版本。生成器的职责是自动收集 6 类对象、自动跑评测、自动打 tag。

生成流程与要点：

1. **release_id 自动生成**：服务名 + 当天日期 + 当天自增序号（三位补零），单调递增 + 唯一，永远不会「同一天两个版本」撞名。
2. **collect_\* 系列自动收集**：data / index / prompt / model / skill_pack / graph_release 各有一个采集函数，不靠人工填，工程师只需一条发布命令。
3. **发布前自动跑评测**：评测在生成 manifest 时执行，结果 inline 写进 manifest，Week 11 的评测强制接入发布链路。
4. **business_slo 和 rollout 策略**：分别从当前指标和默认策略模板加载。
5. **整体 digest**：把 spec 段按 key 排序序列化后取 sha256 写进 metadata。任何字段一动 hash 就变，这就是「不可篡改证明」。
6. **annotated git tag**：让 manifest 在 Git 里也可寻址，配合 cosign 签名形成溯源闭环。

对外只暴露一条发布命令，参数是服务名和审批人列表，输出是 release_id 和已打好的 Git tag。

## Release Manifest 的 5 类消费方

做出来没人用等于没做。manifest 不能只是一个躺在仓库里的文件，必须被这 5 类下游实际消费：

| 消费方 | 具体怎么用 | Week 关联 |
| :--- | :--- | :--- |
| Runtime Service | 启动时加载 manifest，设 release_id 环境变量 | Week 8 |
| Observability | span 自动带 release_id，Phoenix / Jaeger 可查 | Week 12 |
| Evaluation | PR 触发评测时锁定 manifest 版本 | Week 11 |
| Audit | 合规审计直接导出 manifest + trace | Week 14 L4 |
| Rollback | 一键切换到指定 release_id | Week 14 L5 |

关键判断：这 5 类消费方在生产里同时用，release_id 才真正成为「AI 系统的核心 ID」。少接一类，manifest 就废一半：不接 runtime，它管不住线上；不接 observability，出事故还是对不上号；不接 audit，合规来查还是手忙脚乱。

## Industry Signals（2026）

不管叫 manifest、artifact 还是 lockfile，核心都是「多类对象原子绑定 + 签名溯源」。

| 来源 | 做法 | 给你的启示 |
| :--- | :--- | :--- |
| Anthropic / OpenAI | 生产 pin 具体 model snapshot + system card | 原子绑定的概念基础，快照必须钉死 |
| MLflow / W&B Artifacts | 模型 + 数据 + 评测绑成 immutable artifact | 传统 ML 的原子绑定先驱，直接复用 |
| Sigstore / SLSA | 制品签名 + 供应链等级 | 2026 给 manifest / 模型加签名，防篡改 |
| Spotify Backstage | service / data 配置作可审计 YAML | 开源服务治理事实标准，同构 |

不用纠结「自研 manifest 还是用现成的」，概念都在收敛：一次发布 = 多类对象一次锁定 + 可签名 + 可回滚。传统 ML 时代 MLflow / W&B 早就把「模型 + 数据 + 评测」绑一起了，你要做的只是把 AI 时代新增的 Prompt、Skill、图、合规红线也塞进同一个包。

## Recap

- AI 和传统软件的根本差异：同样的代码 + 不同的数据 / Prompt / 模型，行为可以完全不同，所以必须 6 类对象原子绑定。
- manifest 的 9 段对应 Week 1-13 的全部工程对象，release_id 是整个系统的主键。
- 模型必须 pin 到日期快照，禁用滚动别名，否则供应商换权重你无感。
- 2026 新增供应链维度：model card + cosign 签名 + AI-BOM，证明版本没被动过。
- 命名用 Hybrid（服务名-v日期-序号），可读且可单调排序。
- manifest 必须自动生成 + 整体 digest 防篡改，并被 runtime / 可观测 / 评测 / 审计 / 回滚五类下游真实消费。
