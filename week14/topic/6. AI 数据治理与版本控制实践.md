# 6. AI 数据治理与版本控制实践

## 核心目标

从整门课程的视角收口：前 13 周做出的数据湖仓、语义层、RAG、Skill、受控 Agent、评测、可观测、GraphRAG，每个模块都能独立跑，但生产事故往往是整体系统的稳定性问题。

Week 14 的核心不是开发新算法，而是建立一个**发布控制面**：锁定六类可变对象，在变更前后做影响分析和分阶段观察，通过灰度决策让出问题时只需调整一个指针，并保留完整的证据链。

关键判断：发布的输入不是手写的 release_id，而是一份 spec 和一组真实制品。generator 负责收集并哈希，再经过 schema、integrity、policy 三重校验。之后是影响分析、灰度决策，最终回滚、审计和交付证据，全部围绕同一个 release_id 展开。

## 整体架构

spec 声明 + 真实制品 → generator 收集并解析 digest → schema / integrity / policy 三重校验 → 生成不可变 manifest → 影响分析算 blast radius → 注册到 registry 并设置环境指针 → 4 阶段灰度决策 → promote 或 rollback（切指针）→ 审计链 + 合规证据包 + 血缘事件

### 原子指针

这是本周最关键的设计：六类版本不是各自独立改配置，而是先写入不可变的 manifest，线上只保存一个激活的 release_id。切换这个指针即完成发布和回滚。服务也读同一份 manifest，从而保证数据和索引的一致性。

## 发布声明：Release Manifest 的候选 YAML

Week 14 的发布声明用一份 YAML 明确「一次发布绑定了什么」。注意它是**候选声明**，不是发布结果。

| 段 | 内容 | 作用 |
| :--- | :--- | :--- |
| 六类组件 | data、index、prompt、model、skills、graph | 运行时依赖 |
| quality | eval（Week 11）+ business_slo（Week 10 指标） | 准入依据 |
| rollout | 灰度档位 + 回滚阈值 | 发布策略 |
| governance | 审批、数据分级 | 防止发布时版本不一致的风险 |
| digest / release_id | 由 generator 生成 | 不可手工填写 |

各段的硬性约束：

| 组件 | 约束 |
| :--- | :--- |
| data | 同时锁定 lakeFS tag 和 Iceberg snapshots |
| index | index 的 release_id 必须与 data 的 release_id 匹配，避免索引和数据错配 |
| model | snapshot 必须使用固定标识，生产策略拒绝 latest 一类滚动别名 |
| rollout | 必须分为 5 / 25 / 50 / 100 四档 |
| 红线 | PII 与安全通过率列为红线 |
| governance.required | 必须接入影响分析和真实审批系统 |

## 发布链路的核心模块

### schema 校验

`release/` 下有一个统一的 JSON Schema 验证入口。封装很简单：先校验 schema 本身，再用 Draft 2020-12 Validator 校验实例。schema 本身刻意做薄，只负责结构正确性，并检查 date-time 一类格式。

设计原则：结构逻辑与业务逻辑分开，避免失败时问题混杂。

### digest 与签名

digest 模块负责稳定性哈希、制品摘要和可选签名。输入是文件、manifest payload 和签名密钥；输出是 SHA-256 摘要、HMAC 签名及验证结果。

处理分四步：canonical_json → manifest payload → 最终 manifest → 验证。

canonical_json 的关键约束：键排序、紧凑分隔符、禁止非 ASCII 转义、统一编码成 UTF-8。这样避免因键顺序或空格不同导致同一内容算出不同哈希。

### policy 校验

policy 模块定义跨字段和环境级别的发布政策，输出是「允许发布」或「拒绝的原因」。先查通用规则，再检查生产环境的额外规则，测试环境可以放行验证。

| 规则类别 | 具体要求 |
| :--- | :--- |
| 通用 · 组件齐全 | 六个组件必须完整 |
| 通用 · 版本一致 | 索引需绑定同一数据版本 |
| 通用 · 质量门禁 | Week 11 的 eval 和 Week 12 的 SLO 需通过阈值 |
| 通用 · 灰度 | 灰度阶段档位相对固定 |
| 通用 · 红线 | 至少有一条红线 |
| 生产额外 | 人工审批 + 强制签名 |

### generator

generator 负责把声明式的 spec 编译成不可变的 manifest 文件。输入是 spec、环境、操作者、Git SHA 及其他可选参数，输出是 JSON。

流程：解析 → 分配 release_id → 解析制品 digest → 组装 → schema 与 policy 校验。

要点：入口不是简单地保存 YAML，而是补充实际的补丁信息（Git SHA、时间戳等）；解析制品路径时确认未超出项目根目录，再读取文件内容算 digest。

### 影响分析

`tools/impact_analysis.py` 在发布前计算 blast radius。输入是 manifest 字典或候选声明。

它不重复血缘平台的工作，而是把组件映射到发布动作：data 和 model 这类关键组件优先级最高，prompt、index、skills、graph 次之。所有影响项通过集合去重。

### 灰度决策

`rollout/canary.py` 的设计原则是「优先级而非公式」，判定顺序：

1. 验证 observation 是否属于此次 release（release_id + manifest digest 都要对得上）
2. 检查红线区指标
3. 安全指标不可见、样本量不足或观察时长不足 → 回滚
4. 最后阶段才比较 gate 和 baseline 的输出

输出不是一句话，而是包含原因代码、样本量、观察窗口和指标的可审计决策。

### 回滚

`rollout/rollback.py` 是原子回滚命令行。输入当前 target、active 和 reason，输出新的 active release_id 和 generation。

回滚不是把 generation 改回 1 或删除新版本，而是把指针从新版本切回旧版本，generation 继续递增，事故记录保持完整。

### registry

`release/registry` 负责事务型操作，管理发布注册表和环境指针：

1. 四重校验：schema、digest、signature、policy
2. 校验前驱链
3. 幂等：相同 release_id + 相同 digest 可以重试；内容不同则抛冲突
4. 灰度决策入库时同样校验 release_id 和 manifest digest，并用数据库 advisory lock 保证阶段按顺序执行

## 数据模型扩展

`infra/` 下的 SQL 脚本定义 Week 14 新增的表：

| 表 | 作用 | 可变性 |
| :--- | :--- | :--- |
| `governance_release_manifest` | 存储不可变发布实体 | 不可修改 |
| release 环境 pointer 表 | 只指向当前环境激活的 release | 只有 pointer 允许更新 |
| `release_rollout_event` | 追加灰度决策 | 追加，不可改 |
| `release_audit_event` | 追加人和动作 | 追加，不可改 |

设计原则：历史事件和 manifest 不可更改，只有 pointer 允许更新。migrations 文档里加了迁移门禁，用专门的迁移脚本执行 DB 迁移。

## 合规证据与血缘

### 合规证据包

`risk/` 模块下的 generator 自动生成合规证据包，而不是手工编写。它从真实制品递归查找所有 `manifest_digest`，并确认文件存在且 digest 指纹一致。

产物是证据包 JSON 和发布白皮书，其中包含 SHA-256 字节摘要。

### OpenLineage 发布血缘

OpenLineage 把一次发布表达为一个事件，记录组件的血缘链路。代码把六类组件转换为不同的 dataset namespace，分别区分 data、index、prompt、model、skills、graph。

发布事件可以写入本地文件，也可以 POST 到 OpenLineage 后端，不依赖官方 SDK。

## 契约测试与本地验证

测试分三类：契约测试、集成测试、单元测试，共 5 个测试文件全部通过。

实验流程：

1. 启动 PostgreSQL
2. 跑全套测试（契约 + 集成 + 单元），确认 5 项全通过
3. 设置产物输出目录，以模块方式运行 generator，生成第一份不可变 manifest，输出 release_id、manifest digest 和校验结果
4. 拆解 manifest，查看 release_id、环境、`created_at`、Git SHA、六个组件（data / index / prompt / model / skills / graph）和 manifest digest
5. 篡改检测：不修改源文件，在内存中深拷贝并重新计算整个 payload 的哈希；计算出的 digest 与 manifest 中保存的不一致就判定被篡改，标记 blocked 并给出「manifest digest 不匹配」的理由
6. 发布前跑影响分析，查看受影响的组件清单
7. 灰度验证（见下表）
8. 创建独立 PostgreSQL 实例并建 schema，注册并发布第一版，generation = 1，拿到注册 ID 和 rollout event ID
9. 生成第二版（序号 002），验证第一版的灰度观测文件不能用于放行第二版——灰度决策携带 release_id 和 manifest digest，版本对不上直接拒绝
10. 触发事故回滚：不是把 generation 改回 1 或删除第二版，而是把指针从第二版切回第一版，generation 增至 3
11. 用 SQL 验证指针和审计哈希链：事件类型包含 register、decision、rollback；发布记录显示 01 → 02 是灰度通过，02 → 01 是灰度红线
12. 一键生成合规证据包和发布白皮书，检查内容与 SHA-256 摘要
13. 发出发布血缘事件，检查所有运行产物

### 灰度决策的三个验证用例

| 用例 | 指标情况 | 决策 | 原因 |
| :--- | :--- | :--- | :--- |
| 5% 正常放量 | 指标正常，观测 20 分钟 | promote | 全部检查通过 |
| 质量更好但触红线 | faithfulness 提升到 0.92、延迟降到 900 ms，但 PII 泄露率 0.01 | rollback | 平均质量再好也不能抵消红线合规问题 |
| 红线专项 | PII 泄露容忍度 0，实际 0.01 | rollback | 原因代码明确指出红线被违反 |

这三个用例说明的核心设计：红线是一票否决项，优先级高于任何平均质量指标。

## Recap

- Week 14 交付的是一个发布控制面，不是新算法：锁六类对象、变更前算影响、分阶段观察、出事切指针、全程留证据。
- 原子指针是核心设计：manifest 不可变，线上只有一个激活的 release_id，发布和回滚都是切指针。
- release_id 和 digest 只能由 generator 生成，YAML 是候选声明而非发布结果。
- canonical JSON（键排序 + 紧凑分隔符 + UTF-8）是稳定哈希的前提，也是篡改检测能成立的基础。
- 校验分三层且职责分离：schema 只管结构，policy 管跨字段和环境规则，registry 再加 digest、签名和前驱链。
- 灰度决策先验证 observation 归属，再查红线，样本量或观察时长不足一律回滚；红线一票否决，质量提升不能抵消。
- 数据库层面 manifest 和事件表只追加、不可改，只有环境 pointer 可更新，回滚靠 generation 递增记录完整事故轨迹。
