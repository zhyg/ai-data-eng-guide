# 6. OpenTelemetry 与 Tracing 全链路可观测性实践

## 核心目标

将前 5 节的理论落地为可运行的代码：把请求、失败、告警、事故复盘及回归测试形成闭环。从业务请求开始，生成 trace 和 Span，通过 Collector 收集数据，使用 Phoenix 定位问题，通过 SLO 判断服务目标的影响，最后生成 insights 和事后分析报告。

核心思想：可观测性不仅限于查看日志，而是要让每次请求都能定位复盘，并转化为测试用例，从而阻止问题版本的再次发布。

## 整体架构

真实的 trace 主链：

RAG API → Tool API → Agent Copilot → OTel Collector → Phoenix

跨服务请求通过 W3C TraceContext 在 HTTP header 中传播 trace 上下文，并通过 X-Trace-Id 方便查看。同一请求跨 RAG API、Tool API 和 Agent 时不会断裂，所有失败都归属于同一个 trace_id。

## 基础设施层

### OTel Collector

位于业务服务和 Phoenix 中间，是遥测数据的中转站而不是监控平台。

配置要点：
- **接收**：监听 gRPC 和 HTTP 的 OTLP
- **处理**：batch 限制防突发 Span 打爆 + 减少网络开销，resource 统一注入环境字段，内存限制
- **导出**：转发给 Phoenix（或 Prometheus / 其他后端）

应用直接连接 OTel Collector，它决定将数据发送给哪个后端。更换后端时，业务代码无需修改协议。

### Phoenix

存储和展示 AI 调用链，包括 Span 属性、状态和错误等信息。重点不是看彩色条形图，而是识别哪些请求失败了、失败发生在哪一层、使用的是哪个 release_id、返回了多少条证据。

### Docker Compose 编排

通过同一个 compose 网络连接 PostgreSQL、MinIO、Phoenix、OTel Collector、RAG API 和 Tool API。容器内的 localhost 永远指向容器自身，因此 API 需使用服务名 otel-collector。版本锁定以避免冲突。

## 公共埋点能力

集中于可观测性 runtime 文件夹下，提供 4 个核心模块：

### privacy.py（数据安全）

在进入 trace 前对数据进行安全处理：
- 覆盖邮箱、手机号、身份证号等敏感信息
- 对常见的 SQL 文件进行脱敏处理
- 先将数据压缩成单行再进行脱敏，最后限制为 200 个字符

### setup.py（OTel 初始化）

初始化 OpenTelemetry：创建 Tracer，设置采样频率和 Span 限额，配置 OTLP 导出以及统一的资源信息（otel_service_name、endpoint、project 等）。

### trace.py（轻量封装）

提供统一的 Trace 和 Span 上下文管理器，业务代码只需关注 Span 名称。统一完成：创建 Span、设置 OpenInference 类型、写入受控属性、捕获异常并设置状态。业务方只需注入一个组件即可完成数据采集，无需使用复杂的 OTel SDK。

### init（公共入口）

作为稳定的公共入口来隔离内部文件组织。即使未来需要替换 exporter 或拆分 providers 文件，也只需在此处修改，不影响其他调用方。

## 业务服务埋点

### RAG API

- main 文件配置遥测并自动 instrument FastAPI，响应时将 trace_id 返回给调用方
- Router 中包含 RAG query、intent route 等埋点
- 检索与 RAG 是一条链路，从 query 检索到 RAG 的过程都在检索层
- 审计 Audit 也是链路的一部分

### Tool API

- main 中进行 OTel 初始化，在 HTTP context 中提取 trace_id
- 工单查询和创建动作设置生成 Span，只记录参数摘要并埋点

### Agent Copilot

- 将 Week 10 的受控 Agent 逐段暴露为可观测性的 Span
- tools 的 fallback 中，每次尝试都独立记录一个 Span，而不是仅保留最终结果

## 可观测视图：5 类面板

面板分为：总览、质量、性能、成本和错误。目标是帮助从系统问题逐步下沉到具体的 trace 和 Span。

## SLO 与告警

- SLO 目标覆盖可用性、性能、引用覆盖等具体数值
- 通过 tail metrics 中的 window 计算 SLI 的 availability 和 burn rate
- 计算后生成可行动的告警内容，包括错误上下文
- 告警规则和 Runbook 链接将 SLO 决策转化为 Prometheus 风格的系统消费格式
- Fast Burn（1h 内错误率超 14.4 倍预算且持续 5 分钟触发 P1）
- Slow Burn（6h 内错误率超 6 倍预算且持续 1 小时触发 P2）
- PII Leak（1 分钟内增量 > 0 直接触发 P0）

## Bad Case 闭环

### 自动收集与转化

Bad Case 从故障窗口触发告警 → 生成复盘 → 将坏的案例转换为 Week 11 的反例库 → 自动回归评测 → 确认 git 门禁通过。

### 事故报告契约

incident 和 SLO report 的 schema 契约确保系统监控和报告标准一致，必须包含：incident ID、severity、trace_id、root cause、泛答案、期望答案和期望证据等字段。

### render_postmortem

模型输出包括 summary、trace events、root cause、fix、lessons 和 action items。每个异常都需附带状态、延迟和证据数。

### 闭环编排

run_closure 将 SLO、insight、Postmortem 和 Bad Case 与 Evolution Runner 串联成可执行的编排器。demo_full 创建 devbox，通过 W3C context 调用 RAG 和 tool，执行高风险 HITL 路径，形成跨服务调用链路进行验证，并通过 Phoenix REST API 反查 trace。

## 契约测试

## Recap

- 整体架构通过 W3C TraceContext 保证跨服务请求的 trace_id 不断裂。
- 公共埋点能力（privacy / setup / trace）集中管理，业务方只需注入一个组件。
- OTel Collector 作为中转站，更换后端业务代码无需修改。
- 从采集 → 跟踪失败 → 面板展示 → 告警 → Bad Case 沉淀 → 回归闭环，形成完整的可观测性闭环。
- 契约测试确保可观测性基础设施满足工程标准。
