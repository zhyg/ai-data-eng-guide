# 2. Span 级追踪设计

## 核心问题

上一讲把 OTel 接进来了，但接进来不等于用对。一个团队的 trace，OTel 接得挺好，可一打开 Phoenix 时间轴，8 个 span 全叫 "process"、"call"、"run"，属性里就两个字段 input/output，各塞了几千字符。这叫「伪可观测」：看着有 trace，实际等于没有。

span 设计得好不好，决定了你排障是 5 分钟还是 5 小时。

## Span 设计的 3 大原则

每一条都有现成的类比，照着抄就行。

| 原则 | 要求 | 类比 |
| :--- | :--- | :--- |
| Naming 命名 | 用「层.动作.策略」如 rag.retrieve.hybrid，不写 process / call / run，可按前缀过滤 | 好函数命名 |
| Attributes 属性 | 关键参数/结果/决策，不存原文（爆字段），不存 PII（合规），加 _count / _ms 后缀 | 好日志字段 |
| Status 状态 | OK / ERROR + 业务级 error_type（如 insufficient_evidence / tool_timeout / low_confidence） | HTTP status |

关键判断：状态码最被低估。别只有 OK/ERROR，要带业务级 error_type。出错时一眼知道「为什么错」，而不是只知道「错了」。这一个字段能省半小时翻日志。

## 好 span vs 坏 span

好的 span = 「读起来像故事」，名字 + 关键属性一眼说清这一步干了什么。

**坏 span：**
- name = "process"
- attr = {input, output}，各塞几千字符
- 点开看半天不知干嘛

**好 span：**
- name = "rag.retrieve.hybrid"
- strategy=vec+bm25+rrf
- vec_hits=47 / bm25=39 / fused=53
- filter=vip / elapsed=187ms
- 一眼读出：用了什么策略、各路返回多少、过滤了什么、花了多久

土办法：照「好函数名」的标准来——layer.action.strategy，让运维半夜被叫醒、迷迷糊糊扫一眼时间轴就能读懂。

## RAG 全链路 6 段标准 span

经验证的「故障定位最小集」，少一段就有盲区。6 段合起来能回答：慢在哪？召回准不准？重排丢多少？生成花多少 token？审计写了没？

| Span Name | 父子 | 关键属性 | 定位什么 |
| :--- | :--- | :--- | :--- |
| rag.query | 根 | user_id / query / tenant / role | 整体请求入口 |
| rag.intent_route | 子 | intent / confidence / route | 走 RAG 还是 Tool |
| rag.retrieve.hybrid | 子 | top_k / vec_hits / bm25_hits / fused | 召回阶段 |
| rag.rerank.cross | 子 | model / kept / threshold / dropped | 精排阶段 |
| rag.generate.llm | 子 | model / in_tokens / out_tokens / temp | 生成阶段 + 成本 |
| rag.audit.write | 子 | trace_id / release_id / evidence_count | 审计完整性（接 Week 6 血缘） |

为什么是 6 段不是 5 段也不是 10 段？正好对齐 Week 8 的「检索+重排+生成」流水线 + Week 10 的审计。多了是过度埋点（贵、慢），少了就有盲区（出事查不到）。

## Tool / HITL 的 span

工具慢 / 失败 / 路由错、HITL 卡死，没 span 全是黑盒。

| Span Name | 关键属性 | 回答什么问题 |
| :--- | :--- | :--- |
| tool.call.{name} | tool.name / args_hash / result_code / elapsed | 工具调用快不快 / 对不对 |
| tool.fallback | level / primary_error / final_level | 降级链走到第几级 |
| tool.idempotent_check | idem_key / hit / args_hash | 命中幂等缓存了吗 |
| hitl.request | risk_category / approval_layer / sla_min | HITL 触发原因 |
| hitl.wait | notified_at / waited_ms | 审批人响应快不快 |
| hitl.decided | approver / decision / reason | 审批结果 + 责任人 |

这 6 类 span 把「Agent 决策 + 工具执行 + 人工介入」完整记下来。不管是本地工具还是 MCP server 暴露的工具，都走同一套 span。和 Week 10 的工具契约 audit_fields 完全对应。

## Span 属性的「预算」

一个 span 建议 < 20 个属性 + 总字节 < 2KB，否则上报存储成本爆炸。

标准模式：

- **_preview + _len 组合**：如 `prompt_preview`（前 200 字）+ `prompt_len`，既能 review 又不爆字段
- **top_3_chunk_ids 只存 ID 不存原文**：复盘时按 ID 再去拉原文
- **artifact_url 指向对象存储**：hot trace + cold storage 标准模式，trace 表只放热数据，大块内容沉到 S3
- Phoenix / LangSmith / Arize 都支持 link-to-artifact，点一下跳详情

踩坑教训：早期把整段 prompt 塞 span，trace 后端存储一个月涨了 5 倍；换成 preview+artifact 后存储省了约 80%、查询快一倍。

## 一条完整 trace 在时间轴上的样子

```
rag.query              0-2400ms    根 span
  intent_route         0-50ms      意图分类
  retrieve.hybrid      50-250ms    双路召回
  rerank.cross         250-450ms   精排门禁
  llm.generate         450-2300ms  生成 + tokens
```

一眼就知道 2.4 秒里，1850 毫秒花在了 llm.generate 上。要优化延迟，别瞎调召回，先动生成（换模型 / 减 max_tokens / 流式输出）。数据告诉你瓶颈在哪，才不会把一周时间花在错的地方。

## 反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 名字通用 | name = "process" / "call" | 时间轴看不出在干嘛 | 「层.动作.策略」命名 |
| 存原文 | attr = {full_prompt: "..."} | 上传慢 + 存储贵 | _preview + _len + artifact_url |
| 有 PII | 把 customer.phone 存属性 | 合规违规（监管事件） | redact 脱敏后再 set |
| 少关键状态 | 只有 OK / ERROR | 错了不知道为什么 | 加业务级 error_type |
| 不分层 | 所有 span 平级 | 看不出依赖关系 | 父子嵌套，按层组织 |

踩坑提醒：「有 PII」这条是真出过事的。有团队图省事把整个用户 message 塞进 span 属性，里面有身份证号、手机号，结果 trace 数据进了第三方可观测 SaaS，直接变成一次数据出境 + PII 泄露的合规事件。set_attribute 之前先过一遍 redact，没有商量。

## Industry Signals（2026）

| 来源 | 能力 | 工程含义 |
| :--- | :--- | :--- |
| OpenInference spec | RAG / LLM / Tool 各类 span 的标准命名 | 跨工具通用，直接遵守 |
| Anthropic / OpenAI | 原生 trace 响应里自带 reasoning span + tool_use span | 开箱即用，不用自己 wrap |
| Phoenix（Arize） | OpenInference span 专用 LLM 可视化 | prompt/response 一键展开，token 成本立现 |
| OTel GenAI semconv | gen_ai.* 统一 span/attribute 命名 | 2026 仍 experimental，但方向是它 |

span 字段直接照 OpenInference spec 抄，将来无缝迁到 OTel GenAI 官方约定。别自己拍脑袋定一套字段名，换个可观测平台全部对不上、历史数据全废。

## Recap

- span 设计 3 大原则：命名（层.动作.策略）/ 属性（关键参数+结果+决策）/ 状态（OK/ERROR + 业务 error_type）。
- RAG 6 段 span 是故障定位最小集，对齐 Week 8 流水线 + Week 10 审计。
- Tool / HITL 6 类 span 把 Agent 决策和人工介入完整记下来，消除黑盒。
- 属性有预算（< 20 个、< 2KB），用 _preview + _len + artifact_url 标准模式。
- set_attribute 之前先过 redact，PII 零容忍。
