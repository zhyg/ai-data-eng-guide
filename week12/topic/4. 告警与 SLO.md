# 4. 告警与 SLO

## 核心问题

大多数团队花 80% 时间建 dashboard、10% 设告警、0% 想 SLO，顺序全反了。

真实场景：凌晨 3 点，手机连续炸了 50 条告警，爬起来一看全是误报，高峰期 P99 自然高一点就触发了阈值。工程师烦到直接把告警静音。结果第二天起来，真正的故障（一个工具大面积超时）已经悄悄发了 5 个小时，客户投诉一片。

这就是「告警疲劳」：告警太多太吵，人就麻木，真出事反而被淹没。问题的根不在「告警写得不够多」，在于大多数团队设告警靠「经验拍数字」。SLO + 错误预算，才是告警真正的科学基础。

## 阈值告警 vs SLO 告警

「P99 > 2s 就告警」是 2018 年的做法，在 LLM 系统里 = 疯狂误报。

| 维度 | 阈值告警（错） | SLO 告警（对） |
| :--- | :--- | :--- |
| 基础 | 某指标 > X 就告警 | 某 SLO 的错误预算消耗 > Y% |
| 抗噪能力 | 弱（任何一次抖动都叫） | 强（看累积消耗） |
| 可量化 | "P99 > 2s" | "99% < 3s，当前达成 99.2%" |
| 与业务挂钩 | 没有 | SLO 直接对应业务可接受度 |
| 告警密度 | 高（误报多） | 低（只在真有问题时） |
| 可解释 | 不可 | "还剩 35% 错误预算" |

关键判断：告警的本质不是「指标超了某个数」，是「错误预算正在以异常的速度被烧掉」。同样 P99=4s，高峰期偶尔一下是正常波动（在预算内）；持续半小时狂烧预算，才是真应急。

## SLO 三要素

Google SRE 给出的正确答案：

| 概念 | 含义 | 关键 |
| :--- | :--- | :--- |
| SLO 目标 | 业务可接受的范围，如「99% 请求 P99 < 3s」 | 从业务诉求来，不是越高越好 |
| 错误预算 | 100% − SLO，如 1% 可以失败 | 是你能「花」的额度 |
| 燃烧速度 | 错误预算被消耗多快 | 速度超标 = 真应急，正常速度 = 不告警 |

## Copilot 的 5 类核心 SLO

模糊的 SLO（「答得快一点」）不能驱动告警，必须是可测量的数字。

| SLO 类别 | SLI | SLO 目标 | 错误预算 | 优先级 |
| :--- | :--- | :--- | :--- | :--- |
| 可用性 | 成功响应率 | 99.5% | 0.5%/月 = 3.6h | P1 |
| 延迟 | P99 端到端 | < 3s | 5%/月超时 | P2 |
| 质量 | Faithfulness（在线抽样） | > 0.85 | 15%/月低质 | P2 |
| 合规 | PII 泄露次数 | = 0 | 零容忍 | P0 |
| 成本 | 日均 cost/query | < $0.05 | 20%/月预算 | P3 |

注意合规这行：PII 泄露 SLO 是「= 0、零容忍、P0」，和其他可以「花预算」的 SLO 本质不同。可用性可以容忍 0.5% 失败，PII 泄露一次就得电话叫醒所有人。

## 错误预算燃烧速度告警

Google SRE 经典做法，快慢双烧。Fast burn 抓突发故障，Slow burn 抓慢慢退化。

| 告警 | 窗口 | 触发条件 | 持续 | 级别 | 路由 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| copilot_availability_burn_fast | 1h | 错误率 > 14.4× baseline（即 6 小时烧光 30 天预算） | 5min | P1 | PagerDuty + Slack |
| copilot_availability_burn_slow | 6h | 错误率 > 6× baseline（即 3 天烧光预算） | 1h | P2 | Slack |
| copilot_pii_leak | 1min | 增量 > 0 | 1min | P0 | PagerDuty 电话 + SMS + Slack #critical |

要点：
- 14.4× baseline 是 Google SRE 经典公式：0.005 预算 × 14.4 倍速 = 6 小时烧光 30 天预算
- Fast burn(5m) + Slow burn(1h) 双告警，既抓突发又抓慢退化
- PII 零容忍 → P0 + 电话，红线一例就炸
- `for: 5m` 防抖，持续 5 分钟才告警，避免单次抖动误报
- 不同优先级不同路由，不让 oncall 被淹

## 4 级告警分类 + 路由策略

「什么都重要 = 什么都不重要」。没有分级 = 真正的事故被淹没在噪音里。

| 级别 | 触发条件 | 响应 SLA | 路由 | 示例 |
| :--- | :--- | :--- | :--- | :--- |
| P0 红线 | 合规 / 资金 / 数据丢失 | < 5 min 接电话 | PagerDuty 电话 + SMS | PII 泄露 / 退款异常 |
| P1 高 | 可用性 / 重大功能损坏 | < 15 min | PagerDuty + Slack | 错误率突增 / 主链路挂 |
| P2 中 | 延迟 / 质量 / 部分功能 | < 1h | Slack + Email | P99 退化 / 某工具失败 |
| P3 低 | 趋势 / 成本 / 预警 | < 8h（工作日） | Email + 日报 | 成本上涨 / 慢退化 |

分级的本质，是把团队有限的「被打扰额度」留给真正重要的事。

## 告警 → Oncall → 处理的完整链路

oncall 收到告警不该再去查「为什么告警」，上下文要直接送到眼前。

告警自带的完整上下文：
- slo: availability > 99.5%
- current: 98.7% (burning at 14.4x)
- affected_traces: 2,847 (last 1h)
- top_error_types: [TOOL_TIMEOUT: 1502, LLM_429: 894]
- sample_trace_ids: [trace-abc, trace-def, trace-ghi]

Oncall 三步走：
1. 看告警自带上下文
2. 点 sample_trace_ids 跳 Phoenix 看具体 trace
3. dashboard 查 Day-over-Day，决定 rollback / hotfix

incident 状态机自动追踪：triggered → ack → mitigated → resolved（全程时间戳 = MTTR）。

## Industry Signals（2026）

| 来源 | 做法 | 启示 |
| :--- | :--- | :--- |
| Google SRE | SLO + 错误预算 + 多窗口多燃烧率告警 | 系统稳定性的「科学基础」 |
| PagerDuty / Datadog | 告警→ack→升级→复盘全流程产品化 | 别自己造 incident 工作流 |
| Anthropic / OpenAI | LLM API 给明确 SLO（99.9% / P99<5s） | 可参考它做你的内部 SLO |
| Grafana SLO / Sloth / Pyrra | 开源把 burn-rate 告警做成开箱即用 | 不用手写 Prometheus 表达式 |

一个延伸提醒：EU AI Act 对高风险 AI 要求「全生命周期自动记录日志、留存 ≥ 6 个月」，你这套 trace + 告警 + incident 记录，正好是合规审计要的东西。可观测不只是工程提效，2026 也是合规底座。

## 反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 阈值拍脑袋 | "P99 > 2s" | 高频误报 | 从 SLO 反推 burn rate |
| 没有分级 | 所有告警都 @channel | 团队脱敏屏蔽 | 4 级 + 不同路由 |
| 没有错误预算 | "出错就告警" | 正常波动也叫 | 看预算消耗速度 |
| 不接 incident | 告警不关联 trace | 事后查不到 | 自带 sample_trace_ids |
| SLO 拍脑袋 | "99.99% 可用"（业务不需要） | 过度工程 + 浪费 | 从业务诉求出发 |

踩坑提醒：SLO 越高越好是个反直觉的坑。99.9% 到 99.99% 的成本可能是 10 倍，而你的客服 Copilot 客户根本感知不到那 0.09%。SLO 要从业务「能接受多差」反推，不是从「我想多好」出发。

## Recap

- 告警的科学基础是 SLO + 错误预算 + 燃烧速度，不是「指标超了某个数」。
- Copilot 5 类核心 SLO 必须是可测量的数字，合规是零容忍红线。
- Fast burn + Slow burn 双告警，既抓突发又抓慢退化。
- 4 级分类 + 不同路由，把团队有限的被打扰额度留给真正重要的事。
- 告警自带上下文 + sample_trace_ids，让 oncall 不需要再去查「为什么告警」。
