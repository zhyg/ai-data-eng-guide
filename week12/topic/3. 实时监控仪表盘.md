# 3. 实时监控仪表盘

## 核心问题

trace 全上车之后，下一个问题是：这么多数据，到底看哪几张图？

真实场景：一个「很专业」的 dashboard，20 多个面板挤一屏，各种曲线密密麻麻。真出事那晚，oncall 凌晨 3 点被叫起来，盯着那一墙图愣是看不出哪里不对。信息全在那，但「看不见」。

dashboard 的核心矛盾：「看得多」和「看得清」是反的。生产级 dashboard 不是「展示所有数据」，是「为特定角色解决特定决策问题」。

## 不同角色、不同面板

把三拨人的需求塞进同一个 dashboard，结果就是三拨人都嫌它难用。先问「谁在什么场景下用」，再画图。

| 角色 | 看什么 | 需要什么 | 决策问题 |
| :--- | :--- | :--- | :--- |
| Oncall | 5 张图 | 红绿灯 + DoW 对比 | 要不要升级 |
| 工程师 | 具体 trace + span | P50/P95/P99 拆解 + 错误类型 + 堆栈 | 怎么修 |
| PM / 业务 | 业务指标趋势 | 一次解决率 / CSAT / 成本 / 与上一版对比 | 要不要砸资源 |

## 5 个必备面板

不管什么 Agent 项目，这 5 张是「系统体检报告」，缺一张有盲区。前 4 张是 Google SRE「黄金信号」的变体，第 5 张 Quality 是 LLM 时代专属。

| 面板 | 看什么 | 关键指标 | 诊断什么 |
| :--- | :--- | :--- | :--- |
| Overview 总览 | 系统健不健康 | QPS / Error Rate / P99 | 要不要升级响应 |
| Quality 质量 | 答得好不好 | Faithfulness / Citation / Refuse Rate | 要不要回滚 |
| Performance 性能 | 快不快 | 各 span 耗时分布 | 哪一段慢 |
| Cost 成本 | 贵不贵 | Token × 单价（$2-15/1M tok 量级） | 要不要降级模型 |
| Errors 错误 | 错在哪 | 错误类型分布 + 趋势 | 哪类故障在升 |

这 5 张要放在同一屏，切来切去会错过关联：比如成本突然涨、同时 P99 也涨，大概率是召回 top_k 被人调大了。分开看就发现不了这种关联。

## 面板查询逻辑

所有查询都基于 OTel span 属性，不需要单独 ETL 一份数据，这是统一协议的红利。

| 面板 | 关键查询 |
| :--- | :--- |
| Overview | QPS = count(span='rag.query')/60s；Error Rate = count(status='ERROR')/count(*)；P50/P99 = percentile(elapsed_ms) |
| Quality | Citation Coverage = count(evidence_count>0)/count(*)；Refuse Rate = count(insufficient_evidence=true)/count(*)；Live Faithfulness = avg(faithfulness) where sampled=true（1% 抽样） |
| Performance | 各 span 耗时 P99：retrieve / rerank / llm 分别看 |
| Cost | Cost/Query = sum(prompt_tok×price + completion_tok×price)/QPS |
| Errors | Tool Failures = count(*) by tool_name where status='ERROR'；HITL SLA Miss = count(*) where waited_ms>900000 |

要点：
- P99 + P50 双指标：P99 看「最差用户体验」，P50 看「中位体验」，必须都看
- Live Faithfulness 用 1% 抽样：在线全量跑 LLM-judge 太贵，抽样够用（Week 11 学过）
- Tool Failures 按 tool_name 分组：立刻看出哪个工具最不稳
- waited_ms > 900000：就是 Week 10 那个 15 分钟 HITL 超时

## Day-over-Day 对比

「现在 P99=2.1s」几乎没信息量；「比上周同时段差 30%」才是问题。绝对值会骗人，变化率不会。

| 对比方式 | 怎么算 | 适合 | 发现什么 |
| :--- | :--- | :--- | :--- |
| 同比 DoW | 今天 vs 上周同一天同时段 | 日常运营 | 周节律突变 |
| 环比 HoH | 当前小时 vs 上一小时 | 快速问题发现 | 突发故障 |
| 基线对比 | 7 日 / 30 日均线 | 长期趋势 | 慢慢退化 |
| Release 对比 | 当前版本 vs 上一 release | 发布回归 | 上线后退化 |
| 百分位带 | P10-P90 历史带 + 当前点 | 判断正常波动 | 识别真异常 |

oncall 面板里每个核心指标都带一条「上周同时段」的虚线。电商有明显周节律，周一上午的 P99 本来就比周日高，拿固定阈值告警全是误报；拿 DoW 一比，「比上周同时段高 30%」才是真异常。

## 三层钻取

让 oncall 30 秒内从「总览异常」定位到「具体 span」，不再大海捞针。

Top（5 个总览面板红绿灯） → Drill（span / error 拆解定位层级） → Trace（trace 详情时间轴可视） → Span（span 详情属性 + artifact） → Action（决策：回滚 / 修复）

这条钻取链是 dashboard 设计的灵魂。最关键的一条：面板必须能「跳转到 trace」。看到异常却点不进去，oncall 还得另开一个工具重新搜，30 秒定位就变成 30 分钟。

## Industry Signals（2026）

LLM 可观测平台已「选型分化」，三条路按团队规模选。

| 工具 | 定位 | 适用 / 局限 |
| :--- | :--- | :--- |
| Phoenix（Arize）/ TruLens | LLM 可观测开源事实标准、自托管 + feedback function | 中型团队 / 自主可控（UI 朴素） |
| Langfuse | 开源 + LLM 专用 + 自托管友好 | 要数据驻留 / 合规自托管首选 |
| LangSmith | trace + eval + prompt 一站式 SaaS | LangChain 生态 / 快速验证 |
| Braintrust / Datadog | CI 门禁 + PR 评分 / 企业级 APM 一体化 | 要发布门禁 / 大企业统一可观测 |

推荐路径：自托管/合规优先选 Langfuse 或 Phoenix；LangChain 栈用 LangSmith；要把可观测和「发布门禁/PR 评分」打通看 Braintrust。后端都兼容 OTel，Lesson 1 埋的那一份 OpenInference span 喂给哪个平台都能用。

## 反模式

| 反模式 | 具体表现 | 后果 | 正确做法 |
| :--- | :--- | :--- | :--- |
| 全部一墙 | 20+ 面板挤一屏 | oncall 看不见问题 | 5 个总览 + 钻取 |
| 只看实时 | 不做 DoW 对比 | 不知道是否退化 | Day-over-Day 必备 |
| 只看 P99 | 忽略 P50 / 错误率 | 中位体验掉了不知道 | P50 + P99 + Error 都看 |
| 不分角色 | oncall 看工程师面板 | 关键信号被淹没 | 分角色定制 |
| 面板点不进 trace | 看到异常但跳不进去 | 调试要重开工具 | 面板双向跳转 trace |

踩坑提醒：「面板点不进 trace」最容易被忽略，却最毁效率。任何一个总览面板上的异常点，必须能一键跳到对应的 trace 列表。这条钻取链断在哪里，oncall 的排障时间就在哪里翻十倍。

## Recap

- dashboard 核心矛盾是「看得多」vs「看得清」，必须为不同角色定制。
- 5 个必备面板（Overview / Quality / Performance / Cost / Errors）= Google SRE 黄金信号 + LLM 质量。
- Day-over-Day 对比比实时数字更能发现问题，oncall 面板至少要有 3 种对比。
- 三层钻取（总览 → 拆解 → trace → span → 决策）是 dashboard 设计的灵魂。
- 所有查询基于 OTel span 属性，不需要单独 ETL。
