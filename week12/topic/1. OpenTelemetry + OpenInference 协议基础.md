# 1. OpenTelemetry + OpenInference 协议基础

## 核心问题

Week 11 让你知道系统「好不好」，这一周解决另一个要命的问题：系统出事了，你能不能在客户骂完之前找到「卡在哪、为什么」？一个请求穿越 10 多个服务，光看日志就是黑灯瞎火。我们给它装上一台显微镜，让任何一条请求都能完整还原。

真实场景："今天 Copilot 答得很慢。""昨天那条回答好像有问题。"没有细节，但你得在 30 分钟内回答客户：是检索慢、重排慢、生成慢，还是工具卡了？没有可观测性，就是在黑灯瞎火里摸电闸。

关键判断：Agent 时代，trace 比 log 重要 10 倍，因为 log 是「点」，trace 是「因果链」。

## LLM/Agent 时代「打日志」不够用了

传统 Web 一个请求穿 2-3 个服务，日志够用。Agent 一个请求穿 8-15 个 hop，光靠日志根本串不起来：

User 提问 → query Router 意图路由 → RAG 召回/重排/生成 → Tool 工具调用 + fallback → HITL 人工审批 + Audit

8-15 个 hop，每个都有耗时、错误、依赖。光看日志既找不到「慢在哪一段」，也没法把「用户问题 → LLM 决策 → 工具调用」关联起来。必须升级到分布式追踪：一个 trace_id 贯穿全链，每一段一个 span 记录细节。

## 可观测性的 3 个支柱

别只押一样：日志看点、指标看面、追踪看因果链。

| 支柱 | 形态 | 示例 | 管什么 | 短板 | 工具 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Logs 日志 | 事件级文本 | "12:05 调了 RAG 服务" | 单点事件回顾 | 无法跨服务关联 | ELK / Loki |
| Metrics 指标 | 数值时序 | "P99 2.3s / qps 120" | 趋势 + 容量 | 知道出事、不知在哪 | Prometheus |
| Traces 追踪 | 请求级因果链 | "这次穿 8 个服务、慢在 rerank" | 跨服务故障定位 | Agent 时代的命门 | OTel + Jaeger/Tempo |

关键判断：Metrics 告诉你「系统发烧了」，但烧在哪个器官，只有 Traces 能指出来。三样一起用、用同一个 trace_id 串起来，才是完整的可观测。

## OTel 核心模型：Trace / Span / Context

理解这 3 个概念，所有可观测代码长得都一样：

- **Trace**：一次完整请求，对应一棵 span 树
- **Span**：请求里的一个具体步骤
- **Context**：跨服务传递的 trace_id 信封

要点：
- `start_as_current_span` 自动建父子关系，rag.query 是父，retrieve/rerank/llm 是子，自动嵌成一棵树
- `set_attribute` 加结构化属性，之后在 Phoenix / Jaeger 里直接按字段查询过滤
- 一个 trace_id 自动在所有 span 间传递（context propagation），什么都不用做
- span 自动记开始/结束时间，时间轴上一眼看出「哪段慢」

只需要 tracer / span / attribute 三个 API，就能把 RAG 全链路追踪上车。

## OpenInference：把 OTel 扩展成 LLM 专用协议

OTel 的 span 字段是「业务无关」的；LLM 那些特殊数据，得有人来定标准。

| 字段类别 | 标准属性 | 为什么需要统一 |
| :--- | :--- | :--- |
| LLM Call | llm.model_name / invocation_parameters | 跨工具识别用的什么模型 |
| Tokens | llm.token_count.prompt / completion / total | 统一算成本 |
| Messages | llm.input_messages / output_messages | 跨工具看 prompt |
| Tools | tool.name / description / json_schema | 跨平台识别工具调用 |
| Retrieval | retrieval.documents / score | RAG span 标准字段 |
| Embeddings | embedding.model / text | Embedding 调用标准 |

2024 年 Arize 主导推出 OpenInference 把这些钉成标准，Phoenix / LangSmith / Langfuse 都原生支持。emit 一次，多个平台都能消费。

## OmniSupport 里的接入方式

业务代码一个字不改，Instrumentor 自动注入符合标准的 span：

- `OpenAIInstrumentor().instrument()` 一行代码自动追踪所有 OpenAI/Anthropic 调用
- OpenInference 字段自动填好：llm.model_name / token_count.* 不用手写 set_attribute
- `BatchSpanProcessor` 异步批量发送，不阻塞业务、不增加延迟
- 一份设置多个平台消费：Phoenix / Jaeger / Langfuse 走同一份 OTLP 协议，换平台不改代码

## Industry Signals（2026）

OTel + OpenInference 已是事实标准，自研可观测协议在 LLM 时代是工程债。

| 标准 / 平台 | 能力 | 工程含义 |
| :--- | :--- | :--- |
| OpenTelemetry（CNCF 毕业） | 继 Prometheus 之后第 2 个毕业的可观测项目 | 所有云厂商都支持，事实标准 |
| OpenInference（Arize 2024） | LLM 字段标准化，Phoenix/LangSmith/Langfuse 原生支持 | 现在就能用、生态最成熟 |
| OTel GenAI 语义约定（gen_ai.*） | 官方在推 invoke_agent / execute_tool / chat span | 2026 仍 experimental→stable，与 OpenInference 收敛中 |
| Phoenix / Langfuse / Braintrust / Datadog | 后端兼容 OTel，前端做 Agent 专用可视化 | 一次埋点，跨工具自由切换 |

落地建议：当下用 OpenInference（生态成熟），同时关注 gen_ai.* 的进展。埋点抽象一层，将来切换无痛。

## Recap

- Agent 时代必须升级到分布式追踪，Logs / Metrics / Traces 三个支柱缺一不可，但 Traces 是命门。
- OTel 核心模型只有 3 个概念（Trace / Span / Context），3 个 API 就能上车。
- OpenInference 把 OTel 扩展成 LLM 专用协议，标准化了 tokens / messages / tools / retrieval 字段。
- 业务代码零改动，一行 Instrumentor 自动注入标准 span，一份 OTLP 多平台消费。
