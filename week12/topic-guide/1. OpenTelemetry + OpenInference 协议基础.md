# 导学 01：系统出了事，为什么翻日志找不到原因？

## 一句话理解

OpenTelemetry 是一套让每条请求都能被完整追踪的标准协议，OpenInference 在它上面加了 AI 系统专用的字段规范。

## 用生活打比方

把排查系统故障想成快递公司追查一个丢件。传统做法是到每个中转站翻纸质台账，字迹不一、格式不同、时间戳对不齐，翻到天黑也拼不出包裹到底卡在哪一站。现在公司统一了电子面单标准：每个站点扫码时自动记录时间、操作人、下一站去向，所有信息汇总到一个系统里。只要输入快递单号，从揽件到签收每一步都清清楚楚。OpenTelemetry 就是这个电子面单标准，OpenInference 额外规定了 AI 系统里特有的字段（比如用了哪个模型、花了多少 token）该怎么填。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **可观测性三支柱（Logs / Metrics / Traces）** | 日志记单个事件，指标记数值趋势，追踪记一条请求穿过所有服务的完整路径。三样合在一起才算完整的可观测。 |
| **Trace** | 一次用户请求从头到尾的完整记录，像一棵树把所有步骤串起来。 |
| **Span** | 请求里的一个具体步骤，比如"检索文档"或"调用大模型"，记了开始时间、结束时间和关键属性。 |
| **Context（上下文传播）** | 跨服务传递 trace_id 的机制，保证同一个请求到了不同服务也不会断链。 |
| **OpenInference** | Arize 推出的 LLM 字段标准化协议，把 token 数、prompt 内容、工具调用这些 AI 特有信息统一了格式，各平台都能消费。 |
| **Instrumentor（自动埋点器）** | 一行代码注入后，自动给所有 LLM 调用生成符合标准的 span，业务代码不用改。 |

## 避坑提醒

- **以为打了日志就是有可观测性**：日志是散落在各个服务里的点，串不成因果链。一条请求穿过多个服务后，日志之间靠时间戳根本对不齐。
- **以为自己定义一套字段就够用**：自研字段换个可观测平台就对不上，历史数据全废。直接用标准协议，一份数据多个平台都能消费。
- **以为接入 OTel 就完事了**：接入只是第一步，span 名字全叫 "process"、属性塞一堆原文，等于没接。协议上车之后还要设计好 span（下一节课的事）。

## 一句话总结

> **先用 OTel + OpenInference 把协议地基打好，后面的 span 设计、仪表盘、告警才有统一的数据来源。**
