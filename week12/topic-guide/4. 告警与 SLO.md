# 导学 04：告警天天响，为什么真出事反而没人管？

## 一句话理解

SLO 把告警从"指标超了某个数就叫"升级成"错误预算被烧得异常快才叫"，大幅减少误报，让真正的故障不被噪音淹没。

## 用生活打比方

继续我们的快递追踪系统。以前公司规定"任何一个站点处理超过 2 小时就报警"，结果大促期间站点天天超时，调度主管手机炸了上百条通知，烦得直接静音。真正的事故（比如一辆车抛锚导致整条线路瘫痪）反而被埋在噪音里。后来换了一种做法：先定好承诺（每月准时率 99.5%），算出每月允许多少单延误（错误预算），只有当延误消耗速度异常快（照这个速度一周内会把全月额度烧光）才触发告警。偶尔一两单慢了不叫人，持续大面积延误才拉响警报。这就是 SLO 告警的逻辑。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **SLO（服务等级目标）** | 对业务方的承诺，比如"99.5% 的请求必须成功响应"，从业务能接受的底线出发，不是越高越好。 |
| **错误预算（Error Budget）** | 100% 减去 SLO 就是允许失败的额度，比如每月 0.5% 可以出错。这是一笔你可以"花"的容错预算。 |
| **燃烧速度（Burn Rate）** | 错误预算被消耗的速度。速度正常就不告警，速度异常快才叫人。 |
| **快烧 / 慢烧双告警** | 快烧抓突发（短时间内预算急剧消耗），慢烧抓退化（长时间缓慢消耗），两种结合才能全覆盖。 |
| **4 级告警（P0/P1/P2/P3）** | 按严重度分级，每级对应不同的响应速度和通知方式。P0 打电话，P3 发日报，避免所有告警同一个响度。 |
| **告警自带上下文** | 告警消息里直接附当前 SLO 状态、主要错误类型、示例 trace_id，收到告警不用再花时间查"为什么响了"。 |

## 避坑提醒

- **以为告警阈值定得低就是安全**：阈值越低误报越多，团队很快会麻木，真出事反而被淹没。告警该管的是异常趋势，不是单次波动。
- **以为 SLO 定得越高越好**：从 99.9% 提到 99.99% 工程成本可能翻好几倍，而业务方根本感知不到那一点点差异。SLO 从业务能接受的底线出发。
- **以为所有告警都同等重要**：不分级等于全部都不重要。值班人员的注意力是有限资源，要把它留给真正的 P0/P1。
- **以为告警响了就算通知到位**：如果告警里没有上下文，收到的人还得花十分钟去查发生了什么，延误了真正的响应时间。

## 一句话总结

> **用 SLO 加错误预算取代拍脑袋的阈值，告警只在预算被异常消耗时触发，值班人员才能信任告警、快速行动。**
