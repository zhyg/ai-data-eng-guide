# 导学 05：问题修完了，为什么同样的坑还会再踩？

## 一句话理解

把 bad case 复盘做成有固定步骤和产物的标准流程，让每次故障都能沉淀为反例库里的一条永久门禁。

## 用生活打比方

继续我们的快递追踪系统。包裹破损了，差的站点处理方式是赔完就完事；好的站点会拉出这单的全程追踪记录，定位到底是分拣暴力还是装车挤压，然后把这个案例加进培训手册，下次同类操作有标准动作来防住。更关键的是，这个破损案例会变成质检抽查的必查项：以后每次上新设备或换流程，都要专门跑一遍"历史破损件同类场景"确认没有回退。一次事故变成了一条长期生效的质检规则。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **Bad Case 5 步流程** | Detect（发现）→ Triage（定级）→ Locate（定位根因）→ Fix（修复）→ Verify（验证+沉淀），每步有时限和明确产物。 |
| **Trace 根因定位决策树** | 打开 trace 时间轴，按"哪一层异常"逐步缩小范围，照着走新人也能在几分钟内定位，不靠猜。 |
| **5 类常见根因** | 检索漏召、重排丢失、LLM 编造、工具失败、HITL 阻塞，每类对应不同的修复方向。 |
| **复盘模板（7 段）** | Summary、Trace Evidence、Root Cause、Fix、Verify、Lessons、Action Items，每段有明确产物，不是开会聊聊。 |
| **反例库复利** | 把 bad case 自动加进评测集的反例样本，以后任何改动都会对照这条跑回归，同类错误再也发不出去。 |

## 避坑提醒

- **以为修完就算处理完了**：不加进反例库、不跑回归、不更新手册，下次同类问题必然重发。修复只是第 4 步，第 5 步验证加沉淀才是产生长期价值的地方。
- **以为定位问题只能靠资深工程师**：有了 trace 加决策树，按层级缩小范围是机械步骤，入职不久的人也能上手。
- **以为复盘是为了追责**：Blameless（不归罪个人）的文化才能让团队敢上报 bad case。一旦有人因为上报被批评，后面的 bad case 就会被藏起来。
- **以为反例库只要有就行**：每条反例必须先验证"修复有效"再入库，否则库里混着没修好的样本，门禁反而变成噪音。

## 一句话总结

> **把复盘标准化成 5 步流程，bad case 自动沉淀为反例库里的长期门禁，团队就从反复救火变成持续积累。**
