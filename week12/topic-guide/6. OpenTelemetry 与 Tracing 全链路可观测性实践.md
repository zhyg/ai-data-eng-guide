# 导学 06：理论都懂了，代码里到底怎么串起来？

## 一句话理解

这节课把前 5 节的协议、span、面板、告警、复盘串成一条可运行的工程闭环：从请求埋点到故障定位，再到 bad case 自动回灌反例库。

## 用生活打比方

继续我们的快递追踪系统。前面分别讲了电子面单标准、扫码规范、调度大屏、异常告警规则、破损件复盘流程。这节课相当于把这些全部装进一个真实的物流中心跑一遍：仓库里贴上扫码设备，连上调度中心的大屏，配好告警通道，模拟一批包裹从揽件到签收，故意制造一次异常，验证整条链路能不能从告警一路追溯到具体环节，最后把这次异常录入质检必查项。跑通了才算真正上线。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **OTel Collector** | 业务服务和可观测后端之间的中转站，负责接收、批量处理和转发 trace 数据。换后端时业务代码不用动。 |
| **W3C TraceContext** | 跨服务传递 trace_id 的标准 HTTP header，保证同一请求穿过多个服务不会断链。 |
| **公共埋点 runtime** | 把脱敏（privacy）、初始化（setup）、span 封装（trace）集中到一个共享模块，业务方只需注入一行就能完成采集。 |
| **闭环编排（run_closure）** | 把 SLO 计算、告警触发、复盘生成、bad case 回灌反例库这些步骤串成一个自动化流程。 |
| **契约测试** | 验证可观测性基础设施满足工程标准：SLO 配置齐全、告警规则存在、面板字段完整、事故报告通过 schema 校验。 |

## 避坑提醒

- **以为每个服务各自初始化 OTel 就行**：各写各的会出现格式偏差，应该共享一个 runtime 模块统一管理初始化和脱敏逻辑。
- **以为容器内用 localhost 就能连到其他服务**：容器内的 localhost 指向容器自身，跨容器通信要用服务名。
- **以为埋点上了就自动有闭环**：采集只是第一步，从采集到告警到复盘到回灌反例库，每个环节都要显式编排和验证。
- **以为跑通一次就代表没问题**：需要契约测试持续验证可观测性配置没有漂移，新代码上线后也要确认 span 和告警规则仍然完整。

## 一句话总结

> **把协议、span、面板、告警、复盘在代码里串成一条闭环并用契约测试锁住，系统才真正具备"故障分钟级定位加 bad case 自动复利"的运营能力。**
