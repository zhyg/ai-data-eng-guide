# 导学 02：追踪接上了，为什么打开一看还是看不懂？

## 一句话理解

Span 设计决定了追踪数据的信息量，命名、属性、状态三个维度设计到位，打开时间轴才能一眼定位问题。

## 用生活打比方

继续我们的快递追踪系统。电子面单标准统一了，但如果每个站点扫码时只写"已处理"两个字，不写是分拣、装车还是派送，你查包裹时只能看到一连串"已处理"，完全不知道卡在哪一环。好的扫码记录应该写清楚：这一步是干嘛的（分拣 / 装车 / 派送）、关键结果是什么（分到哪条线路、装了几件、几点出发）、有没有异常（破损 / 错分）。这样查件时扫一眼就知道问题出在分拣还是派送。Span 设计就是规定每个扫码点该记什么、怎么记。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **Span 命名三段式（层.动作.策略）** | 比如 rag.retrieve.hybrid，一看就知道是 RAG 层、在做检索、用的混合策略。不写 process / call / run 这种空话。 |
| **RAG 6 段标准 span** | query → intent_route → retrieve → rerank → generate → audit，刚好覆盖 RAG 全链路每一个你会去查的环节。 |
| **业务级 error_type** | 除了 OK/ERROR，再加一个具体错误类型，比如 insufficient_evidence、tool_timeout，出错时一眼知道原因。 |
| **属性预算** | 每个 span 建议控制属性数量和总字节，不塞原文，用摘要加长度的组合（_preview + _len）保持精简。 |
| **artifact_url** | 完整的 prompt、response 这些大块内容存到对象存储，span 里只放一个链接指过去，trace 表保持小巧。 |
| **Tool / HITL span** | 工具调用和人工审批也要有专门的 span，记录每次尝试、降级层级、等待时长，不留黑盒。 |

## 避坑提醒

- **以为接上了 OTel 就自动有好的 span**：自动埋点只管 LLM 调用，业务链路里的检索、重排、工具、审批都要自己设计 span，否则就是一堆看不懂的方框。
- **以为属性越多越好**：把整段 prompt 塞进 span 会让上传变慢、存储变贵，用摘要加链接的模式就够了。
- **以为状态只需要成功和失败**：只有 OK/ERROR 等于只知道"错了"，不知道"为什么错"。加上业务级 error_type，定位速度能快很多。
- **以为用户数据存进 span 没关系**：span 数据可能进第三方平台，里面带了手机号、身份证号就是一次合规事件。写入前必须脱敏。

## 一句话总结

> **Span 设计到位，打开时间轴就像读一个故事，5 分钟定位问题；设计不到位，有 trace 也等于没有。**
