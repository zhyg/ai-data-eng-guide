# 3. HITL

## 核心问题

退款、删数据、发对外邮件、修改财务等动作，再稳的 Agent 也不能自行拍板。但 HITL 也不能同步挂住系统：讲义中的事故是审批人开会，Agent 同步等待 40 分钟，占住会话资源，导致后续用户全部超时。

真正的 HITL 不是确认弹窗，而是工程化的“决策权移交”：可观测、可追责、可回放，且等待审批时释放 Agent 资源。

## UI HITL 与工程化 HITL

| 维度 | UI HITL（常见但不够） | 工程化 HITL（生产级） |
| :--- | :--- | :--- |
| 形态 | 弹窗 / 确认按钮 | 审批工作流 + audit event |
| 同步性 | 阻塞 Agent 等待 | 异步 + Agent 释放资源 |
| SLA | 没有 | 明确 timeout + 降级 |
| 审计 | 没有或事后补 | 审批前、中、后全程 audit |
| 决策回放 | 不可能 | 完整重放 who / when / why |
| Agent 状态 | 原地等待 | 保存 checkpoint，可恢复 |

生产级 HITL 的内核是 `SLA + 降级 + 审计 + 异步`。

## 三阶段工作流

`Pre-Decision → Wait & Notify → Post-Decision`

### Pre-Decision

- Agent 准备调用工具，规则检测到风险。
- 生成 approval_request，附带完整上下文。
- 冻结并持久化 checkpoint。
- 记录审批发起事件。

### Wait & Notify

- 通过 Slack 或邮件异步通知审批人。
- 设置 SLA，例如 15 分钟。
- Agent 释放资源并处理其他会话。
- 审批人可以拒绝且填写理由。
- 审计 notified_at。

### Post-Decision

- 审批结果通过 callback 触发。
- 校验审批人角色，从 checkpoint 恢复 Agent。
- 根据结果执行、拒绝或升级。
- 全程记录 audit_event，能够重放谁在何时为何做出决定。

这套机制就是 Checkpoint + Resume：冻结现场 → 释放资源 → 等待回调 → 恢复执行。

## 触发矩阵：3 类强制 + 2 类条件

| 类别 | 典型动作 | 触发原因 | 审批层级 |
| :--- | :--- | :--- | :--- |
| 强制·财务 | 退款 / 转账 / 优惠券 | 资金不可逆 | 财务团队 |
| 强制·不可逆 | 删数据 / 删文件 / 发对外邮件 | 执行后无法回滚 | 业务负责人 |
| 强制·合规 | 导出 PII / 跨域查询 / 法务报告 | 合规风险 | 合规团队 |
| 条件·金额阈值 | 退款 > 1000 元 | 超自动审批额度 | 主管 |
| 条件·异常模式 | Agent 一小时 5 次重试 | 可能被滥用 / 攻击 | 安全团队 |

触发矩阵必须由框架代码强制执行，绝不能让 LLM 自己判断是否需要审批。

## 四种 HITL 模式

| 模式 | 介入时点 | 典型场景 | 工程实现 |
| :--- | :--- | :--- | :--- |
| Pre-Confirm | 工具执行前 | 高额退款、删数据 | request_approval + 阻塞动作 |
| Approval | 执行后、生效前 | 邮件发送（草稿审） | 生效前 hold + 异步审批 |
| Review | 执行后采样审 | 内部数据导出（10% 采样） | 执行 + 异步采样人工审 |
| Escalation | Agent 不确定时 | confidence < 0.7 | LLM 主动触发 |

不可逆动作必须在执行前拦截；可逆但有质量要求的动作可采样复审；Escalation 是模型不确定时的逃生口，不替代强制规则。

## 五条设计原则

1. **一屏内决策**：摘要、关键参数、一键批准或拒绝，拒绝必须填理由；把决策时间压到 30 秒内。
2. **拒绝理由必填**：理由是免费训练数据；讲义指出积累半年可把误触发率砍一半。
3. **不逐级审批**：避免“组长 → 总监 → VP”，采用分层级、单层决策。
4. **超时必降级**：SLA 15 分钟无结果时，预先确定默认升级、默认拒绝或转人工。
5. **审计不可篡改**：写入 append-only 存储，保留审批人、时间和理由。

## Anti-Patterns

| 反模式 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 同步等审批 | 资源浪费 + 用户干等 | 异步 + checkpoint |
| 没有超时 | 事务挂死 | SLA + 降级路径 |
| 审批信息太长 | 审批慢 / 误批 | 摘要 + 关键参数 |
| 不写审批 audit | 合规审查直接失败 | 发起 / 通知 / 决策三段 audit |
| 让 LLM 判断是否 HITL | 不一致 / 漏审 | 规则强制 + 触发矩阵 |

## Industry Signals

| 框架 / 标准 | 能力 | 工程含义 |
| :--- | :--- | :--- |
| LangGraph interrupt | 每个 super-step 存 StateSnapshot，需要 durable checkpointer | checkpoint 不等于 durable，生产需 Postgres / DynamoDB 和失败恢复 |
| OpenAI Agents SDK | human approval 内置，控制平面位于 trusted infra | auth、audit、人审在容器外且可恢复 |
| Anthropic HITL 三模式 | approve before / sample after / escalate when uncertain | HITL 是 Agent 核心设计 |
| Claude Computer Use | 删文件、提交表单等高危动作强制人工确认 | HITL 是默认行为 |

## Recap

- HITL 是决策权移交协议，不是 UI 按钮。
- 异步通知和 checkpoint/resume 避免审批拖死系统。
- 财务、不可逆、合规动作必须规则强制拦截。
- SLA、降级和三阶段审计共同保证可恢复、可追责、可回放。
