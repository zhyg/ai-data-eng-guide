# 2.工具路由与失败回退

## 核心问题

多工具系统不能把所有工具一股脑交给 LLM 自由选择。真实案例中，团队把 12 个工具全部暴露给模型，用户只是查询工单，Agent 却创建了大量空工单。讲义给出的经验边界是：工具超过 5 个，自由选择就开始明显误选。

受控原则是：高确定性的部分用代码写死，只把真正需要判断的窄决策留给模型。

## 自由调度为什么会翻车

- 工具达到 5+ 后误选率开始上升，甚至把查询错选成写入。
- 工具失败后，模型可能陷入无限重试，占满会话资源。
- 多步任务中，模型偶尔漏掉一步，而系统难以定位遗漏。

## 三种调度策略

| 策略 | 做法 | 适用范围 | 局限 | 工程负担 |
| :--- | :--- | :--- | :--- | :--- |
| LLM 自由选 | 全部工具暴露给 LLM，由模型推理选择 | 工具 < 5、场景多变 | 误选率高、不可控 | 最低 |
| 规则 + LLM | 关键词 / 意图预过滤，再让 LLM 决策 | 工具 5–20 | 规则需要维护 | 中，推荐默认 |
| 显式 Workflow | 代码定义流程节点，LLM 只做节点内窄决策 | 高价值、流程清晰 | 灵活性较差 | 最高 |

选型要看“确定性 × 风险”：

| 场景 | 确定性 | 风险 | 建议策略 |
| :--- | :--- | :--- | :--- |
| 客服 FAQ 问答 | 低 | 低（答错） | LLM 自由选 |
| 多产品线咨询路由 | 中 | 中（误导用户） | 规则 + LLM 兜底 |
| 工单状态更新 | 高 | 中（数据错乱） | 规则 + LLM，并带 confirm |
| 退款 / 资金动作 | 高 | 高（资金损失） | 显式 Workflow + HITL |
| 多步骤报表生成 | 中 | 低 | 显式 Workflow |

风险越高、确定性越高，控制权越应向代码侧移动。

## 五级失败回退链

工具失败不能简单上抛异常，再让 LLM 临场道歉。每类失败都要显式声明路径：

`Primary 主工具 → Retry 幂等重试 → Fallback 备用 / 缓存 → HITL 转人工 → Graceful 优雅降级`

讲义中的工单查询链具体为：

1. 主链路调用实时 API，超时为 1500 ms。
2. 同链路最多重试 3 次，采用指数退避。
3. 读取最多 300 秒、即 5 分钟前的缓存，并标记 stale。
4. 异步通知 Slack 的 `support-oncall`，优先级为 P2，不阻塞 Agent。
5. 返回固定用户消息“系统繁忙，已通知后台”，并标记 `fallback_level` 为 graceful。

每一级都应是独立工程对象，拥有独立函数、独立超时和独立审计。审计至少能回答降到了哪一级、主链路为何失败；例如记录 `fallback_level=cache` 和 `primary_error=TIMEOUT`。

## RAG 也应包装成工具

`用户请求 / request_id → 规则 + LLM 路由 → knowledge_search 或 ticket_query/update → fallback / HITL → 统一响应与审计`

将 RAG 特殊系统改造成 `knowledge_search` 普通工具，可以统一 Schema、fallback 和 audit：

- description 明确用于内部知识库的 “how to / what is”，并以 “NOT for” 排除实时数据、工单和财务查询。
- 输入要求 query 与 tenant；query 最长 500 字符。
- `top_k` 范围为 1–10；文档类型限定为 faq、manual、policy。
- 输出至少包含 1 条 EvidenceAnchor，并带 confidence。
- 所有已认证角色可以访问。
- 查询天然幂等，无需 idempotency key。
- 复用 `primary → retry → cache → graceful` 标准降级模式。

统一抽象后，Agent 只面对一种调用模型，治理也只需维护一套机制。

## Recap

- 生产级 Agent 需要明确决策框架，而不是完全自由选择。
- 默认从“规则 + LLM 兜底”起步，高风险流程使用显式 Workflow。
- 五级降级不是模型临场决策，而是可测试、可超时、可审计的确定性路径。
- RAG 与业务工具使用统一契约，才能统一路由、降级和治理。
