# 6.Copilot 端到端实践

## 实践目标与整体架构

本节把 Week 5 工单工具、Week 8 RAG 和 Week 9 Skill Pack 接入受控 Agent 控制面。`copilot.py` 中的 controlled Agent 负责串联契约、权限、HITL、幂等执行、失败回退和 Action Lineage，让工具既能被模型使用，又始终受规则约束。

`请求 → 工具存在性检查 → JSON Schema 校验 → 角色权限检查 → HITL policy 评估 → 幂等执行 → 记录 Action Lineage → 返回受控结果`

其中，检索链路失败时进入预定义 fallback；低置信度结果暂停并通知人工。控制器不把危险动作的判断和失败处置交给模型临场决定。

## 契约层：统一工具准入规则

课堂以三个契约对象构成控制面的入口：

| 契约 | 职责 | 关键约束 |
| :--- | :--- | :--- |
| `tool_contract_schema` | 定义所有工具共同遵守的顶层结构 | 名称、描述、输入输出 Schema、`allowed_roles`、审计字段、幂等和审批规则 |
| `ticket_update` | 受控写动作样板 | 操作与风险使用枚举；契约指定幂等字段；高风险操作触发 `required_approval` |
| `knowledge_search` | 把 Week 8 RAG 包装成只读工具 | 每条结果包含 EvidenceAnchor，并携带 `trace_id`、`release_id`；主检索失败按契约回退 |

`allowed_roles` 决定调用资格，审计字段规定必须留下哪些追踪信息。操作名和风险等级来自枚举，模型不能自由编造。是否需要人工审批由 `required_approval` 及 HITL policy 决定。

`knowledge_search` 的低分结果不能强行生成答案。课堂契约明确，当 `score < 0.4` 时进入 `pause_and_notify`，把低置信度作为受控状态处理。

## 工具发现与执行分离

`registry.py` 只做四件事：读取契约、按统一 Schema 校验、发现工具、导出 OpenAI/MCP 描述。它不执行工具，更不执行危险动作。

Tool API 同样是只读发现面，课堂展示了四类能力：

1. 工具清单。
2. 单个工具的详细契约。
3. OpenAI 格式导出。
4. MCP 格式导出。

这套接口采用渐进式披露：先返回轻量清单，让上层匹配候选工具，再获取少量候选的详细契约。发现面告诉客户端“有哪些工具、如何调用”，实际执行由独立控制面处理。

## 幂等：用稳定指纹阻止重复动作

写动作可能因网络重试、重复点击或队列重投而重复到达。课堂实现先用 `stable_json` 对 payload 做稳定序列化，消除字段顺序对摘要的影响；再用 `stable_digest` 生成 payload 指纹，并按契约指定的字段构造稳定幂等键。

幂等检查必须位于真实执行之前。Happy Path 中，第一次请求执行并保存结果；第二次相同请求命中幂等记录，直接复用第一次结果，不再创建新动作。payload 变化时，摘要也会变化，不能误用旧结果。

## Fallback：失败后使用可追踪的备用结果

当主向量库或主索引检索失败时，系统进入预定义缓存链路，而不是让模型现场编造：

`主检索 → 记录失败原因 → fallback attempt → 读取缓存 → 返回 EvidenceAnchor → 写入 lineage`

回退结果同时保留主链失败原因、fallback attempt、EvidenceAnchor 和 lineage。这样既能继续服务，也能解释用了哪份备用证据、为什么发生降级。缓存仍不可用时，系统进入既定的通知或受控失败状态。

## HITL：冻结请求，异步批准后恢复

高风险动作命中 HITL policy 后，系统保存请求摘要、触发原因、`trace_id` 和待执行动作，生成以 `APR` 开头的审批 ID，然后暂停执行。审批在控制器之外异步完成，批准后再恢复原现场。

防篡改的关键是 `payload_digest`：申请审批时保存一次，恢复执行时再次核对。审批前后的 digest 必须相同，保证最终执行的仍是审批人看到的原请求。等待审批与执行完成都写成 lineage event，因此一次高风险动作可以完整还原“请求、暂停、批准、执行”的过程。

## Action Lineage：记录动作与全部依据

动作血缘事件至少关联以下内容：

| 类别 | 记录内容 |
| :--- | :--- |
| 事件身份 | `event_id`、`trace_id`、事件阶段 |
| 工具与动作 | `tool_name`、请求摘要、执行结果 |
| 决策依据 | 数据快照、EvidenceAnchor |
| 运行版本 | Prompt、模型、Skill 版本 |
| 人工控制 | 审批等待、审批结果与完成事件 |

动作事件 ID 以 `act` 开头。内部事件还可转换为 OpenLineage 事件，与后续评测和观测体系关联。`trace_id` 把工具调用、fallback、审批和最终动作串成同一条可查询、可回放的链路。

## 工程分层与生产落点

| 层次 | 课堂职责 |
| :--- | :--- |
| service / tool-contracts | 对外提供工具清单、详细契约和格式导出等只读发现能力 |
| tools / control plane | 校验契约与权限，执行 HITL、幂等、fallback 和 lineage 控制 |
| 存储层 | 生产环境至少落地幂等表、审批表、动作血缘表 |
| 测试层 | 分为契约测试和控制面行为测试 |

课堂示例可用内存对象展示流程，生产环境必须持久化。否则进程重启后无法复用幂等结果、恢复审批现场或追查动作依据。

## 课堂验证

### 契约检查

- 所有工具符合 `tool_contract_schema`。
- `ticket_update` 覆盖幂等、HITL 和权限失败。
- `knowledge_search` 输出保留 EvidenceAnchor。
- HITL 与 Action Lineage 的 Schema 能承载对应事件。
- 危险工具的描述能向上层客户端明确风险。

### 控制面行为测试

- 低风险动作可自动执行，重复请求命中幂等结果。
- 高风险动作在审批前保持等待，批准后才执行。
- 角色权限失败会被拦截，同时留下可排查记录。
- 向量检索失败后使用缓存，并保留失败原因、证据与血缘。

### 三条端到端演示

| 路径 | 演示过程 | 验收结果 |
| :--- | :--- | :--- |
| Happy Path | 连续提交两次相同请求 | 第一次正常执行，第二次幂等命中并复用第一次结果 |
| Fallback | 主索引检索失败后读取缓存 | 错误原因、fallback attempt、EvidenceAnchor 和 lineage 均被保留 |
| HITL | 高风险请求先申请审批，再批准恢复 | 申请前等待、批准后执行；审批 ID 以 `APR` 开头，前后 `payload_digest` 一致，等待与完成均有 lineage event |

## 收尾：受控 Agent 的上线判断

完整链路把“能调用工具”升级为“能按契约、权限和风险规则调用工具”。上线时仍应延续整周的 SLO、证据覆盖与可回放要求，但本节的首要交付是可运行的控制面：发现和执行分离，写动作可幂等，高风险动作可暂停恢复，失败有固定回退，所有动作有持久化血缘。
