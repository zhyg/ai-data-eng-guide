# 1. 工具契约化

## 核心问题

Agent 调工具不是普通函数调用，而是让概率模型在生产系统里“按按钮”。一次看似合理的参数可能越过业务边界，一次成功执行也可能完全无法追责。因此，工具边界必须从编译期的代码契约升级为运行时强约束。

真实事故是：客服 Copilot 的退款工具没有幂等保护，网络抖动和前端重发使一笔 800 元退款执行了三次。由此得到上线红线：写类工具不带 `idempotency_key`，不准上线。

## 普通 Function 与受控 Tool

受控 Tool = function + 一整套运行时护栏。

| 维度 | 普通 function | 受控 Tool |
| :--- | :--- | :--- |
| 谁决定调用 | 代码逻辑（开发者写死） | LLM 推理（运行时才决定） |
| 输入约束 | 语言的类型检查 | JSON Schema 强校验 + 业务规则 |
| 错误处理 | 抛异常 / 返回 None | 结构化错误码 + retry 策略 |
| 权限 | 靠调用方上下文 | 工具内嵌 actor / role 校验 |
| 幂等性 | 可有可无 | 必须，重试 / 重发是常态 |
| 审计 | 打条日志事后查 | 实时、结构化的审计事件 |

## 受控工具的四个工程承诺

| 承诺 | 必备能力 | 解决的问题 |
| :--- | :--- | :--- |
| Schema | JSON Schema 定义输入输出；使用 enum、required、format；解码层强制 | 杜绝格式漂移和越界参数 |
| Idempotent | `idempotency_key` 必填；同 key 多次等于一次 | 抵御 retry、双发、重传和重复扣款 |
| Permission | actor + role 内嵌；显式声明 allowed_roles；调用前校验身份 | 越权调用直接拒绝 |
| Audit | 每次调用记录 audit；至少保留 trace_id、args_hash | 实时追踪与合规追责 |

四项是“出厂标配”，少一项都不应上线。

## 工具契约应框定什么

讲义中的 `ticket_update` 契约体现了以下边界：

- 描述明确动作范围，并用 “NOT for” 排除创建、删除和批量更新，减少误激活。
- 输入必填 `ticket_id`、`actor`、`idempotency_key`；工单 ID 使用 UUID 格式。
- 状态只能是 `pending`、`in_progress`、`resolved`、`closed`。
- `idempotency_key` 最短 16 个字符。
- 禁止额外字段，任何契约外参数直接拒绝。
- 仅 `support_agent`、`support_lead` 可以调用。
- 明列 `TICKET_NOT_FOUND`、`INVALID_TRANSITION`、`PERMISSION_DENIED`、`DUPLICATE_REQUEST` 四类失败码，让 Agent 预先知道如何承接失败。
- 强制审计 actor、args_hash、result_code、trace_id，供后续治理消费。

## 幂等：按动作类型选择实现

LLM 误判、用户重发、Agent 重试和网络抖动都会重复发起同一动作。

| 策略 | 怎么做 | 适合什么 | 局限 |
| :--- | :--- | :--- | :--- |
| 自然幂等 | 同一操作多次结果一致，如 UPSERT | 状态更新、配置修改 | 只对可重复操作有效 |
| idempotency_key | 客户端传 key，服务端去重 | 建工单、付款、发邮件 | 服务端要维护去重表 |
| 乐观锁 + 版本号 | 携带 version，CAS 更新 | 高并发更新 | 失败后需要重试 |

写类工具默认使用 `idempotency_key`。即使下游 API 不支持，也应在 Agent 层通过 Redis、args_hash 和 TTL 增加去重层。讲义示例把请求内容计入指纹，使同 key 不同参数不被误判为同一调用；原子占位避免高并发双穿透；TTL 为 24 小时，并回传 `_idempotent_hit` 告诉 Agent 本次使用了缓存结果。

## 工具风险准入矩阵

| 风险类别 | 示例 | 关键风险 | 控制策略 |
| :--- | :--- | :--- | :--- |
| Read-only | ticket_query / kpi_query | 数据泄露 | tenant / role 权限过滤 |
| Write 内部 | ticket_update / assign | 状态错乱 | Schema + 幂等 + 审计 |
| Write 外部 | 发邮件 / 推消息 | 不可逆、影响外部 | HITL |
| Financial | 退款 / 转账 / 优惠券 | 直接资金损失 | HITL + 双签 + 审计 |

财务类和外部不可逆类动作，不论模型置信度多高，都强制进入 HITL。

## Recap

- Tool 的护栏必须在运行时生效，因为调用决定来自概率模型。
- Schema、幂等、权限、审计是四项上线门槛。
- 契约不仅描述正常输入输出，还要写清禁用范围、失败码和审计字段。
- 工具先做风险归类，再配置对应控制；模型的“自信”不能替代审批。
