# 导学 06：怎样把 Copilot 的每次动作管住？

## 一句话理解

端到端实践把工具契约、权限、审批、幂等、回退和追踪接到同一个控制面，再用成功、故障和高风险路径检验整条链路。

## 用生活打比方

继续我们的物流配送中心。信息台先展示可办理的业务和规则，真正出库要经过另一道操作闸门。相同作业单再次送来时，系统凭内容指纹找到原结果，避免重复出库。特殊货物先冻结作业单，主管批准后还要核对内容没有变化。查询线路故障时改用留有来源记录的备用清单。每次等待、批准和出库都写入可长期保存的追踪记录。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **发现与执行分离** | 查询有哪些工具只会展示清单和规则，真正改数据要进入独立的受控入口。 |
| **渐进式披露（Progressive Disclosure）** | 先看简短工具清单，选中候选后再读取详细规则，减少无关信息。 |
| **稳定指纹** | 把请求内容算成稳定标记，相同请求再次到达时直接复用原结果。 |
| **人工审批** | 高风险动作先保存现场并暂停，批准后核对原请求再继续。 |
| **失败回退** | 主检索出错后读取带来源的缓存，同时记下失败原因，防止现场编答案。 |
| **动作血缘（Action Lineage）** | 保存工具、数据、证据、提示词、模型和技能包信息，方便追查一次动作。 |
| **持久化** | 把重复请求、审批现场和动作记录写进可靠存储，服务重启后仍能恢复。 |

## 避坑提醒

- **以为看到工具清单就能直接执行**：清单和详细契约只用于发现，危险动作还要经过校验、权限和审批控制。
- **以为请求标识相同就可以复用结果**：还要核对请求内容的稳定指纹，防止参数变化后误用旧结果。
- **以为批准后可以按新参数执行**：恢复前必须比较审批前后的请求摘要，内容变化就不能继续。
- **以为缓存能返回内容就算回退成功**：缓存结果还要带证据来源、主链错误和追踪记录。
- **以为内存日志足够排查问题**：幂等记录、审批现场和动作血缘需要持久化，才能在重启后恢复和追查。

## 一句话总结

> **用成功、故障和审批演练验证控制面，并确保重复动作被拦住、请求未被篡改、每一步都能恢复和追踪。**
