# 导学 02：工具越多，为什么越要收回模型的选择权？

## 一句话理解

工具路由与失败回退解决两件事：Agent 该选哪个工具，以及选错或调挂了之后怎么接。靠的是规则筛选、窄范围判断和预设的降级路径。

## 用生活打比方

继续我们的物流配送中心。调度台按任务类型分流，查件走查询通道，改地址走订单维护通道，出库走仓库作业通道。员工面前只出现和当前任务相关的岗位，不用从几十个选项里挑。如果实时查询挂了，系统先按规则重试，不行就读缓存（但会标明数据截止到几点），再不行就通知值班人员，最后给客户一个统一的暂不可查说明。高风险出库走固定流程，不由员工临时发挥。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **工具路由（Tool Routing）** | 根据请求类型和风险等级，把任务送到对的工具或固定流程。 |
| **规则加模型（Rules plus LLM）** | 代码先把候选范围缩窄，模型只负责处理剩下的少量判断。 |
| **显式工作流（Explicit Workflow）** | 执行顺序写在代码里，模型只在限定环节做决策。 |
| **失败回退链（Fallback Chain）** | 主工具挂了之后的预设路径，按重试、备用结果、转人工、降级响应的顺序往下走。 |
| **优雅降级（Graceful Degradation）** | 完整服务暂时不可用时，返回有限但可信的结果，同时告知用户有什么限制。 |
| **证据锚点（Evidence Anchor）** | 知识查询返回的具体来源位置，方便核对答案是不是有依据。 |

## 避坑提醒

- **以为把所有工具交给模型就是更灵活**：候选越杂，查询和写入越容易选错。先用规则筛一轮，模型的判断才靠谱。
- **以为工具失败就是继续重试**：没有上限的重试会占住资源，每类失败都该有明确的停止条件和下一步去哪。
- **以为缓存结果就是实时结果**：用缓存兜底可以，但必须标明数据已经过时，否则用户会按旧状态接着操作。
- **以为知识检索就是独立系统**：把它包装成受控工具，路由、回退和审计规则才能统一复用。

## 一句话总结

> **风险越高、流程越明确，控制权越该放在代码和可测试的工作流里。**
