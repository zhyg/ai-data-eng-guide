我们必须从高层视角审视契约的编辑。生产中最怕的是工具仅靠函数名约定，而无明确规范。函数名背后应包含权限、幂等性、失败码及是否需要人工审批等内容。因此，我们需将契约定下来，包括必填字段如名称、模式、描述、输入输出等。 此外，allowed_roles 字段决定了哪些角色可以调用该工具，确保权限管理。审计相关字段则规定了审计日志的内容，以便在问题发生前做好记录。最后，高风险动作应通过人工HITL环入进行审批，避免将风险判断交给大模型。 以 ticket update 契约为例，这是一个受控动作的样板，尽管它不是真实退款系统或完整工单系统。这个工具是第10周的核心工具，可用于未来对接 Slack 发消息等场景。
CM改库状态，如财务发起退款，应遵循特定模板。关键字段包括op_permission，它定义了允许的操作。operation是枚举值，不能随意编写，只能使用预定义的操作名。此外，还有风险等级字段，这也是一个枚举值，由规则层或工作流程提供，确保不会任意编造。 某些操作，例如退款和金融风险处理，需要触发required_approval进行审批。这些条件可以在审计Audit中查看。整个过程中，输入和输出的格式也需严格遵守。
输出格式必须包含特定条件。这是一个样板，用于高风险可控写入的工具契约。受控Agent的核心在于模型是否有资格调用工具及其追责机制。 查询knowledge search本质上是读取而非写入。RAG的主要问题在于检索不到时，大模型可能会生成错误答案或引用混乱。因此，必须携带证据锚点、trace_id和release_id等字段。 输入schema限定了query、product_line、model_list、top_k和min_score等参数。输出要求每个结果中都必须包含证据锚点，并且幂等键内需有特定属性以支持结果复用。HITL条件下，min_score也是必需的。
当 score 小于 0.4 时，会进入 pause_and_notify 状态，意味着在低自信度情况下不应强行作答。接下来我们来看看工具层。工具层主要涉及 tools 目录下的 registry.py 文件，它负责发现、检验和导出工具的描述，但不执行工具。 工具系统中，发现工具和执行工具必须分开，否则直接调用工具存在安全风险。例如，registry.py 中的 discover 方法通过读取契约文件和合约模式 JSON 来生成 for contract 对象，并导出兼容 OpenAI function code 和 MCP 的描述。
更接近于契约，而不是让模型自由发挥。注意属性设置和MCP工具的强调点，即危险工具需让上层客户端知晓。幂等性在生产环境中非常重要，例如退款操作在网络不稳定时可能被重试多次，后端必须支持幂等以避免重复处理。 stable_json将payload转换为稳定的JSON格式，确保字段顺序不影响摘要。stable_digest生成一个哈希指纹，用于Argus的digest和payload的digest。从契约的幂等属性中提取字段，生成稳定的幂等键。 fallback.py主要解决主链故障时的降级问题。例如，在向量库超时的情况下，不能让大模型现场编造答案。降级策略可以保证系统的稳定性和可用性。
在处理过程中，如果遇到重试、缓存或权限问题导致失败，最终可以通知人工介入。总链路失败的条件包括返回 fallback result、记录 fallback attempt 和生成 graceful_response 或 fallback exhausted。 HITL（人在环上）在代码中非常重要。生产环境中，首先将请求摘要、触发原因和 trace_id 存储为快照，然后暂停等待人工审批。审批通过后，通过异步调用恢复现场。注意，HITL 并非简单的确认框，而是包含特定策略的 UI 按钮。
我们通过读取契约中的条件，逐条判断是否满足HITL的要求。这些条件包括简单的条件和action policy。在课堂上，我们主要讨论内存事件，但生产环境中需要将数据入库。这是因为内存中的数据是临时的，一旦丢失就无法恢复，因此通常会将其存储到硬盘上。 血缘记录类似于行车记录仪，它不仅记录模型操作的结果，还记录了基于哪些数据快照、证据、Prompt、模型版本等信息。通过action event记录这些对象，并使用event_id和trace_id进行追踪。最终，这些信息会被绑定在一起，形成完整的血缘记录。
我们使用了一个 openlineage_event 组件，将内部事件转换为 openlineage_event 能识别的对象。这样做是为了在后续的评测或观测中，能够更好地进行关联。 还有一个 build_action_lineage_event，从 payload 中抽取控制字段，生成以 act 开头的事件 ID。这个过程是整个逻辑的一部分。 copilot.py 是第 10 周的主要工作，它是一个工具执行控制面，称为 controlled Agent。这个工具可以用来控制外部模型的接入。 在 invoke 方法中，首先注册 tool name，验证 JSON Schema 是否符合契约，检查权限是否通过，并评估 HITL 的 policy 策略。整个流程非常清晰。
这就是创建我们的申请点，大家可以看下它如何将整个链路串起来。首先验证工具是否存在，如果不存在则不进行调用；接着验证参数是否合规，不合规则由执行器兜底处理；然后检查角色是否有权限调用该工具，例如 Redis 不能执行 bidding oops 动作；之后确认能否命中 HITL，如退格和金融动作，若未命中则暂停；再者检查幂等性，重复请求时必须缓存结果；最后在动作执行后，检查是否写入血缘关系，以保证生产可审计性。 接下来我们来看 Tool API 和数据库落点。先看一下 service 层的 Tool API 是如何构建的，以及路由层的 APR tool contract。这层是给外部系统查看的，只读，用于告知前端控制台、MCP 客户端或 OpenAI Tools 客户端现有工具及其契约。这个接口仅用于发现工具，并非执行危险动作。

向量检索失败后，我们需要走缓存并记录证据。失败本身并不可怕，真正可怕的是无法观测到问题。 我们的 tool API 能够发现并导出工具契约，服务层只负责暴露工具而不执行危险操作。在第二个单元测试中，我们测试了一些相关内容。 实验3包含三个场景：一是顺利进行的情况；二是降级场景；三是HITL（人机交互学习）场景。 在 Happy Path 场景中，第一次请求成功执行，第二次相同的请求则直接从缓存中获取结果，两次请求的 nameage 和 entity_id 保持一致。
我们应该在文件中正确执行这一操作，以确保第二次可以复用第一次的结果，避免重复生成act。这称为幂等命中。接下来，请注意观察cache flow中的关键字段，如lineage events entries中的event_id、trace_id和tool_name等，这些都是我们规定的标准。 完成happy pass后，我们将检查fallback降级部分的测试。通过执行Demo中的e2e_fallback，我们可以看到导致fallback的具体原因。核心问题在于主索引检索失败后使用了缓存进行降级处理。记得之前提到的枚举值吗？它在这里起到了作用。
在 fallback items 中，存在不同的缓存价值策略或层次。首先，当主检索失败时，系统会记录下这一情况；其次，一旦检索失败，系统将使用缓存数据，并记录错误原因，整个过程非常清晰。 接着，我们检查结果中的证据锚点。可以看到，results lineage 记录得非常清楚，在 result 中确实存在锚点。这便是我们的 fallback 测试，整体来说相当规范。 完成 fallback 测试后，我们将进行 HITL 测试。该测试分为两步：申请前和申请后。第一步是在申请前等待，第二步是申请后批准。
