# 导学 04：故障发生时，为何不能只找最有经验的人？

## 一句话理解

把故障按基础设施、数据、模型、服务和合规分类，再将症状、响应时限、责任团队、诊断、修复和回滚步骤整理成可搜索、可执行、可演练的 Runbook。

## 用生活打比方

继续我们的连锁餐厅。门店打烊前发现冷库温度异常，新值班经理如果只会给总厨打电话，处理速度和结果就完全取决于某个人是否在线。

成熟的餐厅会有应急索引。温度告警自动附上冷库故障手册，里面写清先检查什么、哪些食材要隔离、谁负责联系维修、什么情况下停用冷库、怎样切到备用存储。新人照着步骤也能完成基本处置。

事故结束后，团队把告警特征、诊断过程、修复动作和回退办法整理进手册，再安排模拟演练。传感器和自动化助手可以完成查状态、汇总证据、执行低风险操作；停业、销毁食材或影响顾客权益的决定仍由负责人批准。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **Runbook** | 针对一类故障的操作手册，写明如何识别、由谁负责、按什么顺序诊断和修复、失败后怎样回滚。比如针对数据库内存溢出或接口超时编写具体的恢复步骤。 |
| **Runbook 索引** | 把应急手册按基础设施（Infra）、数据（Data）、模型（Model）、服务（Service）、合规（Compliance）分类，并为每份手册记录症状（symptoms）、响应时限（SLA）、责任人（owner）和 Skill Pack。告警系统可以直接匹配对应手册。比如系统通过告警特征直接把对应的处理手册和责任人找出来。 |
| **症状字段（symptoms）** | 描述某份手册适用的告警特征。比如向量库响应变慢或模型请求超时，系统可用这些特征匹配正确的 Runbook。 |
| **Skill Pack** | 把 Runbook 中可自动执行的步骤封装成工具。人可以调用，Agent 也能在授权范围内运行。比如把系统重启和日志提取打包成命令供自动调用。 |
| **事故复盘（postmortem）** | 事故结束后记录发现方式、时间线、根因、修复和回滚的材料。它可以直接生成新的 Runbook 草稿，减少重复整理。比如将一次服务熔断的排查过程和处理步骤记录下来，用来生成新的手册。 |
| **模拟故障演练（Wheel of Misfortune）** | 随机抽取故障场景和值班人员进行模拟演练，再根据执行结果更新手册，避免步骤和凭据长期失效。比如每周抽一名值班人员模拟处理真实告警，发现命令过期就马上更新。 |
| **Agentic SRE** | 让 Agent 持续观察告警、查询日志、分析根因，并在授权范围内按 Runbook 执行恢复动作。比如让智能助手自动查日志定位错误，并在授权下执行预设的修复操作。 |
| **人在回路（HITL）** | 高风险动作执行前必须由人确认。比如回滚生产、冻结服务或修改客户数据，Agent 只能提供证据和建议。 |

## 避坑提醒

- **以为应急能力就是找到最有经验的人**：个人休假、离职或无法联系时，团队会立刻失去处理能力。经验要写进可搜索、可执行的 Runbook。
- **以为写几篇故障文档就有了 Runbook 体系**：文档散落且没有分类、症状、响应时限、责任人和告警关联，事故现场仍然找不到或没人负责。索引必须让告警自动匹配手册，并明确响应时限与责任团队。
- **以为 Runbook 写完就会一直有效**：系统、命令和凭据都会变化，长期不演练的步骤可能在真正故障时失效。模拟演练后要立即修订发现的问题。
- **以为事故复盘和 Runbook 应该分别重写**：两份材料包含大量相同的症状、诊断和修复信息，重复维护容易漂移。应从复盘内容生成手册草稿并加入索引。
- **以为 Agent 可以自主执行所有恢复动作**：回滚生产、冻结服务和处理客户数据会扩大影响面，必须保留人工审批。Agent 更适合查证据、做诊断和执行低风险步骤。

## 一句话总结

> **应急体系要让告警能找到手册、手册能够执行、事故能够沉淀、步骤持续演练，高风险决定始终由人负责。**
