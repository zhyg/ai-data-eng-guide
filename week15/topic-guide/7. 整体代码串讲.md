# 导学 07：面对整套项目代码，应该从哪里读起？

## 一句话理解

本节通过三个核心业务对象、七层架构、三个责任平面和三段代码阅读旅程，串联起从证据生产到治理发布的全套业务因果链。

## 用生活打比方

继续我们的连锁餐厅。新运营团队接手整套体系时，如果从每台设备的说明书开始读，很快就会迷失在细节里。更有效的方式是跟着一份订单走完整条链路。

食材从供应商进入验收区，保留原始批次，再经过清洗、切配和分层存储，最后变成可供门店使用的菜品与指标。顾客下单后，前台确认门店和权限，厨房按当前菜单版本取用合格食材，特殊操作交给经理审批，完成后记录服务质量和处理经过。

看全局时还要区分顾客看到的门店界面、负责加工食材的厨房体系，以及制定配方、权限、发布和回退规则的运营控制体系。任何改动都要说明影响哪张订单、使用哪份依据、属于哪版菜单。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **业务上下文（Case / Ticket）** | 当前客服问题及其业务上下文，包含租户、产品线、SLA、会话和允许执行的动作。它决定系统正在为谁处理什么事。比如系统接到一个退货请求，它得先确认这是哪个客户发起的、属于什么商品线、服务承诺时间是什么，这样才能确定接下来该怎么处理。 |
| **事实依据（Evidence）** | 回答和决策可以核对的事实依据，连接原始来源、内容切片、索引、动作、血缘与审计记录。比如系统回复客户说支持七天无理由退款，这个回答的背后必须能明确关联到退换货政策文档里的具体段落，绝不能凭空捏造。 |
| **发布版本（Release）** | 一次可复现的系统能力组合，绑定数据、索引、提示词、图、模型和技能版本，约束本次运行使用哪套内容。比如每次系统升级，都会把当时的业务文档、检索规则和AI模型绑定打包成一个快照，确保在这个版本下不管怎么测，结果总是稳定的。 |
| **七层架构** | 按来源、原始落盘、解析标准化、Lakehouse、资产检索、产品执行、保障治理划分系统能力，帮助定位模块处于哪一层。比如一份售后说明书从外部进入系统，要依次经过原件保存、格式解析清洗、建立索引等好几个层次的加工处理，最终才能被问答功能拿来用。 |
| **三个责任平面** | 用户面负责界面和业务体验，数据面负责生产事实与证据，控制面负责契约、权限和发布决策。横切的测试与可观测为它们提供验证。比如客服在网页上提问是用户面管，系统怎么把文档变成结构化知识是数据面管，而客服能不能查到机密信息则是控制面管，大家各司其职。 |
| **一条主线、三段旅程** | 整套系统沿证据生产、证据消费、治理发布展开。原始输入先变成资产，再用于回答和动作，最后进入评测、追踪、灰度和回滚。比如系统把原始文档处理成知识是第一段旅程，拿着这些知识去回答客户问题是第二段，而监控回答准不准、耗时多久就是第三段。 |
| **契约体系** | Data、Service、Tool、Release 契约分别约束数据结构、服务输入输出、业务动作和版本组合，让模块交接有稳定边界。比如开发团队约定好，凡是调起问答服务，发来的请求里就必须带上工单号和用户身份标识，漏掉任何一个都会被直接拒绝，这就是契约的作用。 |
| **契约测试与健康检测** | 用机器校验检查契约、采集幂等、资产状态、离线质量、在线 SLO、请求追踪、发布门禁和整组回滚是否正常。比如每次有新功能要上线，系统都会自动跑一遍脚本，看看各种数据格式对不对、回答有没有变慢，只有全绿通过了才允许真正发布。 |

## 避坑提醒

- **以为逐个读完函数就是理解了系统**：函数只能展示局部实现，无法说明业务因果和责任边界。先看 README、架构、核心对象和主线，再进入具体目录。
- **以为契约就是给人看的说明文档**：契约还要由测试自动验证输入、输出、失败条件、角色和审批要求，未通过的对象不能进入下游。
- **以为浏览器或模型直接决定数据库行为就是正常的架构**：外部请求只能提出受限意图，Product API 恢复可信身份，Tool Contract 再执行权限、幂等、证据和风险校验。
- **以为回滚服务代码就是恢复了旧系统**：AI 行为还依赖数据、索引、提示词、模型、技能和图。回滚要切回整组 Release，避免组件版本互相错配。
- **以为测试和可观测就是开发末尾补上的工作**：契约、资产检查、评测、trace、SLO 和发布健康都贯穿主线，它们共同证明每次输入、回答、动作和发布可信。

## 一句话总结

> **读整套项目时先找业务对象和因果链，再确认架构层、责任平面、契约输入输出与 Release 边界，最后下钻实现细节。**
