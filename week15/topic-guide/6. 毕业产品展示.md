# 导学 06：一套企业 AI 产品，怎样把问答、审批和追踪连起来？

## 一句话理解

毕业产品以工单为业务入口，把带证据的检索问答、受契约控制的业务动作、人工审批、统一指标、发布版本和运行健康检测装配进同一套系统。

## 用生活打比方

继续我们的连锁餐厅。顾客反馈某道菜与菜单说明不符，前台先调出订单、门店、菜单版本和历史沟通，再查配方、供应批次与操作记录，给出带来源的解释。

简单问题可以从菜单和记录中直接检索。涉及多个门店、供应商和时间段的问题，需要沿着它们之间的关系逐步核对；要总结整条供应链的共性问题，还要汇总多个环节的信息。每个结论都附上依据和查询记录，方便主管复查。

前台补充普通备注可以直接完成。退款、额度调整或影响顾客权益的操作要写明理由，连同订单和证据交给主管审批。总部统一定义各门店的运营指标，当前运营包同时锁定食材批次、菜单、审批规则和设备设置。开店前还要检查前台、厨房、仓储与审批系统是否就绪。系统会记录整次处理经过，出问题时能够沿记录查回去。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **工单上下文** | 与当前问题有关的租户、产品线、状态、版本、SLA 和历史时间线。系统先恢复这些信息，才能按正确权限和业务范围回答。比如遇到客诉，系统要先弄清这是哪个客户的订单、属于什么产品线、处理有没有超时，才能给出正确的答复。 |
| **混合检索（Hybrid RAG）** | 同时使用语义相近和关键词精确匹配来找资料，再合并并重排结果。它适合具体事实、错误码和操作步骤类问题。比如查找某个特定错误码的解决办法，系统会同时用关键词匹配错误码字眼，并用语义理解你的真正意图，最终把最准确的文档找出来。 |
| **图检索增强生成（GraphRAG）** | 多跳路径沿实体关系分步取得证据，Global 路径汇总多个文档或关系社区。前者适合跨条件推理，后者适合全局主题和流程归纳。比如要查某个报错现象具体影响了哪些产品线，系统会沿着报错记录和产品线之间的关系链，顺藤摸瓜一步步找出所有关联信息。 |
| **证据标识（evidence id）** | 给每条可引用依据分配稳定标识，并关联来源文档、章节、相关性和发布版本，方便回答、动作和审计共同引用。比如系统的每句回答都会关联一个唯一编号，点击就能直接跳转到原始操作手册的对应段落，证明这确实是有据可查的。 |
| **工具与人在回路（Tool / HITL）** | 工具契约（Tool Contract）规定角色、参数、证据、幂等和风险条件。低风险动作通过校验后执行，高风险动作保存为待审批状态，由主管批准或拒绝。比如客服发起了一个调整用户账单金额的动作，系统不会立刻去改数据库，而是把这个操作拦下来生成一条待办，等主管确认无误后才真正放行。 |
| **指标注册表（Metric Registry）** | 为每个运营指标保存唯一名称和统一语义。产品只能读取这些定义，不能让浏览器临时拼接查询口径。比如“日均工单量”在系统里只登记一种计算规则，所有业务看板都必须按这个规则来显示，防止不同部门自己查出的数据打架。 |

## 避坑提醒

- **以为给客服一个聊天框就是完成了企业产品**：脱离租户、产品线、工单状态和角色权限的回答无法安全进入真实业务。入口要先恢复可信的工单上下文。
- **以为答案读起来通顺就是可以交付的标准**：模型可能补出资料中没有的内容。回答必须附带证据标识、来源和版本，用户反馈也要能回到同一条链路。
- **以为所有问题都该走同一条检索路径**：具体事实、跨文档推理和全局归纳需要的处理方式不同。统一走复杂路径会增加时延和成本，统一走简单路径又可能答不全。
- **以为模型判断低风险就是可以直接改业务数据**：动作权限和风险必须由工具契约执行，高风险请求要持久化并等待人工审批。
- **以为本地演示能跑通就是生产容量足够**：复杂图检索和本地模型可能在并发或资源不足时变慢。上线前还要检查服务是否就绪，并验证容量、超时、缓存、降级路径和 Release 一致性。

## 一句话总结

> **企业 AI 产品要让每次请求同时带着可信上下文、证据、动作权限、统一指标和 Release，并能用 trace 与健康检测验证完整链路。**
