# 导学 06：一套企业 AI 产品，怎样把问答、审批和追踪连起来？

## 一句话理解

毕业产品以工单为业务入口，把带证据的检索问答、受契约控制的业务动作、人工审批和全链路追踪装配进同一套系统。

## 用生活打比方

继续我们的连锁餐厅。顾客反馈某道菜与菜单说明不符，前台先调出订单、门店、菜单版本和历史沟通，再查配方、供应批次与操作记录，给出带来源的解释。

简单问题可以从菜单和记录中直接检索。涉及多个门店、供应商和时间段的问题，需要沿着它们之间的关系逐步核对；要总结整条供应链的共性问题，还要汇总多个环节的信息。每个结论都附上依据和查询记录，方便主管复查。

前台补充普通备注可以直接完成。退款、额度调整或影响顾客权益的操作要写明理由，连同订单和证据交给主管审批。系统还会记录这次处理经过哪些服务、用了哪版菜单和数据、花了多长时间，出问题时能够沿记录查回去。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **工单上下文** | 与当前问题有关的租户、产品线、状态、版本、SLA 和历史时间线。系统先恢复这些信息，才能按正确权限和业务范围回答。 |
| **混合检索（Hybrid RAG）** | 同时使用语义相近和关键词精确匹配来找资料，再合并并重排结果。它适合具体事实、错误码和操作步骤类问题。 |
| **GraphRAG 多跳** | 沿实体之间的关系分步查找证据，适合答案需要跨多个条件或文档才能得到的问题。每一步都保留使用的资料。 |
| **GraphRAG Global** | 汇总多个文档或关系社区的内容，再生成全局主题和流程摘要，适合整体归纳类问题。 |
| **证据标识（evidence id）** | 给每条可引用依据分配稳定标识，并关联来源文档、章节、相关性和发布版本，方便回答、动作和审计共同引用。 |
| **工具契约（Tool Contract）** | 规定业务动作允许哪些角色调用、需要哪些参数和证据、怎样保证重复请求不重复执行，以及什么风险必须审批。 |
| **人在回路（HITL）** | 将高风险动作保存为待审批状态，由主管查看理由、风险和证据后批准或拒绝，模型不能直接完成。 |
| **链路标识（trace id）** | 串起一次请求经过的产品入口、检索、模型、工具和审批步骤，便于定位耗时、错误、数据和版本来源。 |

## 避坑提醒

- **以为给客服一个聊天框就完成了企业产品**：脱离租户、产品线、工单状态和角色权限的回答无法安全进入真实业务。入口要先恢复可信的工单上下文。
- **以为答案读起来通顺就可以交付**：模型可能补出资料中没有的内容。回答必须附带证据标识、来源和版本，用户反馈也要能回到同一条链路。
- **以为所有问题都该走同一条检索路径**：具体事实、跨文档推理和全局归纳需要的处理方式不同。统一走复杂路径会增加时延和成本，统一走简单路径又可能答不全。
- **以为模型判断低风险就能直接改业务数据**：动作权限和风险必须由工具契约执行，高风险请求要持久化并等待人工审批。
- **以为本地演示能跑通就代表生产容量足够**：复杂图检索和本地模型可能在并发或资源不足时变慢。上线前还要验证容量、超时、缓存和降级路径。

## 一句话总结

> **企业 AI 产品要把工单上下文、证据、动作权限、人工审批和 trace 绑定在同一次请求中，才能安全进入业务流程。**
