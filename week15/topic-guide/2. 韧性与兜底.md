# 导学 02：上游服务出故障，AI 怎样还能给出回应？

## 一句话理解

提前声明从完整能力到最小可用服务的降级路径，优先守住用户有回应和不泄露 PII，再配合熔断、缓存和限流应对模型、检索与流量异常。

## 用生活打比方

继续我们的连锁餐厅。午餐高峰时，某种食材断供、烤箱故障、配送变慢都很常见。门店不能把后厨错误单直接递给顾客，也不能让所有订单一直等着。

餐厅会提前准备处理顺序：先按完整菜单出餐；主厨工位忙不过来就换备用工位；复杂设备坏了就暂停售卖依赖它的菜；部分食材缺货就改推能正常制作的简餐；后厨都无法工作时，提供已备好的安全餐品、改约其他门店或转人工处理。每种处理都要给顾客明确回应，食品安全底线不能因降级而放松。

门店备好的常点菜和厨房预处理食材既减少日常工作量，也能在供应链故障时继续出餐。归档库保存完整出餐记录和问题案例，供事故复盘使用，不直接拿来给顾客出餐。菜单换版时只处理受影响的备料，不把所有库存都扔掉。订单太多时，前台按厨房产能放单，短时高峰允许排队，等待过久就明确告知并给出后续安排。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **五级降级链** | 预先排好一组从完整功能到最低可用服务的替代路径。每一级都要给用户可理解的回应并守住 PII 红线，再尽量保留答案质量和引用。比如大模型不可用时换备用模型，图检索故障时改走普通检索，在线路径都失败时返回缓存或转人工。 |
| **降级事件（degradation event）** | 每次系统切换到较低能力时留下的记录，说明从哪条路径切到哪条路径，方便面板显示当前状态并支持事后复盘。比如系统从复杂的图检索自动切换到普通检索时留下一条打点记录。 |
| **四级缓存** | 把完整回答和中间结果保存在不同位置。离用户近的缓存响应快，组件缓存复用计算结果；冷存储保留完整链路和问题样本，用于事故兜底与复盘，不参与在线回答。比如在外层直接返回常见问题的完整答案，在内部保留具体文档段落的计算结果。 |
| **发布标识（release_id）驱动的精细化失效** | 发布新版本时先看数据、提示词或模型中哪部分变了，再只清除受影响的缓存。无关结果继续保留，避免缓存突然全部失效。比如发布时只修改了提示词，那就只清除最终生成的答案缓存，保留已经算好的向量缓存。 |
| **令牌桶** | 按固定速度发放请求额度，同时允许短时积累一些额度应对突发流量。额度用完后，请求进入等待或降级处理。比如给核心用户分配更大的额度池，在流量突增时确保他们能优先被处理。 |
| **统一路由（LiteLLM Router）** | 集中声明模型之间的备用顺序，并统一处理负载均衡、超时和重试，让业务服务少写一套模型切换逻辑。比如主力模型超时没有反应时，通过它自动把请求转给预设好的备用模型。 |

## 避坑提醒

- **以为多重试几次就是有韧性**：上游持续故障时，重复请求会继续占用资源并放大延迟。韧性需要可替代的模型、检索、缓存和人工路径。
- **以为降级要等值班人员手工切换**：人工发现和操作都需要时间，用户会先遇到白屏。每条降级路径要提前声明，由故障条件自动触发并留下记录。
- **以为发布新版就该清空所有缓存**：无关缓存被删除后，大量请求会同时压向刚恢复的上游。应根据数据、提示词和模型的变化范围精细失效。
- **以为限流就是把技术错误返回给用户**：用户需要知道当前是否能处理、要等多久、还有什么替代方式。优雅排队和兜底回答应屏蔽内部错误细节。
- **以为缓存只用于降低成本**：上游不可用时，缓存还能继续回答高频问题。它同时承担性能、成本和故障兜底职责。

## 一句话总结

> **把降级路径、触发条件和用户回应提前写清，始终守住 PII 红线，再用缓存与限流保住核心服务。**
