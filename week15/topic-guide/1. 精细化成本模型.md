# 导学 01：AI 每回答一个问题，钱到底花在哪了？

## 一句话理解

把一次 AI 查询拆成生成、检索、向量处理、存储和缓存等成本，再关联到具体请求与发布版本，团队才能找到真正值得优化的环节。

## 用生活打比方

这一周我们用「连锁餐厅的中央厨房与门店运营」来串起所有概念。

中央厨房每天采购食材、预处理半成品，再由门店接单、烹饪和出餐。财务如果只看到整月采购与水电总额，就不知道哪道菜耗料多、哪家门店浪费大、哪版菜单让成本突然上涨。

成熟的餐厅会把每份订单拆开记账：食材用了多少，哪道工序耗时，是否调用了昂贵设备，常点菜能否提前备好。简单小菜走短流程，复杂套餐才动用全部工位。菜单换版后，订单还要标明使用哪一版配方，方便发现哪次调整让成本上升。

AI 系统也要按请求拆账。高频问题可提前缓存，简单问题走轻量路径并使用轻量模型，重复内容避免再次处理，离线任务集中成批完成。LiteLLM 网关还能设置硬预算上限，并按请求和发布版本归因模型花费。这样才知道工程时间该花在哪里。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **每千次查询成本** | 把一段时间内的总花费换算成固定查询量对应的成本，方便比较不同问答路径。比如普通检索问答和需要多轮工具调用的问题，可以用同一单位判断谁更贵。 |
| **题型路由** | 先判断问题类型，再选择合适的处理路径。比如简单事实查询走普通检索，跨文档归纳才使用更复杂的图检索。 |
| **向量表示（Embedding）复用** | 同一段内容已经生成过向量表示时，后续直接使用已有结果，避免重复计算和付费。比如处理相同的文档段落时直接取已有的向量结果，不再发给模型重新计算。 |
| **语义缓存** | 问法不同但意思接近时，也能复用已有答案。它会设置严格的相似条件，并按租户和发布版本隔离，避免拿错答案。比如两个用户的问法只差一两个助词，意思完全一样时，可以直接给出缓存好的答案。 |
| **提示缓存（Prompt Caching）** | 把系统提示、固定说明和长期不变的上下文保存起来，后续请求不再重复处理这些内容。比如把大段的系统设定或长篇参考资料存起来，后面的每次提问就不需要重新算一次这些内容的开销。 |
| **成本监控面板** | 按时间、成本类别、请求链路和发布版本展示花费，让异常增长能够被发现并追到来源。比如通过面板发现某个版本发布后，某条处理路径的花费突然变高，从而快速定位修复。 |

## 避坑提醒

- **以为成本管理就是看供应商总账单**：总账只能说明花了多少钱，不能说明哪类请求、哪个组件或哪个发布版本造成了增长。成本要进入请求链路和版本记录。
- **以为换便宜模型就是最有效的降本**：普通问题如果误走复杂检索或多轮工具调用，处理路径带来的浪费可能更大。先把题型路由做对，再对简单问题进行模型降级，并通过统一网关控制预算。
- **以为成本最高的环节就是最该先优化的环节**：有些优化开发周期长，节省却有限。应比较节省金额和工程投入，先做回报更快的缓存、路由与复用。
- **以为语义相近就可以直接复用答案**：相似条件过宽会把不同问题当成同一个问题，多租户或不同版本之间共用缓存还可能带来错误与泄露。缓存必须设置严格条件并做好隔离。
- **以为离线任务也该逐条走实时接口**：不要求立即返回的向量处理和评测适合批量执行，逐条调用会增加请求开销和成本。

## 一句话总结

> **先把成本归因到请求、组件和发布版本，再按投资回报率安排缓存、路由、模型降级、复用和批处理，并用统一网关守住预算。**
