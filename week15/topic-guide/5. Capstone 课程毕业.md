# 导学 05：学完课程后，拿什么证明自己真的会做？

## 一句话理解

Capstone 把整门课程的代码、架构、评测、发布、合规和运维材料整理成一套可运行、可检查、可讲解的工程作品。

## 用生活打比方

继续我们的连锁餐厅。总部准备把中央厨房和门店方案交给新的城市运营团队，只做一桌好吃的菜还不足以证明这套体系能长期经营。

完整交付要让接手方拿到配方与供应流程，能照说明启动门店；看到食材验收、试营业和服务指标，知道质量经过检查；拿到菜单版本、变更记录和应急手册，遇到问题能追查和恢复；还要有架构图、合规材料与讲解方案，让监管、合作方和新员工都能理解。

作品展示也要先讲顾客遇到什么问题，再演示正常出餐、需要经理批准的特殊处理和一次问题复盘。数据、制度和判断依据放在后面支撑结论，听众才能评估整套运营能力。

## 关键概念

| 概念 | 大白话解释 |
| :--- | :--- |
| **毕业作品（Capstone）** | 把课程中分散的能力组合成一个完整项目，用可运行系统和工程材料证明自己能交付企业级 AI 服务。比如向面试官展示一个包含代码、架构和运维记录的完整智能客服系统。 |
| **工程产物（Engineering Artifacts）** | 运行系统时产生并持续维护的材料。比如系统上线后留下的发布记录、服务契约、评测结果和应急手册等。 |
| **发布清单集合（Release Manifests）** | 保存每次发布绑定的数据、索引、提示词、模型、技能和图版本，用来证明线上组合可复现、可回滚。比如记录上线时用了哪个版本的提示词和模型，出错时能立刻退回去。 |
| **评测报告（Eval Reports）** | 记录离线评测、业务 SLO 和版本对比结果，帮助评审判断系统质量是否达到门禁要求。比如用测试数据证明新版本的回答质量比老版本好，满足上线标准。 |
| **应急手册库（Runbook Library）** | 按故障类型组织的处理手册和演练记录，用来证明系统出了问题后有人知道怎样诊断、修复和回滚。比如把基础设施、模型和服务等各类故障的恢复步骤整理在一起，随时查阅。 |
| **八条工程承诺** | 用数据有契约、答案有证据、行为受控制、质量可量化、故障可定位、版本可回滚、监管可审计、长期可运营，检查作品是否真正具备生产能力。比如用可定位的故障和可回滚的版本，向评审证明系统是个可靠的生产工具。 |

## 避坑提醒

- **以为听完课程就等于拥有工程能力**：学习记录只能说明接触过内容。能运行的仓库、测试、发布记录和运维材料才能让陌生人检查实际能力。
- **以为一个能回答问题的 demo 就是完整作品**：企业系统还要控制动作、评测质量、追踪故障、管理版本、满足合规并准备应急处理。
- **以为答辩应该先展示用了哪些技术**：听众先关心解决了什么业务问题、结果怎样、风险如何控制。架构和工具应服务于这条叙事。
- **以为说回答很准就能证明质量**：主观描述无法复查。应展示评测方法、业务目标、版本对比和失败样本，让结论有数据依据。
- **以为项目做完后就不需要演进计划**：当前版本只证明此刻可用。后续复现、深入专题、真实落地和公开输出，决定作品能否持续体现能力。

## 一句话总结

> **完整 Capstone 要同时交付可运行系统、可验证证据、可恢复的运维资产和清晰说明，并为八条工程承诺提供可检查的证明。**
