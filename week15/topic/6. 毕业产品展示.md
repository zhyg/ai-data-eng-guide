# 6. 毕业产品展示

## 核心目标

本节不再展示单个脚本，而是把前 15 周的能力装配成一个可登录、可查询、可审批、可观测、可发布的企业级 AI 产品。

产品以客服工单为业务入口：系统必须基于真实证据回答问题，用策略和契约控制工具动作，用 HITL 审批高风险操作，并通过 trace、指标和发布记录实现全链路可归属、可追溯。

## 产品定位

OmniSupport 可以理解为一个“企业 Agent + 知识库 + 动作控制面”：

- 客服在工单上下文中提问，而不是进入一个脱离业务的聊天框。
- 回答必须附带来源文档、章节、相关性和 evidence id，模型不能自行编造事实。
- 低风险动作可直接执行；涉及资金、权限或敏感信息的动作必须进入审批。
- 每次问答和动作都关联 trace id，可回到完整调用链、模型和发布版本。
- 指标语义、发布对象和审计事件由控制面统一管理，浏览器不能绕过契约直接操作底层数据。

## 整体架构

业务与知识源 → 对象存储 / 事务库 → 文档解析与标准化 → Hybrid RAG / GraphRAG → 本地或商业模型 → 带证据回答 → Tool Contract 风险判定 → 直接执行或 HITL → OTel / Phoenix trace → 指标与发布治理

| 层 | 主要职责 |
| :--- | :--- |
| 产品界面 | 为客服和主管提供分权控制台、工单、问答与审批入口 |
| Product / RAG API | 恢复可信身份和业务上下文，路由检索与生成请求 |
| 检索层 | 支持向量、关键词、混合、本地图、多跳和全局摘要路径 |
| 模型层 | 默认使用本地模型，也可通过配置切换国产或海外商业模型 |
| Tool / HITL | 对备注、状态变更、资金调整等动作做权限、风险和审批控制 |
| 数据与资产层 | 管理工单、混合模态知识、索引、图和统一指标语义 |
| 可观测与治理层 | 记录 trace、指标、lineage、release_id 和审计证据 |

## 运行与权限边界

产品通过 8010 端口访问，界面至少区分客服与主管两类权限：

| 角色 | 主要能力 |
| :--- | :--- |
| 客服 | 查看工单上下文、提问、阅读引用、提交备注或动作请求 |
| 主管 / 管理员 | 查看待审批任务，核对风险、金额、证据和 trace 后批准或拒绝 |

演示环境主要使用本地 Qwen3-14B 模型。模型接口已经抽象为可配置层，可按资源和合规需求替换其他开源或商业模型。本地大模型便于调试与数据控制，但会明显占用 GPU、CPU 和内存，是演示中最主要的性能约束。

## 数据与知识资产

系统装载约 200 条接近真实业务的工单，并把多模态知识纳入同一证据链。

| 资产 | 作用 |
| :--- | :--- |
| 工单及时间线 | 提供问题、状态、优先级、产品线和历史处理上下文 |
| HTML / PDF 文档 | 提供可分页、可定位的产品与运维知识 |
| PNG / 音频等非结构化对象 | 验证多模态原件进入知识资产流程 |
| 结构化运营数据 | 支撑 KPI、风险和审批上下文 |
| 向量与关键词索引 | 支撑语义召回和术语精确命中 |
| GraphRAG 图 | 支撑多跳推理和全局归纳 |
| Metric Registry | 为指标提供唯一名称、语义和 release 归属 |

这些对象不是独立 demo，而是从 SaaS 与运营数据进入知识、指标和图资产，再由在线产品统一消费。

## 演示链路一：工单上下文中的证据问答

客服选中工单后，系统先恢复工单 id、租户、产品线、版本、SLA 和时间线，再把问题交给 RAG。演示中的问答链路是：

工单上下文 → 选择检索模式 → 召回 top-k 证据 → 本地模型生成 → 展示回答与引用 → 记录耗时和 trace id → 用户反馈

输出不只是答案，还包含：

- evidence id。
- 来源文档及章节。
- 检索和相关性分数。
- 当前检索配置和执行路径。
- 生成耗时与 trace id。

用户可以根据 trace id 对回答标记是否有用，使一次线上反馈能够回到对应证据、模型和版本。

## 演示链路二：多跳与全局摘要

系统支持 Hybrid RAG 和 GraphRAG 两类互补路径：

| 路径 | 适合的问题 | 处理方式 |
| :--- | :--- | :--- |
| Hybrid | 具体事实、错误码、操作步骤 | 合并语义和关键词召回，再重排 |
| GraphRAG 多跳 | 需要跨多个条件和文档逐步验证的问题 | 沿实体和关系逐步取得证据 |
| GraphRAG Global | 需要全局主题和流程归纳的问题 | 聚合社区或文档摘要后再生成 |

多跳演示会显示每一步使用的文档和反馈，而不是只返回最终结论。全局摘要对本地资源要求更高；演示中一次运行因本地模型承载不足未能及时返回，这也直接暴露了生产系统必须做容量规划、超时和降级的原因。

## 演示链路三：受控动作与 HITL

产品不仅回答问题，还能执行工单动作。动作按风险分流：

| 动作 | 风险处理 |
| :--- | :--- |
| 添加备注、普通状态更新 | 校验角色和幂等性后直接执行 |
| 涉及资金或信用额度的变更 | 必须填写理由并创建审批请求 |
| 高风险请求 | 携带 trace、风险类型、金额和 evidence id 进入主管审批 |

主管登录后可以看到完整上下文，再决定批准或拒绝。模型和浏览器只能提出受限意图，最终数据库行为必须经过 Tool Contract、角色策略和 HITL 控制。

## 核心数据模型

| 对象 | 关键内容 | 在链路中的作用 |
| :--- | :--- | :--- |
| Case / Ticket | tenant、产品线、状态、风险等级、SLA | 提供业务上下文和权限边界 |
| Timeline / Note | 工单历史与人工备注 | 记录业务状态变化 |
| Evidence | evidence id、来源、章节、分数、release_id | 证明回答依据来自真实知识 |
| Action | 工具意图、角色、幂等键、风险与结果 | 控制可执行的业务动作 |
| Approval | 金额、理由、证据、审批状态 | 持久化 HITL 流程 |
| Trace / Span | trace id、路径、模型、时延和状态 | 还原一次请求的完整执行链 |
| Metric | 名称、统一语义、值、data release id | 为运营面板提供唯一指标口径 |
| Release | data、index、prompt、model、skills、graph | 约束本次运行使用的系统版本 |

这些对象共同保证“谁在什么工单上，基于哪份证据，用哪个版本，执行了什么动作”能够被完整回答。

## 契约与健康检测

### 契约检查

- RAG 响应必须带引用、evidence id、trace id 和版本信息。
- Tool 请求必须校验角色、租户、幂等性、证据和风险等级。
- 高风险动作必须持久化为待审批状态，不能由模型直接执行。
- KPI 只能从 Metric Registry 读取定义，浏览器不能提交任意 SQL。
- 线上组件通过同一 release_id 绑定，避免数据、索引、Prompt、Graph 和模型漂移。

### 运行健康检测

- 启动时检查 Product API、RAG / Tool API、控制台、模型和存储进程是否就绪。
- 观察本地模型的 GPU、CPU、内存占用以及 10～30 秒级生成时延。
- 每次请求通过 trace id 检查从产品入口到检索、模型和动作的完整链路。
- 对 Hybrid、多跳、全局摘要分别观察成功率与耗时，资源不足时触发明确的超时和降级。
- 面板按工单、指标、release 和服务展示运行状态，异常结果能回到 trace 和 audit。

## 演示结论与限制

演示验证了工单问答、引用展示、低风险动作、HITL 审批、指标面板和全链路追踪可以在同一产品内闭环。主要限制来自本地模型资源：复杂 GraphRAG 全局摘要可能因算力和承载不足变慢或失败。生产化时应增加模型网关、容量基线、并发控制、缓存和 Week 15 的五级降级链。

## 本节交付物

- 可分角色登录的客服与主管控制台。
- 约 200 条工单及多模态知识资产。
- Hybrid RAG、GraphRAG 多跳与全局摘要入口。
- 带来源、分数、evidence id 和 trace id 的回答。
- 低风险直通、高风险 HITL 的动作控制链。
- 指标、trace、lineage、audit 和 release 治理面板。

## Recap

- 毕业产品以工单为业务入口，而不是脱离上下文的聊天 demo。
- 回答必须有真实证据，动作必须受角色、风险、幂等性和 HITL 控制。
- Hybrid RAG 解决具体事实，GraphRAG 解决多跳和全局归纳，两者共享证据与版本基础。
- trace id 把产品入口、检索、模型、动作、指标和发布版本连成完整证据链。
- 本地模型资源限制是演示中观察到的真实瓶颈，生产化必须补充容量、缓存和降级机制。
