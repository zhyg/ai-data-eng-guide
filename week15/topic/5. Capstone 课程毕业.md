# 5. Capstone 课程毕业

## 核心问题

听完课程、看过文档、跑过 demo，都不等于拥有企业 AI 数据工程能力。面试官、客户或评审真正会问的是：“给我看你做过的东西。”

Capstone 的目标，是把 15 周积累收口为陌生人可以直接评估的实物证据：能运行的仓库、能解释的架构、能验证的指标、能审计的发布、能执行的运维体系，以及清晰的后续路线。

## 毕业的定义：能向陌生人证明你能做

| 作品维度 | 核心产物 | 用途 |
| :--- | :--- | :--- |
| Code + Docs | GitHub 项目、README、架构图、15 周代码和测试 | 让别人能 clone 并跑通，用于面试与求职 |
| Engineering Artifacts | Release Manifest、SLO 契约、评测报告、Runbook 库和演练记录 | 展示生产工程能力，供团队或客户 sign-off |
| Presentation | 15 分钟答辩 PPT、合规白皮书、12 个月路线图 | 让听众理解问题、判断与演进方向 |

不到 20% 的候选人能展示 release manifest、SLO 契约和 Runbook 库。多数人只有一个可运行的 demo；治理、合规、可观测和运营能力，才是“会调 API”与“能负责生产系统”的分界线。

## 15 周工程武器库

| Week | 主题 | 代表产物 |
| :--- | :--- | :--- |
| 1～2 | 业务边界 + 数据契约 | YAML contract + manifest + risk map |
| 3～4 | 采集 + Lakehouse | Ingestion pipeline + Iceberg tables |
| 5～6 | 语义层 + 资产化编排 | dbt models + Dagster assets |
| 7～8 | 非结构化 + RAG 服务化 | 文档管道 + Hybrid retrieval + Rerank |
| 9～10 | Agent Skills + 受控 Agent | Skill Pack + Tool contracts + HITL |
| 11～12 | 评测 + 可观测 | RAGAS + LLM Judge + OTel + Dashboards |
| 13～14 | GraphRAG + 版本治理 | Graph schema + lakeFS + Release manifest |
| 15 | 上线收官 | Cost + SLO + Runbook + Capstone |

这张表不是课程目录，而是成果地图：每个阶段都对应可展示、可验证、可复用的工程对象。

## 完整 Capstone 作品集

| 交付物 | 应包含的内容 |
| :--- | :--- |
| Source Code | 15 周完整代码、测试和可运行说明 |
| Release Manifests | 数据、索引、Prompt、模型、Skills、Graph 原子绑定的发布记录 |

| Roadmap | 毕业后 12 个月演进计划 |

这些交付物合起来，要证明系统不仅“能回答”，还可发布、可回滚、可观测、可治理、可运营。

## 15 分钟答辩 PPT：标准 12 页

答辩先讲问题，再讲技术。听众不关心你是否使用 RAG，他们关心系统解决了什么业务问题、达到什么效果、如何控制风险。

| 页码 | 内容 | 表达重点 |
| :--- | :--- | :--- |
| 1 | 封面：项目名、姓名、课程结业 | 建立项目身份 |
| 2 | 问题陈述：客户真实业务挑战 | 先说明为什么做 |
| 3 | 系统架构图 | 数据 → 检索 → 生成 → Agent → 治理，一图看懂 |
| 4 | 核心工程承诺 | 答得稳、办得对、可观测、可治理 |
| 5 | Demo · Happy Path | 用户提问 → 答案 → 引用 → 工单更新 |
| 6 | Demo · HITL Path | 高风险动作 → 审批 → 执行 |
| 7 | Demo · Bad Case | 客诉 → trace → 修复 → 反例库 |
| 8 | 评测数据 | 6 类 RAGAS 指标、业务 SLO、A/B 对比 |
| 9 | 治理 | 6 类对象原子绑定与秒级回滚 |
| 10 | 合规 | EU AI Act / 中国备案与不可篡改白皮书 |
| 11 | 关键学习 + 演进路线 | 学到的 3 件事与下一步 3 件事 |
| 12 | 致谢 + 问答 | 收口并接受评审 |

三个 demo 分别覆盖顺利路径、高风险路径和故障路径；指标页用“Faithfulness 0.91”代替“回答很准”这类主观描述；治理和合规是多数作品缺失、但最能体现生产能力的部分。

## 毕业后 12 个月路线

| 阶段 | 目标 | 关键动作 | 成功标准 |
| :--- | :--- | :--- | :--- |
| 月 1～3 · 巩固 | 把 15 周代码跑到 100% | 复现 OmniSupport 并部署 | 给陌生人 demo 时不卡顿 |
| 月 4～6 · 拓展 | 深入 2～3 个技术专题 | 深挖 Graph、评测或可观测 | 写出 3～5 篇技术博客 |
| 月 7～9 · 实战 | 在企业中真实落地一次 | 推动公司或实习项目上线 | 有客户使用且评测达标 |
| 月 10～12 · 输出 | 建立行业影响力 | 开源、演讲或写课 | GitHub 获得 100+ star |

课程提供的是广度与地图；只有持续复现、落地和输出，才能把它转化为技术深度和职业价值。

## 2026 年值得深扎的五个方向

| 方向 | 本课程覆盖边界 | 下一步 |
| :--- | :--- | :--- |
| 多 Agent / Agentic 编排 | 单 Agent 受控执行 | Agent 协作、Workflow 编排、LangGraph 深水区 |
| 评测与 AI 可靠性 | RAGAS + 门禁 | 在线质量守护、AI SRE、系统化 evals |
| Context Engineering | 基础 Prompt + RAG | 长上下文、记忆、检索编排、Prompt Caching |
| 模型后训练 | 使用现成模型 | LoRA、DPO、GRPO |
| AI 安全 / Red Team | 合规边界 | Prompt 注入、越狱、对抗评测 |

如果只选择一个方向，优先“评测与 AI 可靠性”：模型会越来越便宜、越来越强，真正稀缺的是让 AI 系统在生产中可信赖的能力。

## 八条工程承诺

| 工程承诺 | 来源 | 工程承诺 | 来源 |
| :--- | :--- | :--- | :--- |
| 数据有契约 | Week 2 | 故障可定位 | Week 12 |
| 答案有证据 | Week 8 | 版本可回滚 | Week 14 |
| 行为受控制 | Week 10 | 监管可审计 | Week 14 |
| 质量可量化 | Week 11 | 长期可运营 | Week 15 |

这八条共同定义“可信赖的智能服务”。AI 工程的本质不是使用了多酷的模型，而是在真实业务约束下稳定交付这些承诺。

## 课程收口

- Week 1～7 是输入侧：数据契约、资产化、多模态，让输入可信赖。
- Week 8～10 是服务侧：RAG、Skill、Agent，让系统答得稳、办得对。
- Week 11～12 是保障侧：评测、可观测，让质量和故障可量化、可定位。
- Week 13～14 是演进侧：GraphRAG、治理，让系统能升级、能回滚。
- Week 15 是运营侧：成本、韧性、SLO、应急，让系统长期稳定运行。

## Recap

- 毕业不是“学完”，而是拥有一套陌生人能直接评估的工程实物证据。
- Capstone 要同时覆盖代码、工程产物和表达材料，不能只交一个 toy demo。
- 15 分钟答辩先讲业务问题，用三类 demo、量化评测、治理和合规证明结果。
- 12 个月路线从复现、深扎、落地走向公开输出，把课程广度转化为专业深度。
- 数据有契约、答案有证据、行为受控制、质量可量化、故障可定位、版本可回滚、监管可审计、长期可运营，是 15 周最终形成的八条工程承诺。
