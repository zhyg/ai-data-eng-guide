# 3. SLO 体系

## 核心问题

系统上线半年后，业务方迟早会问：“它现在到底好不好？”没有 SLO 的团队只能回答“最近还可以，CSAT 大概 4.2”；有 SLO 的团队可以回答“过去 30 天 SLO 达成 99.4%，错误预算还剩 35%”。

本节把 Week 11 的评测和 Week 12 的可观测收口为工程、业务、合规三方都能理解并签字的服务契约，让质量从主观感受变为可量化、可承诺、可执行的运行规则。

## SLO 不是 KPI

| 维度 | KPI（错配） | SLO（正确） |
| :--- | :--- | :--- |
| 本质 | 业务方追求的目标 | 工程与业务之间的双向契约 |
| 谁制定 | 业务方单方决定 | 业务 + 工程共同签署 |
| 上限 | 没有，越高越好 | 有明确边界，达到即可 |
| 不达标 | 工程团队继续加班 | 错误预算耗尽后暂停新功能 |
| 超额时 | “很好，继续提高” | 使用预算做更激进的改动 |
| 对业务方的约束 | 可以无限追加要求 | 不能临时要求高于契约的水平 |

SLO 为质量追逐画出边界：达到即可；预算充足时允许创新；预算烧完时停止新增风险。它既约束工程团队，也约束业务方。

## AI 服务的 SLO 指标组

传统 SRE 主要关注可用性和延迟，AI 服务还必须纳入回答质量、合规和成本。

| 指标组 | SLO 示例 | 错误预算口径 |
| :--- | :--- | :--- |
| 可用性 | 成功响应率 99.5% | 0.5%，即 30 天约 3.6 小时 |
| 性能 | P50 < 1 秒，P99 < 3 秒 | 按不达标请求计 |
| Faithfulness | 在线抽样 > 0.85 | 15% |
| Citation Coverage | 100% | 不允许无引用答案 |
| Refusal Rate | < 5% | 按过度拒答计 |
| PII 与合规 | PII 泄露 = 0，合规拦截率 > 99% | PII 为 0% 红线 |
| 成本 | cost/query < $0.05 | 20% |

其中 AI 质量类最容易被漏掉。只监控可用性和延迟，相当于只检查一个会产生幻觉的系统“在不在线”，却不检查“说得对不对”。

## SLO 阈值的六步制定法

| 步骤 | 具体做法 | 工具或参与方 |
| :--- | :--- | :--- |
| 1. 收集历史 | 获取过去 30～90 天实际表现 | Week 12 dashboard |
| 2. 计算分位 | 得到 P50 / P95 / P99 现状基线 | Prometheus / Datadog |
| 3. 业务表态 | 明确可接受的最低水平和期望水平 | 业务方访谈 |
| 4. 取交集 | 在现状与业务可接受范围内取 70%～80% | 三方会议 |
| 5. 试运行 | 正式签署前观察 30 天 | 试运行环境 |
| 6. Sign-off | 工程、业务、合规三方签字 | 契约文档 |

最常见的错误，是跳过历史数据直接拍一个“99.99%”。多出来的 0.09% 可能让工程团队付出巨大成本，而业务并不能感知。SLO 应从“业务最低能接受多差”反推，而不是从“技术上想做到多好”出发。

## 错误预算与 Burn Rate

错误预算是 SLO 的灵魂。没有预算及其自动动作，SLO 仍然只是另一种 KPI。

### 可用性预算

- 可用性目标为 99.5% 时，30 天错误预算约为 3.6 小时。
- fast burn：14.4 倍持续 5 分钟，触发 P1，表示约 6 小时就会烧光预算。
- slow burn：6 倍持续 1 小时，触发 P2，表示约 3 天会烧光预算。

### AI 质量与合规预算

- Faithfulness 目标为 0.85，允许 7 天内最多 15% 的低质结果；5 倍 burn rate 持续 30 分钟触发 P2。
- PII 泄露目标为 0；泄露比例达到 0.0001 并持续 1 分钟，就触发 P0、通知值班并冻结发布。

### 预算驱动的动作

| 剩余预算 | 自动动作 |
| :--- | :--- |
| < 25% | 冻结非关键变更 |
| < 10% | 冻结全部变更并启动 incident review |
| > 50% | 允许更激进的改动和实验 |

预算不只是用来限制团队，也应该被合理消费。预算充足却不敢做任何改变，会让团队陷入过度保守。

## 三方签字的 SLO 契约

一份可签署的服务等级协议应使用业务语言，而不是只留在工程 dashboard 中。讲义给出的 OmniSupport Copilot 契约包含：

| 契约项 | 承诺 |
| :--- | :--- |
| 可用性 | 月度成功响应率 ≥ 99.5%，错误预算 3.6 小时/月 |
| 性能 | P50 ≤ 1.0 秒，P99 ≤ 3.0 秒，99% 请求达标 |
| AI 质量 | 7 日 Faithfulness ≥ 0.85，Citation = 100%，Refusal ≤ 5% |
| 合规 | PII 泄露 = 0，合规拦截率 ≥ 99% |
| 成本 | 月度 ≤ $50,000，单次查询中位数 ≤ $0.05 |
| 预算管理 | 剩余 < 25% 冻结非关键变更；< 10% 冻结全部变更 |

契约还要规定责任边界：SLO 未达标时，工程方在 30 天内给出改进计划；P0/P1 事故在 48 小时内提交完整 postmortem；业务方在恢复期间不得同时要求新功能；SLA 修订需三方签字并提前 30 天通知。

## SLO as Code（2026）

| 来源 | 做法 | 启示 |
| :--- | :--- | :--- |
| Google SRE | 用错误预算平衡质量和速度 | SLO 文化的基础 |
| OpenSLO + Sloth / Pyrra | YAML 定义 SLO，自动生成 Prometheus burn-rate 告警 | SLO 进入 Git，可 review、可版本化 |
| Nobl9 | 多数据源 SLO 平台化 | 中大型团队不想自建时的选择 |
| Anthropic RSP | 将 AI 质量 SLO 设为模型发布强制项 | 质量门禁成为行业标准 |

SLO 不应只写在 Confluence。使用 OpenSLO 等规范后，定义、评审、告警生成和版本治理都可以进入 Week 14 的发布链路。

## Anti-Patterns

| 反模式 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 把 SLO 当成越高越好的 KPI | 工程团队永远追赶，成本失控 | 达到契约即可，用错误预算做取舍 |
| 只写可用性和延迟 | 系统在线但可能持续答错 | 加入 Faithfulness、Citation、Refusal |
| 拍脑袋定 99.99% | 阈值脱离历史和业务价值 | 先看 30～90 天历史，再三方取交集 |
| 只有目标，没有错误预算 | 不达标时没有动作 | 定义快慢双烧与自动冻结策略 |
| PII 与普通质量平均 | 高质量可能掩盖合规事故 | PII 零容忍，单独设置 P0 红线 |
| SLO 只存在文档里 | 不能自动告警和执行 | SLO as Code，进入 Git 和发布门禁 |

## Recap

- SLO 是工程、业务和合规之间的双向契约，不是“越高越好”的 KPI。
- AI 系统必须同时覆盖传统可靠性、AI 质量、合规与成本指标。
- 阈值应从 30～90 天历史和业务可接受下限反推，再试运行 30 天。
- 错误预算和 burn rate 决定何时创新、何时冻结，是 SLO 的执行核心。
- PII 泄露是零容忍红线，不能被平均质量抵消。
- 2026 年应采用 SLO as Code，让定义、告警和版本治理形成闭环。
