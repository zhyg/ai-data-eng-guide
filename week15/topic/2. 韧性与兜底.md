# 2. 韧性与兜底

## 核心问题

AI 系统上线后一定会遇到 OpenAI 429、pgvector OOM、上游维护、模型超时和流量 10 倍突增。真正的韧性不是“重试 3 次”，而是提前设计一条从全功能到最小可用的降级路径，确保异常时仍然“有回声、不白屏”。

真实场景：OpenAI 大面积返回 429，缺少韧性的 RAG 服务直接把异常抛给用户。5 分钟内在线用户流失 30%，客服电话被打爆。中等体量 C 端服务的 P0 事故每分钟可能损失 $500～$5,000。另一套系统自动降级到 BM25 检索并用缓存兜底，用户几乎感觉不到故障。

## 韧性的本质：保住核心，放弃边缘

传统软件追求“永远可用、永远快”，但一次 LLM 调用超时 30 秒并不罕见。AI 系统更现实的目标，是按服务等级决定异常时必须保留什么。

| 等级 | 必须保留的能力 | 策略 |
| :--- | :--- | :--- |
| P0 · 永远保住 | 有响应、不泄露 PII | 任何情况下都守住，失守即事故 |
| P1 · 尽量保住 | 答案基本正确、有引用 | 可以短时降低质量，但尽力满足 |
| P2 · 主动降级 | 用 BM25 替代向量、mini 替代大模型 | 牺牲部分质量换取可用性 |
| P3 · 果断拒绝 | 复杂归纳类问题转人工 | 放弃边缘功能，保住核心资源 |

韧性不是承诺所有功能永远正常，而是明确最差情况下仍能交付的最小服务。

## 五级降级链

| 级别 | 降级动作 | 触发条件 | 用户体验 |
| :--- | :--- | :--- | :--- |
| L0 · 全功能 | gpt-4o + Hybrid + Graph + Rerank | 系统正常 | 最佳质量 |
| L1 · 轻度 | sonnet 替代 gpt-4o | gpt-4o 排队或延迟超过 5 秒 | 质量略降，仍然优秀 |
| L2 · 中度 | 关闭 Graph，全量走 vector | Graph 服务慢或报错 | 暂时不能做跨文档归纳 |
| L3 · 重度 | BM25 替代 vector，并使用 mini 模型 | pgvector 故障或 Embedding 变慢 | 准确度降低，但仍可使用 |
| L4 · 兜底 | 返回缓存结果或引导人工 | 所有在线路径都失败 | 不白屏，并转人工 |

五级链的关键是“预先声明 + 自动触发”。不能等值班人员半夜手工切换；最后一级即使无法生成答案，也要明确告诉用户服务繁忙并已转人工，而不是暴露 500 或 429 技术错误。

## 分层韧性的执行原则

服务入口先尝试 L0，每类故障触发对应的下一层路径：

LLM 超时或限流 → 更换模型 → Graph 服务失败 → 关闭 Graph → 向量或 Embedding 服务失败 → BM25 + mini → 全路径失败 → 宽松缓存或 HITL

工程上需要满足四个约束：

1. 同类错误连续 5 次后自动熔断，避免慢服务拖死整条链路。
2. 每次切换都记录 degradation event，让 Week 12 面板显示当前运行级别。
3. 每一级都返回结构化 answer，不把内部异常直接抛给用户。
4. 极端情况下触发 Week 10 的 HITL，让客服接手。

模型间的 fallback、负载均衡、超时和重试可交给 LiteLLM Router 统一声明，业务服务只负责系统级降级语义。

## 四级缓存：韧性的第二防线

缓存既降成本，也能在上游故障时继续服务高频问题。

| 缓存级别 | 位置 | 内容 | 命中率 | 主要价值 |
| :--- | :--- | :--- | :--- | :--- |
| L1 · Browser | CDN / Edge | 完整 response | 5%～10% | 0 ms 响应 |
| L2 · App | Redis | 语义级 response | 20%～35% | 降成本 + 韧性 |
| L3 · Component | Local LRU | Embedding、rerank 等中间结果 | 40%～60% | 降组件成本 |
| L4 · Cold | Object Storage | 完整 trace + bad case | N/A | 事故兜底 + 复盘 |

四层合并后，全链路命中率可达到 50%～70%。这部分流量既减少正常运行成本，也能在模型和检索上游故障时继续响应。

## release_id 驱动的精细化失效

缓存失效不能采用“发布就全部清空”的粗暴策略，而应比较 Week 14 release manifest 中发生变化的对象。

| 变更对象 | 失效范围 | 原因 |
| :--- | :--- | :--- |
| data | 所有 RAG 答案；若能识别 changed paths，只删受影响文档 | 数据变化可能让事实过期 |
| prompt | 只失效最终答案，不删 Embedding | Embedding 与 prompt 无关 |
| model | RAG 答案与 rerank 结果 | 生成与排序行为都可能变化 |
| 单个 lakeFS path | 仅删除对应文档与 chunk | 避免无关缓存损失 |

精细化失效比全量清理可把命中率再提高 30%～50%。缓存失效本身也是发布工程的一部分，而不是临时运维动作。

## 限流与优雅排队

Edge 层是抵御流量突增的第一道防线。令牌桶允许短时突发、限制长期速率，适合请求耗时和成本都较高的 AI 服务。

讲义中的基线策略是：

- VIP：速率 300、容量 1000，保证付费客户在流量突增时优先通过。
- Default：速率 100、容量 300。
- 有令牌立即放行；没有令牌最多排队 5 秒。
- 排队超时后不返回 429，而是返回友好提示，并建议 30 秒后重试。
- 限流同样记录 degradation_level，进入 trace 和事故复盘。

限流、缓存和降级链共同构成三道防线：先限制流入，再利用缓存吸收请求，最后逐级降低在线依赖。

## Industry Signals（2026）

| 来源 | 能力 | 2026 年建议 |
| :--- | :--- | :--- |
| Resilience4j / Sentinel | 熔断、降级、隔离、限流 | Java 生态使用 Resilience4j，阿里生态可用 Sentinel |
| LiteLLM Router | 模型 fallback、负载均衡、重试 | AI 模型降级链优先交给它统一配置 |
| Cloudflare AI Gateway | 限流、缓存、fallback、监控一体 | 不想自建的团队可直接使用 |
| Anthropic 降级实践 | opus → sonnet → haiku → cached | 与本节的分层降级原则一致 |

需要纠正一个旧认知：Netflix Hystrix 已经退役并进入维护状态，不应再作为新系统的默认选型。

## Anti-Patterns

| 反模式 | 为什么失败 | 正确做法 |
| :--- | :--- | :--- |
| 只配置“重试 3 次” | 上游持续故障时只会放大流量和延迟 | 设计显式的五级降级链 |
| 等 oncall 手工切换 | 响应慢、依赖个人经验 | 每级预先声明并自动触发 |
| 把 429 / 500 原样返回用户 | 技术故障直接转化为信任和收入损失 | 始终返回 answer、重试节奏或人工入口 |
| 发布时全量清缓存 | 命中率骤降并引发缓存雪崩 | 按 data、prompt、model 和 changed path 精细失效 |
| 所有客户共享同一限额 | 突发流量影响关键和付费用户 | 按业务等级配置令牌桶和优先队列 |
| 新项目继续使用 Hystrix | 依赖已退役方案 | 使用 Resilience4j、Sentinel 或网关能力 |

## Recap

- 韧性的目标不是“永远正常”，而是异常时保住 P0/P1 核心能力、主动放弃边缘功能。
- 五级降级链必须预先声明并自动触发，每一级都要返回用户可理解的结果。
- 四级缓存是成本与韧性的共同抓手，全链路命中率可达 50%～70%。
- 缓存失效要由 release manifest 和 changed paths 驱动，避免全量清理。
- 令牌桶限流允许短时突发，并以优雅排队和明确重试节奏替代裸 429。
- 工具链已经成熟，真正的难点是团队是否在上线前就把降级路径设计清楚。
