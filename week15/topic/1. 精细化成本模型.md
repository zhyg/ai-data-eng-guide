# 1. 精细化成本模型

## 核心问题

AI 系统上线后，最先暴露的往往不是模型能力，而是成本失控：LLM API、向量数据库、Embedding 跑批都在持续花钱，但团队只能看到一张月账单，无法回答钱花在哪条链路、哪个版本、哪类问题上。

真实场景：一个系统上线 3 个月后，单月 LLM API 花费 12 万元、pgvector 实例 1.8 万元、Embedding 跑批 6 千元。CFO 追问成本归因，团队却只能展示供应商总账单。

本节的目标，是把 AI 成本从财务结果变成可拆账、可归因、可监控、可优化的工程对象。工程方法得当时，一个季度可稳定降低 20%～40% 的成本。

## 成本工程的四个环节

| 环节 | 核心动作 | 工程价值 |
| :--- | :--- | :--- |
| 拆账 | 按 Embedding、检索、生成、存储、缓存分项 | 知道钱花在哪一段，而不是只看总数 |
| 归因 | 计算每次查询的成本，并关联 release_id 与 trace span | 定位到版本、请求和组件 |
| 监控 | 把成本接入 Week 12 的 dashboard 和 PR 检查 | 让成本和质量拥有同等优先级 |
| 优化 | 按节省成本与工程投入之比排序 | 先做回本最快的事，避免拍脑袋 |

关键判断：成本失控往往不是模型单价太贵，而是范式用错。用 GraphRAG Global 回答普通 FAQ，可能比纯向量 RAG 贵 5～15 倍。Week 13 的题型路由不仅提高质量，也是最大的省钱手段之一。

## 每千次查询成本

“每千次查询成本”是 AI 成本最重要的单位指标。它能把技术架构直接映射为业务单价，并暴露不同查询范式之间的巨大差距。

| 场景 | 主要消耗 | 每千次查询成本 | 成本大头 |
| :--- | :--- | :--- | :--- |
| 纯向量 RAG | 向量召回 + LLM 生成 | $1.5～3 | 60% 为生成 |
| 混合 RAG | 向量 + BM25 + Cross-Encoder rerank | $2.5～5 | 50% 生成 + 20% rerank |
| Agent 调工具 | 多次 LLM 调用 + tool 执行 | $5～15 | 70% 为多轮 LLM |
| GraphRAG Global | 社区检测 + 摘要 + 二次生成 | $8～25 | 60% 为多次 LLM |
| HITL 触发 | 通知 + 人工等待 + 二次生成 | $15～50 | 人工时间占大头 |

这张表说明，最有效的优化常常不是更换模型，而是先判断问题是否真的需要 Agent、GraphRAG 或 HITL。

## 五大优化抓手

ROI 以“节省成本 ÷ 工程投入”衡量。应从高 ROI 项开始，而不是哪里绝对金额高就先削哪里。

| 抓手 | 具体做法 | 预期节省 | ROI |
| :--- | :--- | :--- | :--- |
| Cache 高频查询 | 识别 top-100 高频 query 并缓存 | 20%～40% | ★★★★★ |
| 题型路由 | 简单问题不用图、不使用长上下文 | 15%～30% | ★★★★★ |
| Embedding 复用 | 同一 chunk 不重复 embed | 5%～15% | ★★★★ |
| 模型降级 | 简单问题改用 mini / haiku | 生成成本降低 20%～50% | ★★★★ |
| Batch 推理 | Embedding / Rerank 批量执行 | Compute 降低 30% | ★★★ |

缓存和题型路由投入小、回报高，通常一周内回本。先把这两项做扎实，往往就能先砍掉约三成成本。

## 语义缓存：回本最快的优化

语义缓存不是只做字符串相等判断，而是采用“字面匹配 + 语义近邻”的双层结构：

1. 先以租户、release_id 和 query 指纹组成键，执行 O(1) 字面查找。
2. 字面未命中时，对 query 生成向量并查找最近邻，完成 O(log n) 语义查找。
3. 相似度阈值设为 0.92，只复用“几乎一样”的问题，防止误命中导致答错。
4. tenant 负责多租户隔离，release_id 负责版本隔离；发布新版本时，旧缓存自然失效。

讲义给出的实战基线是：在 10 万 DAU、top-100 query 占 60% 流量的场景中，缓存命中率达到 35%，每月节省约 $15,000；工程投入为 2 个工程师周，ROI 回收期约 3 天，年化节省接近 $180,000。

## 2026 年的成本利器

| 利器 | 作用 | 成本收益 |
| :--- | :--- | :--- |
| LiteLLM 网关 | 统一 100+ 模型、设置硬预算上限、按 tag 归因 | 单点控制所有模型花费，避免预算超支 |
| Prompt Caching | 缓存系统提示和长上下文等静态部分 | 缓存 token 约省 90% |
| Batch API | 将 Embedding、离线评测等非实时任务批量执行 | 约降低 50% |
| 模型价格下降 | DeepSeek-V3 约 $0.27/百万 token，gpt-4o 约 $2.5/百万 token | 同等能力单价一年下降一个数量级 |

另一组参考数据是 gpt-4o-mini 约 $0.15/百万 token。模型价格持续下降后，“AI 太贵”更多是缓存、路由、批量和网关没有工程化，而不只是模型本身昂贵。

## 成本监控面板

成本面板是在 Week 12 可观测体系上的升级，至少要覆盖四类视图：

| 视图 | 观察内容 | 目的 |
| :--- | :--- | :--- |
| 日成本趋势 | 总成本及 LLM、Embedding、存储等分类成本 | 发现趋势与异常增长 |
| Cost per 1k Queries | 总成本除以查询量 | 与业务单价直接对比 |
| Top spans by cost | 按 span 汇总成本最高的链路 | 找到真正的优化对象 |
| Top release by cost | 按 release_id 汇总成本 | 定位哪个版本引入成本回归 |

关键告警包括：

- 日成本超过过去 7 天均值 30% 时触发 P2。
- 月度支出相对预算和当月时间进度快烧 30% 时触发 P1。
- 成本告警与质量告警进入同一值班通道，让团队把成本当作质量问题处理。

## Industry Signals（2026）

AI FinOps 已从“查看月账单”发展为完整的工程学科。

| 来源 | 做法 | 启示 |
| :--- | :--- | :--- |
| LiteLLM | 统一网关 + 预算上限 + 成本归因 | 2026 年单点管理模型花费的优先选择 |

| Langfuse / Helicone | trace 级成本归因 | 每条 trace 都携带 cost，可接入 Week 12 |

## Anti-Patterns

| 反模式 | 问题 | 正确做法 |
| :--- | :--- | :--- |
| 只看供应商月账单 | 无法定位到请求、组件和版本 | 建立每千次查询成本并关联 trace / release_id |
| 认为单价是唯一问题 | 忽略范式选择造成的 5～15 倍差距 | 先做题型路由，再比较模型价格 |
| 哪里金额高就削哪里 | 忽略工程投入，可能长期不回本 | 按 ROI 排序，优先缓存和路由 |
| 只做字面缓存 | 换一种说法就无法命中 | 字面查找与高阈值语义近邻结合 |
| 缓存不做租户和版本隔离 | 可能跨租户泄露或复用旧答案 | key 同时绑定 tenant 与 release_id |
| 离线任务仍走实时单次 API | 白白承担更高单价 | Embedding 和评测优先使用 Batch API |

## Recap

- AI 成本是可拆账、可归因、可监控、可优化的工程对象，不是一张财务月账单。
- “每千次查询成本”是关键单位指标；范式选错比模型单价贵更危险。
- 缓存与题型路由是 ROI 最高的两项优化，通常一周内即可回本。
- 语义缓存要采用 0.92 高阈值，并以 tenant 和 release_id 隔离。
- LiteLLM、Prompt Caching、Batch API 与持续下降的模型单价，可以在基础优化之外继续大幅降本。
- 成本必须进入 trace、release 和告警体系，与质量共同成为上线门禁。
