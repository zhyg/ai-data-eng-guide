# 4. 应急 Runbook 体系

## 核心问题

判断一个 AI 团队是否成熟，可以看凌晨 3 点发生故障时值班人员的第一反应：是“赶紧把老工程师叫起来”，还是打开故障分类树，5 秒内找到对应 Runbook。

一个生产系统可能遇到 50 多种异常，经验如果只存在个人脑中，人员离职、休假或生病就会让团队失能。本节把 Week 9 的单个 Runbook 扩展为可索引、可触发、可执行、可演练的应急体系。

## 应急能力的五级成熟度

| 等级 | 具体表现 | 应急依赖 |
| :--- | :--- | :--- |
| L0 · 无 | 出事就“打电话找老 X” | 个人英雄 |
| L1 · 散文式 | Confluence 有零散文档，但找不到 | 文档 + 经验 |
| L2 · 索引化 | 有故障分类树和 Runbook 库 | 体系化文档 |
| L3 · 可执行 | Runbook 变成 Skill Pack 和 CLI | 工程化执行 |
| L4 · 自主 | Agentic SRE 自动诊断和修复 | 系统自治 + 人守红线 |

多数团队卡在 L1：文档写了却无法在事故现场快速定位。真正的工程拐点是 L3——同一份应急知识既能由人执行，也能由 Agent 调用。

## 五类 Runbook

Runbook 必须按故障对象分类，否则“写了但找不到”等同于没有。

| 类别 | 典型场景 |
| :--- | :--- |
| Infra | pgvector OOM、Redis 连接中断、对象存储变慢、GPU 集群故障 |
| Data | lakeFS 分支冲突、索引重建中 |
| Model | LLM API 429、Embedding 超时 |
| Service | RAG 服务故障、Agent 工具失败、HITL 超时积压 |
| Compliance | PII 泄露告警 |

基础设施约占事故类型的 30%，Data + Model 约占 35%，Service + Compliance 约占 35%。先覆盖最高频的 25～30 个场景，通常就能解决 80% 的夜间事故；不必一开始追求写全 50 个。

## Runbook 索引与告警联动

索引不只是目录，还要成为告警系统的机器可读路由表。

| 字段 | 作用 |
| :--- | :--- |
| id | 为 Runbook 提供稳定标识，如基础设施或模型类编号 |
| name | 描述故障场景 |
| symptoms | 声明可匹配的告警特征，如 pgvector P99 > 5 秒、OOM kill、OpenAI 429 |
| sla | 明确 P0/P1/P2 的确认和解决时限，例如 P1 在 15 分钟内响应、1 小时内解决 |
| owner | 指定负责团队，避免事故中临时找人 |
| skill_pack | 关联 Week 9 的可执行恢复能力 |

Week 12 的告警根据 symptoms 自动匹配 Runbook，并在通知中附上链接。值班人员不需要再到 Wiki 中搜索；Agent 也可以根据同一个索引定位可执行 Skill。

## 从 Bad Case 自动生成 Runbook

每次事故都应成为团队资产，而不是只留下一份复盘文档。自动化链路是：

Postmortem → 提取告警特征与根因层 → 自动分类 → 生成诊断、修复与回滚步骤 → 加入索引 → 生成 Runbook 文档 → 生成 Skill Pack → 安排季度演练

生成过程复用 postmortem 中已经存在的信息：

- incident_id 生成稳定的 Runbook id。
- detection.alert_signatures 变成 symptoms。
- root cause 所在层决定分类。
- severity 决定 SLA。
- timeline 中的 diagnosis 和 fix steps 形成执行步骤。
- resolution 中的 rollback steps 形成回滚方案。

这样不需要工程师把同一份事故信息重复写两遍。事故越多，Runbook、Skill Pack 和团队应急能力越丰富，形成长期复利。

## Wheel of Misfortune 演练

写 Runbook 只是第一步，真正的验证来自持续演练。

| 维度 | 具体做法 | 工程价值 |
| :--- | :--- | :--- |
| 频率 | 每周 1 次，每次 30 分钟 | 防止能力退化 |
| 随机 | 随机抽 1 名 oncall 和 1 个 Runbook | 避免经验集中在少数人手里 |
| 真实 | 模拟真实告警和监控数据 | 贴近事故现场 |
| 评分 | 主持人按 Runbook 打 1～5 分 | 检验文档与执行质量 |
| 迭代 | 发现漏洞后立即提 PR 修复 | 及时更新过期命令和失效凭据 |

没有演练过的 Runbook 基本等于没有。写 10 份但从不执行，不如维护 3 份并每周演练。

## Agentic SRE（2026）

Agentic SRE 把 detect → diagnose → remediate 串成自主事故响应链。它可以持续观察告警、查询日志、分析根因，并在授权范围内按 Runbook 执行恢复动作。

| 厂商或信号 | 能力 | 讲义数据 |
| :--- | :--- | :--- |
| Resolve.ai | 自主事故响应 | 2025 年 12 月估值 $1B，目标是自主解决 80% 事故 |
| Cleric | 7×24 自动排查告警与根因分析 | Gartner 2025 AI for SRE Cool Vendor |
| Traversal | 因果 ML 根因定位 | 准确率超过 90%，为 DigitalOcean 每年节省 3.6 万工时 |
| 行业整体 | AI 自动化事故响应 | MTTR 最高降低 70%，63% 开发者已在使用 |

Agentic SRE 的学习材料正是结构化 Runbook、Skill Pack 和 postmortem。先把这些基础资产做好，才有可靠的自动化输入。

## 人必须守住的红线

Agent 可以负责查日志、归纳证据、定位根因和提出方案，但高风险动作必须保留 HITL：

- 是否回滚生产版本。
- 是否冻结服务和全部变更。
- 是否修改或删除客户数据。
- 是否执行会扩大业务影响面的动作。

正确分工是 Agent 做高频、耗时、可验证的工作，人负责不可逆判断和风险红线。

## Anti-Patterns

| 反模式 | 后果 | 正确做法 |
| :--- | :--- | :--- |
| 应急知识只在老员工脑中 | 人员不可用时团队失能 | 建立索引化 Runbook 库 |
| 文档散落在 Wiki | 告警发生时找不到 | 用 symptoms 自动关联告警 |
| 一开始追求覆盖所有事故 | 投入过大、长期失去维护 | 先覆盖 25～30 个高频场景 |
| Runbook 只写不演 | 命令、凭据和路径悄悄过期 | 每周随机演练并立即修复 |
| 复盘与 Runbook 各写一次 | 重复劳动，内容容易漂移 | 从 postmortem 自动生成草稿 |
| Agent 可自主执行高风险动作 | 错误判断可能扩大事故 | 人工审批守住回滚、冻结和数据操作 |

## Recap

- 应急能力是系统属性，不应依赖个人英雄。
- Runbook 要从散文文档升级为有分类、有症状、有 SLA、有 owner 的机器可读索引。
- 从 postmortem 自动生成 Runbook 和 Skill Pack，可把每次事故转化为团队复利。
- Wheel of Misfortune 用每周随机演练维护“肌肉记忆”，发现问题立即修复。
- Agentic SRE 能显著降低 MTTR，但高风险动作仍必须由人审批。
- 先覆盖 25～30 个高频场景，就能解决约 80% 的夜间应急问题。
