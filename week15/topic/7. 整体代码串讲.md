# 7. 整体代码串讲

## 核心目标

本节不逐个解释 Python 函数，而是建立阅读整套项目的全景心智模型：数据如何从不可信输入变成可信证据，再变成回答、指标和受控动作，最终如何被评估、追踪、发布和回滚。

阅读代码时始终追问三个问题：当前模块改变了哪个业务状态、消费了什么证据、受哪个发布版本约束。只要这条业务因果链清楚，复杂目录就会变成一组责任边界，而不是文件堆积。

## 三个核心业务对象

| 对象 | 核心含义 | 贯穿的范围 |
| :--- | :--- | :--- |
| Case / Ticket | 当前客服问题与业务上下文 | tenant、产品线、SLA、会话、可执行动作 |
| Evidence | 回答和决策可核对的事实依据 | source manifest、chunk、索引、action、lineage、audit |
| Release | 一次可复现的系统能力组合 | data、index、prompt、graph、model、skills / service |

Case 决定“为谁、在什么业务上下文中做事”，Evidence 证明“为什么这样回答或行动”，Release 约束“这次运行到底使用哪套系统能力”。

## 七层架构

| 层 | 主要对象 | 责任 |
| :--- | :--- | :--- |
| 1. Source | 结构化、半结构化、非结构化源 | 保存原始业务事实与来源身份 |
| 2. Landing / Raw | 原始事件、对象地址、批次 manifest | 保真落盘，支持重放和追溯 |
| 3. Parse / Normalize | document unit、section、table、timestamp | 屏蔽 PDF、OCR、音视频解析器差异 |
| 4. Lakehouse | bronze、silver、gold | 分层清洗、统一模型、快照和演进 |
| 5. Asset / Retrieval | dbt metric、向量、FTS、RRF、rerank、Graph | 把数据变成指标和可检索证据 |
| 6. Product / Controlled Agent | Product API、RAG API、Tool API、HITL | 生成回答并执行受控业务动作 |
| 7. Assurance / Governance | eval、OTel、Phoenix、audit、lineage、release | 评估、追踪、审计、灰度和回滚 |

七层架构回答“系统有哪些能力层”；部署拓扑回答“进程和网络边界在哪里”；三平面模型回答“代码责任属于哪里”。

## 三个责任平面

| 平面 | 组成 | 责任 |
| :--- | :--- | :--- |
| 用户面 | Web App、客服控制台、管理控制台、Product API | 组织登录、工单、问答、反馈和审批体验 |
| 数据面 | data、pipeline、Lakehouse、index、graph、metric mart | 生产事实、证据、索引和指标资产 |
| 控制面 | contracts、Tool API、release、rollout、policy | 约束输入、动作、版本和发布决策 |

测试、eval、可观测、审计和 lineage 是横切证据，不属于单一平面，却为每个平面的行为提供验证。

## 一条主线、三段旅程

### 第一段：证据生产

Source → Contract + Manifest → Ingest → Raw / Lakehouse → Parse + Normalize → Chunk + Evidence ID → Index / Graph / Metric Mart

这一段把不可信输入变成可检索、可计算、可追溯的资产：

1. Contract 声明对象稳定结构，Manifest 声明本次输入批次的身份、来源、策略和版本。
2. Ingest 做指纹去重、upsert、checkpoint 和错误隔离，保证重跑不会翻倍。
3. Media Loader 保留文档、图片、音频、视频原件和对象地址。
4. Parser Adapter 把不同解析器结果归一为统一 document units。
5. Normalize 统一章节、表格、页码、时间码和元数据。
6. Chunk 按结构与语义切片，并以 evidence id 连接源位置。
7. Lakehouse 形成 bronze、silver、gold，dbt 和 Dagster 再把结果组织成指标和资产图。
8. 向量、BM25 / FTS、Graph 分别形成语义、精确和关系检索能力。

### 第二段：证据消费

客服工单 → Product API 恢复身份与上下文 → RAG Contract → 题型路由 → Hybrid / Graph 检索 → Rerank + Context → 模型生成 → Answer + Citation + Trace → KPI 或 Tool Action → HITL

在线请求有固定顺序：

- Product API 把客户端 token 还原为可信身份、tenant、role、case、session 和 active release。
- RAG 请求契约先验证问题、过滤器和输出要求。
- Router 根据题型选择 Hybrid、本地图、多跳或全局路径。
- Hybrid 使用 vector + FTS / BM25，经 RRF 合并，再由 Cross-Encoder 重排。
- GraphRAG 使用实体、关系和社区处理跨文档问题。
- 生成阶段只能消费裁剪后的证据上下文，响应必须带 citation 和 trace。
- KPI 读取统一 Metric Registry；动作先经过 Tool Contract、权限、幂等和风险判定。
- 低风险动作直接执行，高风险动作持久化并等待 HITL。

### 第三段：治理与发布

Result → Feedback / Eval → Trace / Audit / Lineage → Quality Gate → Release Manifest → Canary → Environment Pointer → Promote / Rollback

治理路径把一次结果变为可运营证据：Eval 衡量案例总体质量，Trace 解释单次请求的执行路径，Audit 记录责任主体和业务状态变化，Lineage 连接数据、模型与动作。通过门禁后，release manifest 把所有组件锁成不可变候选集，灰度验证后再切换环境指针。

安全回滚恢复的是整组能力，而不是只替换服务代码；否则旧服务仍可能读到新数据、新索引或新 Prompt。

## 核心目录与模块职责

| 模块 | 输入 | 核心职责 | 输出 |
| :--- | :--- | :--- | :--- |
| contracts | 业务规则和对象定义 | 声明输入、输出、失败条件和兼容边界 | Data / Service / Tool / Release 契约 |
| pipeline / ingest | 通过准入的 manifest | 去重、upsert、checkpoint、错误隔离 | 原始事件与规范业务表 |
| media / parser / chunk | 文档、图片、音视频原件 | 解析、标准化、结构与语义切片 | knowledge document、section、chunk、evidence id |
| Lakehouse | 原始与规范数据 | bronze / silver / gold 分层、快照和回填 | 可消费数据资产 |
| dbt / Metric Registry | 结构化事实 | 统一指标定义和语义 | Metric Mart / KPI |
| Dagster / Data Factory | 资产依赖和分区 | 物化、backfill、asset checks、运行事件 | 可运营 pipeline |
| index / graph | chunk 与实体关系 | 构建向量、FTS、rerank 和图索引 | 可版本化检索资产 |
| Product / RAG API | 用户、case、query、release | 身份恢复、路由、检索、生成 | 带引用的回答 |
| Tool API / HITL | 受限动作意图 | 权限、幂等、证据、风险和审批 | 业务状态变更与审计事件 |
| eval / observability | 回答、动作与运行事件 | 离线评测、在线 SLO、trace、bad case | 质量与故障证据 |
| release / rollout | 通过门禁的组件版本 | 原子绑定、灰度、指针切换、回滚 | 可激活、可审计的环境版本 |

## 契约体系

### Data Contract

约束 document、sheet、JSON、ticket 等对象的字段类型、来源、tenant、PII、许可和版本。Schema 描述某一类对象的稳定结构；Manifest 描述某一次输入批次的身份、所有权、模态、schema 版本、去重策略、环境和保留期。

### Service Contract

约束 RAG 问答的请求与响应，包括问题、租户、角色、过滤器、引用、release_id 和 trace id。它确保 Product API 与 RAG API 之间的行为稳定。

### Tool Contract

约束动作角色、幂等键、证据、审计字段、失败码和 HITL 条件。浏览器和模型只能提出契约允许的意图，不能直接决定数据库操作。

### Release Contract

约束 data、index、prompt、model、skills 和 graph 如何组成不可变版本，供灰度、激活和回滚使用。

## 数据模型演进

| 模型组 | 关键对象 | 解决的问题 |
| :--- | :--- | :--- |
| 业务上下文 | case、ticket、tenant、product、SLA、timeline | 请求属于谁、处理什么业务 |
| 原始与规范资产 | source manifest、raw event、knowledge document、section | 来源是否可信、是否可重放 |
| 证据与检索 | chunk、evidence id、vector / FTS index、entity、relation | 回答依据在哪里、如何召回 |
| 指标资产 | staging、intermediate、mart、metric registry | KPI 是否只有一个定义 |
| 交互与动作 | conversation、feedback、action、approval | 回答如何反馈、动作如何受控 |
| 质量与追踪 | eval case、trace / span、audit event、lineage event | 质量如何量化、责任如何追溯 |
| 发布治理 | release manifest、rollout event、environment pointer | 哪套组件正在运行、如何回滚 |

这些模型不是一次性设计完成，而是随课程逐周扩展；但它们始终围绕 Case、Evidence、Release 三个核心对象连接。

## 契约测试与健康检测

| 检查面 | 验证内容 |
| :--- | :--- |
| 契约测试 | Schema 可机器校验，服务和工具的输入、输出、失败码、角色和 HITL 条件稳定 |
| Ingest 健康 | manifest 准入、指纹去重、checkpoint、重跑幂等、错误隔离 |
| 资产健康 | 分区物化、backfill、asset checks、索引与 Graph 版本一致 |
| 离线质量 | RAGAS、LLM Judge、回归集、Bad Case 是否通过门禁 |
| 在线质量 | 可用性、延迟、Faithfulness、Citation、PII、成本及错误预算 |
| 请求追踪 | OTel / Phoenix 是否能从 Product API 追到检索、模型、工具和审批 |
| 发布健康 | observation 的 release_id / digest 是否匹配，灰度指标和红线是否通过 |
| 回滚验证 | 环境指针是否恢复整组组件，audit 和 lineage 是否保留完整记录 |

测试和可观测不是末尾补充，而是横切所有层的工程证据。契约防止不兼容输入进入系统，eval 判断输出质量，trace 解释单次执行，SLO 判断长期运行状态，release gate 决定版本是否能上线。

## 建议的代码阅读顺序

1. 先读 README，理解产品边界和三个核心对象。
2. 看七层架构、部署拓扑和三平面图，建立目录与责任映射。
3. 阅读 docs / blueprints，按 Week 2～14 理解每阶段为何存在。
4. 沿证据生产主线读 contracts → ingest → parser → Lakehouse → index / graph / metric。
5. 沿证据消费主线读 Product API → RAG → Tool API → HITL。
6. 最后读 eval → observability → audit / lineage → release / rollout。
7. 回到 Capstone，验证所有局部能力如何装配成一个产品。

## Week 15 的最终收口

前 14 周解决了输入、服务、评测、可观测、图谱和版本治理；Week 15 再补上长期运营：

- Cost 把每条 trace 和 release 的花费变成可归因指标。
- Resilience 为模型、检索和缓存设计自动降级路径。
- SLO 把离线评测与在线观测收口为可执行契约。
- Runbook 把事故证据转化为可索引、可演练、可由 Agent 使用的恢复资产。

## Recap

- 整套项目的核心不是文件数量，而是 Case、Evidence、Release 三个对象和一条业务因果链。
- 证据生产把原始输入变成 index、graph 和 metric；证据消费把它变成回答、KPI 和受控动作；治理路径让结果可评估、可追踪、可发布、可回滚。
- 七层架构看能力层次，部署拓扑看进程边界，三平面模型看代码责任。
- 契约与 manifest 分工不同：前者定义稳定结构，后者定义一次运行的身份和策略。
- 安全回滚必须恢复整组组件，不能只回滚服务代码。
- 读任何模块都应回答：它改变什么业务状态、消费什么证据、受哪个 release 约束。
