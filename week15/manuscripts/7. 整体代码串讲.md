第一周和第二周不仅仅是准备工作，它们是我们生成数据和产品的主线入口控制面。通过数据契约、工具契约和服务契约等，我们控制整个系统的输入。 数据契约包括data契约、tools契约和服务契约。data契约中可能包含schemas，如document、sheet、contract、json和ticket等，这些用于约束字段类型、来源、租户PI、许可和版本。 服务契约规定了问答的输入输出以及引用版本和trace的字段，供RAG API和product API使用。工具契约则涉及RAG请求和响应schema，定义了我们的工具如何工作。
我们的契约文件包括Tool Contract schema、talk control schema和Ticket Update JSON。这些文件约束了角色、幂等性、审计、失败码和HTL条件，它们会消费tool API和agent。 在release下的manifest v2中，我们规定了多组件版本如何组成不可发布的变量，这将用于release和rollout。 Manifest是一次输入批次的身份证，它回答数据来源、所有权等问题，确保责任可追溯。同时，它还说明内容的模态和schema版本，以便下游解析。 Manifest还需定义如何判断重复和变更，以避免重跑时的重复写入问题。此外，它还指定了允许进入哪些环境以及保留时间。
Doc asset 和 Audit offset 都是 offset 输入边界。在 data 目录下，有一个名为 Synergy 的种子工程，它用于查看具体数据批次，并声明 source schema 和 Git。此外，还包含多个 manifest 文件。 Test contract 下的契约不是说明书，而是自动化的质量门禁。契约和 manifest 共同减少输入口的不确定性。Manifest 描述某次输入批次的身份、来源和策略，而 schema 描述某一类对象的稳定结构。前者服务于运行追溯，后者服务于自动验证。两者缺一不可，否则会将兼容性和异常推到下游。 主线任务的第二阶段是数据采集与 Lakehouse 处理。这涉及幂等、分层、快照、回填和资产化编排。当契约和 manifest 通过后，数据正式进入系统。原始对象保持落盘，结构化事实进入数据仓库和湖仓。Pipeline 是可重放的，确保同一批数据重复执行时不会翻倍。

在之前的课程中，我们介绍了几个处理阶段。首先是Low Node，它获取对象模态和源元数据，统一源文档。接着是Passed Parser Adapter，将不同解析器的结果归一化，确保下游不依赖于PDF、OCR或SAR库的私有结构。核心输出是document units。 第三步进行标准化，统一章节、表格、时间码、页码和元数据，输出knowledge document和section。第四步是trunk，按结构化和语义进行切片，输入为document chunk。最终输出是event_id，连接chunk和source的位置。 整个过程在pipeline下执行，包括Parcel的标准化等步骤。第七周的内容还包括video和chunk的处理。最后是Index Graph和Metric Mart，通过索引、混合检索与GraphRAG实现。
