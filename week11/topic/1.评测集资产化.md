# 1. 评测集资产化

## 核心问题

Week 10 造好了能办事的 Copilot，这一周要回答一个要命的问题：你凭什么说它「办得对」？第一步，先有一把能反复用的尺子——评测集。

真实场景是那段每个 AI 团队都熟悉的对话：产品问「这周效果怎么样」，工程答「抽测了几个 case，感觉还行」。这话搁 2026 年会被客户和监管双重打回。因为「感觉」不可复现、不可对比、不可追责，在生产里等于没有质量保障。

关键判断：评测集烂，后面 metrics、judge、gate 全是空中楼阁。

## 评测集是「数据资产」，不是「测试用例」

传统软件测试集写一次、跑很久、偶尔补；AI 评测集是另一种东西——它脚下的三样东西一直在动：

- 业务在变：FAQ 更新、政策调整、用户说法演化，昨天的标答今天就错。
- 模型在变：GPT-4o → GPT-5、reranker 升级、prompt 迭代，同一题答案全变。
- 上下文在变：Week 7 多模态、Week 8 RAG 服务化、Week 9 Skill，系统底座一直在改。

所以评测集是一个持续演进的资产，比测试用例多出 4 个工程属性：**可版本 / 可回归 / 可对抗 / 可治理**。

## 人工抽测 vs 评测集资产化

这张表是判断「AI 团队成不成熟」最直接的信号：抽测 = 还在 Demo 阶段，资产化 = 进了生产阶段。

| 维度 | 人工抽测 | 评测集资产化 |
| :--- | :--- | :--- |
| 样本数 | 5-20 个 / 凭直觉挑 | 50-2000 个 / 分层覆盖 |
| 版本 | 没有 | v1 / v2 / v3 显式版本号 |
| 可重放 | 不可 | 同份数据 + 同份评测器 → 完全可重放 |
| Bad case 沉淀 | 靠工程师记忆 | 反例库自动维护 |
| 团队协作 | 靠 Wiki / 群里喊 | Git 跟踪 + PR review |
| CI 集成 | 不可能 | PR 触发回归 + 自动门禁 |
| 长期价值 | 复盘时一次性用 | 复利资产，越用越值钱 |

## 评测集的 4 类样本

少一类，就有一整块评测盲区。

| 类别 | 占比 | 覆盖内容 | 验证目标 | 来源 |
| :--- | :--- | :--- | :--- | :--- |
| Happy 高频典型 | 60-70% | FAQ / 常见操作 | 基础能力 | 产品历史日志采样 |
| Boundary 边界长尾 | 15-20% | 同义改写 / 罕见术语 / 含糊 | 泛化能力 | 低频高价值场景 |
| Adversarial 反例 | 10-15% | PII 诱导 / 越权 / 误导攻击 | 安全 + 合规 | 历史事故 + 红队 |
| Multi-hop 多跳 | 5-10% | 跨多文档 / 多步推理 | 复杂推理 | 真实复杂工单 |

关键判断：反例库（Adversarial）是整个评测集里价值最高、却 90% 团队没有的部分——它不来自「正常用户」，来自你踩过的坑和红队攻击。反例占比低于 10%，这套评测集就只测了「晴天」，一上线遇到「暴雨」必崩。

## 从历史日志半自动生成三元组

纯人工写 50 条「问题-答案-证据」三元组要 8-15 小时，半自动只要 2-3 小时，标注工作量砍到 1/5。要点：

- 用结构化输出（Week 8 的 Structured Outputs）保证 LLM 生成的样本能被代码直接解析。
- 每条样本带 `source_doc` + `doc_version`，评测集与数据资产形成血缘，Week 14 治理直接消费。
- 让 LLM 输出 `category`，评测集天然按 4 类分组，省一道人工标注。
- 关键是「半自动」：LLM 生成 + 人工 review，绝不全自动——反例和边界机器编不出真实感。

实战流程：拉生产 RAG 日志历史 doc → auto-generate 100 条候选 → 人工 review 50 条并修正 → 手工补 10-20 条 adversarial 反例 → 写入 `evals/v1.json`。

## 合格评测样本的字段

绝不是只有 Q&A 两栏，少一个字段就少一种工程能力。

| 字段 | 含义 | 为什么必填 |
| :--- | :--- | :--- |
| sample_id | 唯一标识 | CI 报告关联 / Bad case 跟踪 |
| query | 用户问题 | 评测输入 |
| expected_answer | 标准答案（关键事实） | faithfulness 评测对照 |
| expected_evidences | 应引用的 chunk_id 列表 | context_precision 评测 |
| category | happy / boundary / adversarial | 分层统计，不混在一起算 |
| tags | 业务标签（vip / cn / refund） | 细分分析，定位哪类掉得狠 |
| source_doc + doc_version | 来源 + 版本 | 数据资产血缘 |
| created_at + created_by | 溯源 | 审计 |

没有 category 就只能看总分、看不出哪类掉；没有 doc_version，事故复盘时连「当时用的哪版文档」都查不到。

## 评测集必须绑进 release manifest

不同版本的评测集会算出不同的分，不锁版本，「上线前 vs 上线后」根本没法比。评测集是继索引 / prompt / 模型 / skill pack 之后，第 5 类必须锁版本的对象。manifest 的 `eval` 段要钉死：

- `dataset` 段：数据集 id、version、sample_count，把「这次发布用了哪份评测集」显式钉死。
- `categories` 拆分：一眼看出反例够不够（如 20/150 ≈ 13% 合格）。
- `generated_from`：记清来源（production_logs / bad_case_archive / red_team），告诉你这份集能不能继续扩。
- `digest` 内容指纹：任何样本改动 hash 就变，复盘时精确定位「是不是评测集动过」。
- `baseline_metrics`：下一版上线时的对比基线，也就是回归门禁的硬约束（如 faithfulness 0.892、answer_relevance 0.913、context_precision 0.870、adversarial_pass_rate 0.95）。

## Industry Signals（2026）

评测集资产化早已是行业标准基础设施，开源生成 + 平台托管两条腿都成熟了。

| 工具 / 实践 | 能力 | 怎么用 |
| :--- | :--- | :--- |
| RAGAS TestsetGenerator | 从知识库自动合成 RAG 评测集 | 半自动生成开源首选，先用它探索 |
| DeepEval Synthesizer | pytest 风格 + 数据合成 + CI 集成 | 用 RAGAS 探索，用 DeepEval 卡门禁 |
| OpenAI Evals / Anthropic Eval Recipes | 版本化 eval set + step-by-step 模板 | 别从零造，套官方 recipe |
| Hugging Face Datasets | 数百个公开 eval set | 通用能力直接复用，省采样 |

落地路径：业务垂直集自己半自动生成（RAGAS 探索 + DeepEval 固化进 CI），通用能力直接拿 HF 公开集。把精力花在「反例库」上，那才是护城河。

## Recap

- 评测集是持续演进的数据资产，具备可版本 / 可回归 / 可对抗 / 可治理四个工程属性。
- 4 类样本缺一不可，反例库价值最高且最稀缺，占比低于 10% 就是只测晴天。
- 从历史日志半自动生成三元组省 80% 标注，但反例必须人工补。
- 样本字段是后续所有分析的地基，评测集必须绑进 release manifest 并锁版本。
