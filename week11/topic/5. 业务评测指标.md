# 5. 业务评测指标

## 核心问题

前 4 节做了技术指标体系，最后一讲把它翻译成老板和监管听得懂的话：让评测从「系统好不好」升级为「业务有没有变好」。

真实场景：向 CEO 汇报 AI 客服项目，工程同学一上来就是「Faithfulness 0.89、Context Precision 0.87」，CEO 一脸茫然，反问三个问题——客服自助解决率涨了没？客户满意度上来没？合规拦截率达标没？全答不上来。技术指标再漂亮，翻译不成业务结果，在老板眼里就等于没做。技术指标是手段，不是目的。

## 技术指标好 ≠ 业务好

评测体系必须有一条「业务漏斗」做翻译。F=0.9 是技术指标，「一次解决率 50%→65%」是业务指标，中间隔着好几环：

`Tech 技术指标（F/AR/CP） → Quality 回答质量（用户理解度） → Behavior 用户行为（是否还追问） → Workflow 业务流程（工单是否关闭） → Business 业务指标（自助率/NPS）`

每一环都有「漏斗损失」。如果技术指标涨了、业务指标却没动，一定是中间某一环卡住了——比如答案质量上去了，但 UI 太难用、用户看不懂，工单照样没关。评测体系从第一天就要把这条漏斗画出来，追的是 end-to-end 的业务影响，不是只盯两端的数字自嗨。

## 金融客服域的 4 类核心业务 SLO

任何一类不达标，只能内部 Beta，不能 GA。业务方关心的不是「AI 答得对不对」，是「问题解决没、效率提没提、合规兜没兜住」。

| 类别 | 关键指标 | 目标值 | 关联技术指标 |
| :--- | :--- | :--- | :--- |
| 自助 + 闭环 | 一次解决率 / 自助分流 / 工单闭环 / 升级率 | >65% / >70% / >90% / <10% | Faithfulness + AR |
| 效率 + 成本 | AHT / TTFR / 每单成本 / 重复咨询率 | <5min / <30s / <¥3 / <15% | Latency + Cost |
| 质量 + 体验 | CSAT / NPS / 投诉率 / 无用回答占比 | >4.0 / >30 / <2% / <5% | AR + Citation |
| 风险 + 合规 | 合规拦截率 / 误导率 / PII 泄露 / 引用覆盖 | >99% / <0.1% / =0 / >95% | Adversarial + Audit |

这 4 类合起来 = 金融客服 Copilot 上线门禁。最后一行「风险 + 合规」是红线中的红线——前三类不达标顶多体验差，第四类不达标是监管事件。标准：质量、效率类可以边上线边优化，合规类必须 100% 达标才准 GA，一例 PII 泄露就够上新闻。技术指标和业务指标的对应关系（右列）要从设计期就 wire 死。

## 金融业的 4 条硬性合规红线

这 4 个不是「优化项」，是「红线」——踩了就不是扣分，是出局。

| 红线 | 阈值 | 说明 | 后果 |
| :--- | :--- | :--- | :--- |
| 合规拦截率 | ≥ 99% | 「保证赚钱」「零风险」等高风险话术必须被 AI 主动拦 | 低于 99% = 罚款 + 停业务 |
| 高风险误导率 | < 0.1% | Agent 自己不能说违规话，大流量下 0.1% = 每天数百次违规 | 比拦截更严 |
| PII 泄露率 | = 0 | 身份证 / 卡号 / 手机号任何 PII 进答案 = 监管事件 | 必须 100% 零事故 |
| 引用证据覆盖 | ≥ 95% | 每条专业建议必须能反查依据，监管审计抽查时是合规底线 | —— |

合规指标和质量指标本质不同：质量指标是「越高越好」的连续优化，合规指标是「过线/出局」的二值红线。做法是合规指标单独一块、红色、带阈值告警，Pre-Release Gate 里强制校验，一条不过整个发布卡死。

## 风控域评测完全不同

客服测「答得好不好」，风控测「判得对不对」。风控是离散决策，错一次直接对应资金损失，比客服评测严格 5 倍。

| 类别 | 具体指标 | 看什么 |
| :--- | :--- | :--- |
| 离线模型效果 | AUC / KS / Gini / Precision / Recall / PR-AUC | 能不能区分好坏样本 |
| 在线业务效果 | 拦截损失 / 实际损失率 / 通过率 / 误杀成本 / 净收益 | 上线后的真实业务结果 |
| 运营 + 人审 | 告警量 / 命中率 / 人审吞吐 / 处理时长 / 积压 | 运营扛不扛得住 |
| 稳定性 + 漂移 | PSI / 特征漂移 / 标签漂移 / 阈值敏感性 | 模型在不在悄悄劣化 |
| 合规 + 解释 | 原因码覆盖 / 解释一致性 / 公平性 / 审计可追溯 | 能不能解释 + 合规 |

风控这 5 类必须并行盯，不能只看 AUC。见过团队 AUC 0.88 很得意，结果「在线业务效果」那栏一看——误杀成本高到把拦截收益全吃光，净收益是负的。模型再准，业务上亏钱也是失败。「稳定性 + 漂移」那栏的 PSI 是风控模型的命门，它告诉你模型该不该重训了。

## 风控 3 个最常用指标速记

这 3 个是风控同学张口闭口的「黑话」，必须门清。

| 指标 | 测什么 | 怎么理解 | 阈值 |
| :--- | :--- | :--- | :--- |
| AUC 区分能力 | 任取 1 好 1 坏，模型给坏的打分更高的概率 | AUC=0.85 → 85% 概率排对 | > 0.75 可用 / > 0.85 优秀 |
| KS 区分峰值 | 好坏累积分布最大差距 | KS=0.4 → 某阈值抓 70% 坏、同时误伤 30% 好 | > 0.3 可用 / > 0.45 优秀 |
| PSI 分布漂移 | 当前分布 vs 训练分布 | 是否该重训的最重要信号 | <0.1 稳定 / 0.1-0.25 轻微 / >0.25 严重漂移 |

AUC 看整体排序能力，KS 看最佳阈值处的区分峰值，PSI 看模型有没有过期。前两个是上线前看的（模型好不好），PSI 是上线后天天看的（模型坏没坏）。三个一起才是风控模型的完整体检。

## 把业务 SLO 也绑进 release manifest

上线决策的最后一道门：不再只看技术分，业务指标也得过；Canary 回滚直接挂业务红线。manifest 的 `business_slo` 段要点：

- **`business_slo` 段**：标明 `domain`（如 finance_customer_service），上线决策不再只看技术分，这是给 CEO 看的那一栏。
- **每个指标带 target / current / status**：如 first_resolution_rate、self_service_rate、cost_per_ticket、csat，一眼看出哪个不达标。
- **合规红线单独成组**：compliance_block_rate、pii_leak_rate，Pre-Release Gate 强制校验。
- **`auto_rollback_on` 挂业务指标**：Canary 期间 PII 泄露一例就秒回滚、一次解决率跌破阈值就回滚，这是 Week 11 给 Week 14 治理的关键贡献。

技术指标、业务指标、合规红线全收进一份 manifest，这就是「评测驱动发布」的完整形态。

## Industry Signals（2026）

AI 系统的「成功」必须用业务指标定义，从「技术 KPI」转向「业务 OKR + 合规双指标」。

| 来源 | 做法 | 启示 |
| :--- | :--- | :--- |
| Google SRE | 所有系统都有业务 SLO + 错误预算 | 「100% 可用」不是目标，「满足业务」才是 |
| Anthropic AUP + Evals | 把合规拦截做成产品级评测维度 | 能不能拦住合规风险是硬要求 |
| Salesforce Einstein | AI 成功指标直接挂 Sales/Service KPI | AI 好不好 = 业务好不好 |
| 中国央行 / 金监 / 证监 | AI 客服/风控要「业务效果 + 合规」双指标 | 不能只做技术评测，要算法备案 |

尤其在金融，监管要的是「业务效果 + 合规」双达标——RAGAS 跑得再漂亮，合规拦截率不到 99% 一样上不了线。把业务 SLO 和合规红线绑进 manifest，是这一周送给 Week 14 治理最重的一份礼。

## Week 11 能力栈

五节连起来，就是一套「可量化、可门禁、可监管」的评测体系：

`Dataset 评测集资产（4 类样本） → Metrics RAGAS 6 维 + 性能成本 → Judge LLM 裁判（校准 + 跨评） → Gate 回归门禁（PR/Pre/Canary） → Biz 业务 SLO（领域专属指标）`

有数据、有刻度、有可信的裁判、有牙齿的门禁、有业务和合规的落点。Copilot 的「质量」，第一次从「我觉得还行」变成了一个能写进 release、能卡住 PR、能交给监管看的工程指标。Week 12 起进入可观测，把评测从「事前事中」扩展到「事后实时观察」。
