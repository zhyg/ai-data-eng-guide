# 3. LLM 当裁判

## 核心问题

上一讲那些语义指标，其实都是 LLM 在打分；这一讲把「裁判」本身管起来。LLM-as-Judge 能把人工抽测成本砍到 1/100，但要小心 4 类系统性偏差。

真实场景：第一次用 LLM-as-Judge 的人做法都很自然——把答案 + 标答丢给 GPT，让它打 1-5 分。上线后会发现一堆怪事：同一份答案今天打 4 分、明天打 3 分；排在 prompt 前面的答案分数系统性偏高；写得长的得分高、短的得分低，哪怕内容一样好；judge 模型还偏爱给「和自己风格像」的答案打高分。这不是 prompt 没写好，是 LLM 这种架构的固有毛病。

关键判断：用 LLM 当裁判绝不是「换个 prompt」那么简单，它必须四样配齐——**明确的评分锚点、反偏差约束、人工校准、cross-evaluate**，缺一个评测结果就不可信。一个没校准过的 judge 打出来的 0.9，和算命没区别。

## LLM-as-Judge 的 4 类系统性偏差

注意：不是「换个更强的模型」就能解决，这是 Transformer 架构的固有特性，必须用工程手段对抗。

| 偏差 | 具体表现 | 为什么发生 | 消除方法 |
| :--- | :--- | :--- | :--- |
| 位置偏差 | A/B 顺序换一下分数就变 | LLM 注意力对位置敏感 | 两个顺序各跑一次取平均 |
| 长度偏差 | 长答案分数系统性偏高 | 误以为「长 = 详细」 | prompt 显式声明「长度不计分」 |
| 自我偏好 | GPT 给 GPT 打高分 | 训练数据风格相似 | 永远 cross-evaluate |
| 拒绝偏差 | 说「我不确定」反而比错答得分高 | LLM 偏好谦逊回答 | prompt 显式定义「不确定」的扣分规则 |

踩坑提醒：模型越强，偏差更隐蔽、更难发现，但它还在。别指望「等更好的模型」，老老实实上工程手段：换序取平均 + cross-evaluate + 人工校准。

## 3 种 Judge 模式

没有最好的模式，只有最适配你场景的模式。

| 模式 | 做法 | 适合 | 坑 |
| :--- | :--- | :--- | :--- |
| Pairwise 两两对比 | A vs B 谁更好 | A/B 测试 / 模型对比 | 位置偏差最严重，必须换序 |
| Single Score 单条打分 | 给一条答案打 1-5 分 | 批量评测 / 历史趋势 | 分数飘 ±1，必须锚点校准 |
| Reference-based 对标答 | 答案 vs 标准答案对照 | 有 ground truth 的场景 | 标答构建成本高（但值） |

关键判断：生产默认 Reference-based——有标答兜底，judge 发挥空间最小、最稳。Pairwise 准但只给相对结果（适合选型），Single 灵活但飘（适合看趋势）。一句话：能构建标答就别裸评。

## 一份生产级 judge prompt 的要点

一份好 judge prompt 和差的，同一批数据能差出 30% 的一致性。以 faithfulness 的裁判为例，四个关键设计：

- **评分锚点分 4 档**：如 1.0 全部 claim 有支撑、0.7 大部分支撑仅 1-2 处轻微外推、0.4 半数编造、0.0 大部分捏造。LLM 不再在 0-1 之间自由发挥，分数标尺被钉死。
- **IMPORTANT 段直接对抗偏差**：显式声明「不因答案长度加分」「上下文不足时『我不知道』给 0.5」「换过措辞的引用仍算支撑」，把长度偏差、拒绝偏差在 prompt 里强制约束。
- **calibration anchor 示例**：给 LLM 看具体的对错示例（如同一段重置密码流程，忠实转述给 1.0，编造出「5 步、先登录」给 0.4），把刻度校准到位。
- **结构化 JSON 输出**：输出 score、reason 和 unsupported_claims，能被代码消费、回流反例库。

prompt 才是 LLM-as-Judge 的真正灵魂，改几个字效果能差 30%。

## 用人工金标准校准

LLM judge 像一把自动卷尺，出厂刻度不一定准，必须用人工标注校准。标 100 条人工金标准，跑 judge 看一致性。

| 一致性指标 | 怎么算 | 建议阈值 | 不达标怎么办 |
| :--- | :--- | :--- | :--- |
| Cohen's κ | 排除随机一致后的真实一致度 | > 0.6 = good | 改写 judge prompt |
| Pearson r | 连续分数的相关系数 | > 0.75 | 加 calibration anchor |
| MAE | 平均绝对误差（0-1 scale） | < 0.15 | 换更强的 judge 模型 |
| Top-K 一致 | 人工 top-K 与 LLM top-K 重合度 | > 80% | 看具体偏差类型对症下药 |

4 个指标从不同角度看一致性，单一指标会误导：κ 看分类一致、r 看趋势、MAE 看绝对误差、Top-K 看排序。κ > 0.6 是 Krippendorff 那条通用阈值，低于它 judge 和人的判断分歧大到不能用来做决策。

规矩：这 100 条金标准只需标一次（重大场景变更再重标），却是整套自动评测的「信任之锚」；judge prompt 一改必须重跑校准，因为改 prompt 等于换了个裁判。校准报告随 judge prompt 一起 git 跟踪，`trust_level` 写进 release manifest，judge 不可信这次发布就该卡住。

## Cross-Evaluate：用不同 family 模型互相打分

单模型 judge 有自我偏好，尤其当 RAG 本身也用同一模型生成时。

| 策略 | 具体做法 | 成本 | 准确度 |
| :--- | :--- | :--- | :--- |
| Single Judge | 只用一个 LLM 评判 | 1x | 低（有 bias） |
| Pair Judge + Average | GPT-5 + Claude 各跑取平均 | 2x | 中高（消除大部分 bias） |
| Pair Judge + Disagree Flag | 两家分歧 > 0.3 标记人工二审 | 2x | 高 |
| Multi-Judge Voting | GPT-5 + Claude + Gemini/DeepSeek R1 投票 | 3-5x | 最高（合规 / 资金场景） |

生产推荐：常规评测用 Pair Judge + Average（如 GPT-5 + Claude Sonnet 4.6，预算紧可用 DeepSeek R1 当便宜的第二裁判），成本翻一倍但把系统性偏差基本消干净。高风险场景（合规话术、资金动作）上 Multi-Judge Voting。记住最隐蔽的陷阱：RAG 用 GPT-5 生成、又用 GPT-5 当裁判，分数高得离谱也别信，那是自己夸自己。

## Industry Signals（2026）

pairwise + cross-evaluate + 校准锚点，已是公认底座。

| 来源 | 关键结论 | 工程含义 |
| :--- | :--- | :--- |
| Anthropic Eval 实践 | 推荐 Pairwise + Cross-Evaluate，避免自评 | 裁判和选手不能是一家 |
| OpenAI gpt-judge 公开数据 | LLM judge vs 人类 κ ≈ 0.62-0.7 | 可用但必须校准，别裸信 |
| LMArena（原 LMSYS Arena） | pairwise 模式与人类一致性 > 80% | pairwise 是事实工业标准 |
| DeepEval / Braintrust | 内置 judge 反偏差 + 校准 anchor | 别自己从零写 judge 框架 |

GPT-judge 和人类的一致性 κ 也就 0.65 上下——可用、但必须配人工校准 + cross-evaluate。谁跳过校准直接拿 judge 分数做上线决策，谁就是在用没校准的仪器做手术。

## Recap

- LLM-as-Judge 必须四样配齐：评分锚点、反偏差约束、人工校准、cross-evaluate。
- 4 类系统性偏差是架构固有特性，换更强的模型解决不了，只能用工程手段对抗。
- 生产默认 Reference-based，能构建标答就别裸评。
- 用 100 条人工金标准校准，κ < 0.6 的 judge 不能拿去做生产决策；改 prompt 必须重新校准。
