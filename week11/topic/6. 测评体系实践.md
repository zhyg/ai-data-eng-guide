# 6. 测评体系实践

## 实践目标与整体链路

本周的核心任务是为 Copilot 建立一套质量控制体系。前几周已经实现了 RAG 回答问题和受控 Agent 动作，但业务方不仅关心「能不能答」，还关心问题变化、性能退化、证据准确性和安全性。本节的目标不是「生成一份评测报告」，而是让报告参与发布决策。

整条链路从 RAG 输出开始，一路串到发布治理：

`RAG 产物 → 黄金测试集（标准答案 + 证据） → models 把 JSON 转判断对象 → metrics 算分 → Runner 编排 → regression 防退化 → calibrate 校准 → release manifest 绑定发布`

## 上游产物与评测输入

RAG 的一次产物包括答案、上下文、时间戳、证据引用、置信度和 trace_id。真实入口在 `rag.py`，返回 answer、citations、context 和 trace_id，背后是 vector + BM25 检索加 rerank 的检索链路，为本周提供 context 和 events。

为了让评测稳定可复现，本周提供一套 evals fixture 作为离线数据（含 case 数据和 case_id）。演示时用固定的上下文和答案跑通控制面，先确认频次和契约，再接真实 RAG API。

## 评测集资产与契约

黄金测试集作为评测集资产，需绑定数据集 ID、版本和指纹等信息。本周用两份 schema 把资产钉死成契约：

| 契约 | 约束对象 | 作用 |
| :--- | :--- | :--- |
| `dataset_schema` | 黄金数据集每条样本 | 每条样本必须包含规定字段，缺字段即不合格 |
| `eval_report.schema.json` | Runner 输出的评测报告 | 报告结构固定，后续接入 CI & release gate |

`golden v2.3` 包含 8 条真实样本，全面覆盖 happy path、boundary、adversarial、multi-hop 四类，每个 case 的标准答案、关键词、证据以及拒答阈值都清晰定义。

## 核心对象模型

第 11 周的核心是一套结构化对象模型，让后续所有文件操作对象、而不是散乱的目录。

| 对象 | 职责 |
| :--- | :--- |
| EvalSample | 从黄金数据集读取的标准样本，含 category、expected_answer、expected_citation_ids、should_maintain 等字段 |
| context 统一处理 | 兼容 timestamp、证据锚定、trace_id 等字段 |
| predictions | 统一处理预测输出，含检索的 citations、confidence、cost、延迟 |
| CaseScores | 记录单个 case 的评分 |
| EvalCaseResult | 汇总样本与预测结果 |
| eval_input | 把上述内容串联，构成全链路对象模型 |

## 数据加载与指纹

`dataset` 中的 `load_eval_sample` 逐行读取 JSON 转为 EvalSample，出错时显示文件行号方便定位，并检测空集和重复 case_id。`dataset_digest` 对评测内容做哈希，`dataset_manifest` 生成 ID、version、sample_count。这些设计确保评测集作为数据资产的完整性——任何改动都会改变 digest 和 release 版本。

## 指标计算

`metrics.py` 是本周最重要的文件，它把「感觉答案不错」变成可解释的分数和失败原因。`single_case` 是单个 case 的总入口，返回所有评分，包括：

- answer token 与 context token 的重合度。
- 近似计算的忠实度（课堂版 deterministic heuristics）。
- `context_precision`：召回上下文中与预期答案或关键词相关的比例。
- 召回度、关键词覆盖、语义相似度、答案正确性等。

## Runner 编排

Runner 编排具体运行路径，把样本、预测结果、指标和门禁汇总成评估报告：

- `run_with_predictions`：离线路径，用黄金数据集和 fixture 跑结果，稳定复现。
- against the RAG API：真实路径，通过并发调用 `run_answer` 实现。
- `gate_decisions`：根据 pass_rate 决定门禁结构，做测试门禁，并生成报告与日志。

编排本身是辅助性的，本周重点在下面的回归门禁。

## 回归门禁与校准

`regression.py` 是回归门禁的核心，不只看绝对分数，而是检查新版本是否退步：从评测报告或纯 metrics JSON 抽取指标，与上一版对比检测退化。`eval baselines` 里存了本周基线，代表当前版本的质量标准，阈值决定是否阻断。

`calibrate` 通过 Cohen's Kappa 等指标比较人工评分与大模型评分，确保 LLM 判断与人工标签对齐，预期 `trust_level: high`。注意：模型或风控样本一旦变化，都要重新校准并再跑 A/B 测试。此外还有生产环境的大模型 judge 模板，以及做样本对比与统计检验的 A/B 测试。

## 发布契约绑定

业务 SLO 把技术指标翻译成业务需求，用 pass / fail 评估，确保技术成果能被上级认可。`release_manifest_schema.json` 定义发布契约：在 Week 10 的基础上，本周新增 `eval_dataset`、`judge_calibration` 和 `business_slo` 三块，纳入发布治理。示例 manifest 展示了如何绑定本周评测结果。

## 课堂验证

实验按「先契约、再离线、后回归」的顺序跑通：

1. **文件齐备检查**：运行命令确认本周所需文件全部就位。
2. **契约测试**：位于 `tests/contract`，默认跑 `eval_contracts.py`，通过后确认黄金数据集、prediction fixture、release manifest 都符合契约——这是后续评分的基础，不符合契约后面的评分就没有意义。
3. **离线评测**：跑 RAGAS fixtures 模块，输出 Metrics 和 gate，确认 `gate_status` 为 passed 且 `report_path` 存在，用离线 fixture 稳定跑通评测控制面。
4. **评测报告摘要**：在控制台查看报告概览。
5. **回归门禁**：拷贝 baseline（`metrics.json`），再跑 regression gate 对比退化。
6. **校准验证**：通过 human 金标准跑校准，确认 `trust_level: high`。
7. **全量测试**：运行本周全量测试，确保所有样本通过。

## 收尾

第 11 周的目标是让评测报告参与发布决策，而不是躺在周会 PPT 里。整条链路把「能评测」升级为「评测能卡住发布」：评测集资产化并锁版本，指标可解释、可诊断，裁判经过人工校准，门禁能阻断退化，业务 SLO 和合规红线绑进 release manifest。评测让你知道「好不好」，Week 12 的可观测会让你知道「出事了在哪、为什么」。
